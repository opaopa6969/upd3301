# 設計 — upd3301

## 契約（suite-contract 準拠）

- pure・依存ゼロのJavaScript。DOMなし・`three`なし・`Math.random`禁止。
- 決定論：同じポート書き込み＋同じメモリ＋同じ `update(dt)` 列 →
  ビット単位で同一の画面。ブリンク位相はフレームカウンタのみから導出。
- 固定ステップ：`update(dt)` は秒を積算し `frameHz`（既定60）でフレーム
  単位に実行。テスト用に `stepFrame()` も公開。
- 出力は plain data + `schemaVersion`：`getScreen()` はスカラと typed array
  （文字コード、生アトリビュートペア、展開済みアトリビュート）を返す。
  コアはアトリビュートバイトの「意味」を決めない — 下流が読んで判断する。

## レイヤと依存の向き

```
index.js  （μPD3301チップ — メモリも色もPC-8001も知らない）
upd8257.js（μPD8257 DMA — CRTCを知らない）
   ↑ 両方を import するのが
pc8001.js（配線＋アトリビュート意味論＋レンダラ＝「下流」）

crt.js   （物理層1: 蛍光体 — GRBインデックスのフレームを消費）
tube.js  （物理層2: マスク/ガラス — リニア光の3プレーンを消費）
   ↑ 全部を組み合わせるのは
demo/    （ブラウザデモ。手描きCGROMを注入）
```

論理スタック（index/upd8257/pc8001）と物理スタック（crt/tube）は互いに
import しない。demo/テストの層でだけ、plain data（インデックス画素→
輝度プレーン→RGBA）で接続される。物理スタック内では tube.js が crt.js の
純関数ヘルパ（tintMatrix）のみを import する。

`index.js` と `upd8257.js` は sibling を import しない。ループを閉じる
コーディネータ（DRQ → DMA pull → 行バイト）は `Pc8001TextSystem`。

## 主要スキーマ

`getScreen()`（schemaVersion 1）:
`{cols, rows, linesPerChar, skipLine, reverseDisplay, displayEnabled, frame,
cells: u8[rows*cols], attrs: u8[rows*cols], attrPairs: u8[rows*attrsPerRow*2],
attrsPerRow, attrMode, cursor {x, y, enabled, blink, block, on}, attrBlinkOn}`

`renderScreen()` → `{width, height, pixels: u8[w*h]（0..7 GRBインデックス）,
ink: u8[w*h]（1=そのピクセルに文字ドットが描かれた、0=空白）, schemaVersion}`。

`ink` マスクは色とは独立。黒文字（fg=0）はピクセル0を書くが、色だけでは
「文字なし」と区別できない。`ink` により PC-8801 側のコンポジタは
グラフィック面の上に文字を不透明に重ねられる（黒/反転文字でオフスク
スクラッチを隠せる）。合成しない呼び出し側は無視してよい。

## 設計判断

- **DRQはpull型コールバック。** チップは行ごとに `drq(buf)` を呼び
  `桁数 + 2×アトリビュート数` バイトを期待。不足はUビット（アンダーラン）
  を立て、非公開のステータスbit7が落ちる — 実機と同じ。
- **アトリビュート展開**はMAMEの `default_attr_fetch` 準拠
  （fill-forward。先頭ペアは0桁目まで遡って充填。2ペア目以降の位置0は
  行末扱い — N-BASICが未使用スロットをそう埋めるため）。
- **PC-8001の2状態デコード**はチップの外：カラー指定（bit3=1）と機能指定
  （bit3=0）は別々の状態を更新する。色を変えても反転/点滅は解除されない。
- **CGROMは注入式。** 実機のキャラジェネROMは著作物なので同梱しない。
  テストは合成グリフ、デモは手描き5×7フォント。
- **タイミングはフレーム粒度。** ドットクロックなし。1フレーム分のDMAは
  `stepFrame()` 内で行順に実行（実機の水平帰線バーストと同順）。VRTCは
  フレーム終端の割り込み/ステータスとして観測（フレーム途中の線は見えない）。
- **`resetEx` は弾く、ポート経路は切り捨てる。** ポート経由のRESETは
  80×64・20ペアより大きい値を物理的に要求できないので、`_applyResetParams`
  の `Math.min` は**シリコンそのもの**。一方 `resetEx` には切り捨てる
  シリコンが無いので、黙って別の画面を返さず投げる（`MAX_EX_ROWS`,
  `MAX_EX_ROW_BYTES`）。代入前に全引数を検証するので、弾かれた呼び出しは
  チップを直前のジオメトリのまま残す（中途半端な再構成をしない）。
- **点滅周期はひとつ、レートはふたつ。** `blinkPeriodFrames()` が両方の
  点滅レートの唯一の出どころで、2以上の偶数にクランプする。これにより
  「アトリビュートはカーソルの半分のレートで点滅する」が、初回RESET前の
  チップが持つ 0 を含めた全ての値で成立する。ポートの符号化は
  (B+1)×16 の倍数しか作れないので、この正規化が実機の周期に触ることはない。

## 未検証の挙動（分かっていないこと）

このモデルには、実機で確認が取れていない挙動が2つある。「直す」のではなく
ここに記録する。どちらも変更すれば353本のPC-8801比較が動くのに対し、
それを正当化するだけの根拠が揃っていないため。**この2点について
現在のコードを典拠にしないこと。**

### SET INTERRUPT MASK がステータスに与える副作用（issue #22）

**うちの実装。** VRTC割り込みのマスク解除（`010x_xx?0`）で E/LP/N/U を
クリアし、**VE は残す**:

```js
this.interruptMask = value & 3;
if ((this.interruptMask & 1) === 0) this.status &= STATUS.VE;
```

**MAME の実装**（`src/devices/video/upd3301.cpp` 原文）:

```cpp
// Unmasking ME has the side effect of clearing all status bits except bit 7
// pc8801:laptick implictly expect text layer to be concealed by running this command alone
if (!m_me)
    m_status = 0x80;
```

MAME の `get_display_status()` は `m_status & STATUS_VE` で、偽なら
`screen_update()` は何も描かない。つまり MAME では VRTC のマスク解除が
**VE を落としてテキスト面を消す**（次の START DISPLAY まで）。そして
MAME のコメントは、実タイトル `pc8801:laptick` がそれに依存していると書く。

**分かっていること:**

- クリアの副作用が存在すること自体は両実装で一致している。ここは争点ではない。
  データシートの E の「読み出しでクリア」は、この副作用について
  **矛盾しているのではなく単に何も言っていない**。
- 食い違うのは **VE ビットだけ**。MAME は落とし、うちは残す。さらに
  うちのモデルでは VE はフェッチに影響しない（表示ゲートは
  `SET INTERRUPT MASK` が触らない別フィールド `this.ve`）ので、
  MAME に合わせるなら `this.ve` も落とすかどうかを決める必要がある。

**分かっていないこと:**

- 実機の μPD3301 がここで VE を落とすのか。この副作用に触れた
  データシートの記述は見つかっていない。MAME のコメントが挙げるのは
  データシートではなく**あるゲームの観測された要求**。
- 採用するとPC-8801のパリティが上がるのか下がるのか。**未測定。**
  実験は安くて具体的：`status = 0`（VEを落とす）＋ `this.ve = false` を当てて
  `tools/batch-compare.mjs` を353本に回し、現在の基準（完全一致326 /
  追従334 / blank 0）と比べる。**根拠と実測の改善が揃ったときだけ採用する** ——
  「典拠が正しい」と「実装が正しい」は別、というのが走行の教訓。

`test.mjs` が現在の挙動を固定している（"SET INTERRUPT MASK unmask keeps VE"）
ので、変更するときは落ちるテスト付きの意図的な行為になる。ドリフトはしない。

### μPD8257：モードレジスタ書き込みとバイトペアのフリップフロップ（issue #24）

**うちの実装。** `writePort(8, …)` は `modeReg` を設定し、共有の
ロー/ハイ フリップフロップをクリアする。

**典拠が言っていること。** MAME の `i8257_device::write` は
`m_transfer_mode` を設定するだけで、`m_msb` をクリアするのは
`device_reset()` のみ。Intel 8257 のデータシートは F/L フリップフロップを
「チャネルレジスタのアクセスでトグルし、RESET 入力でクリアされる」と説明し、
Mode Set 書き込みでクリアされるとは書いていない。（入手できた
データシートPDFはスキャン画像なので、これはその二次転記に基づく。
強い根拠だが一次資料そのものではない。）

**直さない理由。** 差が観測できるのは、モード書き込みがバイトペアの
**途中**に挟まったときだけ。このコードベースにその順序は無い
（`initTextMode` は 0x68 を先に書く。N-BASIC もその順）ので、
乖離は潜在的なまま。それでも取り除くのは353本の判断になる —— 実タイトルが
逆順でDMACを設定している可能性があるため。`test.mjs` はテスト名に
乖離であることを明記した上で現在の挙動を固定している。

## やらないこと

ライトペン、特殊制御文字（STATUS N）、DMAキャラクタモードとバースト
モードの区別、コンポジット映像のアーティファクトカラー。

## 検証

`node --test`（49ファイル・1027ケース）：ジオメトリのデコード、行DMAバイト数、アンダーラン、
アトリビュート展開、VRTC割り込みマスク、カーソルブリンクの決定論、
固定ステップのフレーム正確性、8257のフリップフロップ/オートロード、
2状態アトリビュートデコード、フルシステム描画の決定論（2回実行の
ビット一致）、ベーマガ27色技（カウント2倍→2画面交互→オートロードで
巻き戻り）、40桁ドット倍幅、画面反転。

境界は「近い値」ではなく**実際に壊れる値**を踏む：`blinkPeriod` の 0/1/奇数
（2:1の点滅比）、`resetEx` への 負数 / 小数 / NaN / 文字列 / 過大ジオメトリ
（ガード前はそれぞれ別の壊れ方をした —— 素のtyped-array RangeError、黙って
切り詰められた画面、文字列連結された行長、何も報告しない0×0チップ、
プロセスの停止）、DMACポート窓の 0x5e–0x6b 全走査、そして上記2件の
未検証挙動の固定。
