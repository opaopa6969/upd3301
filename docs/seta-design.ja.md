# Seta アーケード基板

セタの初期アーケードハードをこのリポジトリの「機種」として実装したもの。68000 が1個、
スプライトと背景の両方を描く custom が1個、RAM から16音を鳴らす custom が1個、
ワークRAM 16KB、以上。BIOS もディスクもキーボードもバンク切替も OS も無い。

`machine88.js` / `machinenes.js` / `machinemd.js` / `machinex68.js` と同じ契約
（`stepFrame()` / `frame` / `snapshot()` / `restore()` / `schemaVersion`）を満たすので、
`demo/machine.html` はこの機種を何も知らないまま早送り・巻き戻し・ジョグシャトルを提供する。

**3本のゲームが MAME 0.242 と1ピクセル単位で一致することを確認済み。**
サンダー＆ライトニングはデモ1分ぶん・21フレームを抽出して**すべてで 92160画素中 0画素差**。
ウルトラマン倶楽部と Krazy Bowl も各6フレームで一致。手順は 9 節。

## 1. 何を作ったか

| ファイル | 中身 |
|---|---|
| `setarom.js` | MAME の ROM セット。基板ごとのチップ配置、バイトインターリーブ、CRC による同定、リージョンへの組み立て |
| `x1001.js` | X1-001 / X1-002 スプライト対。タイル展開、スプライト512枚、浮動タイルマップ、ラップ、反転 |
| `x1010.js` | X1-010 音源。16音、ROM からの PCM と、チップRAM からの波形＋エンベロープ |
| `machineseta.js` | 機種本体。ページテーブル方式のアドレスデコーダ、4種の基板配線、割り込み、プロテクトPAL、操作系、フレームループ |
| `setatools/boot.mjs` | headless実行、フレーム統計、ASCIIサムネイル、スナップショット実測 |
| `setatools/mameref.lua` | 神託側。指定フレームで MAME の状態、または画面の画素をダンプする |
| `setatools/mameref.mjs` | 突き合わせ。こちらを同じフレームまで走らせて、領域ごと／画素ごとに差分を取る |
| `test-seta.mjs` | `node --test` 44件。**1件も ROM を必要としない** |

`package.json` に `./setarom` / `./x1001` / `./x1010` / `./machineseta` を追加した。
`m68000.js` は**無改造**で使っている（メガドライブと X68000 が依存しているのと同じファイル）。
`tools/` は触っていない。

## 3. 基板

サンダー＆ライトニング。セタが出したなかで最も単純なもの:

```
                +-------------+
   16 MHz  ---> |   /2        | ---> MC68000  @ 8 MHz
                +-------------+
                      |
   $000000-$00FFFF    | プログラムROM 64KB（32KB×2、インターリーブ）
   $FFC000-$FFFFFF    | ワークRAM 16KB
   $100000-$103FFF    | X1-010  16音、チップRAM 8KB、サンプルROM 1MB
   $200000            | 割り込みアック
   $400000-$41FFFF    | PAL16V8、書き込み専用（プロテクト）
   $500001            | コインカウンタ / ロックアウト / サウンドイネーブル
   $600000-$600003    | DIPスイッチ
   $700000-$7003FF    | パレット512本、RRRRRGGGGGBBBBB
   $B00000-$B0000D    | 操作系と、プロテクトの読み出し
   $D00000-$D00607    | X1-001  スプライトY、タイルマップスクロール、制御4バイト
   $E00000-$E03FFF    | X1-001  スプライトのコード・X・色（8Kワード）
```

画面は 512x256、そのうち 384x240 がモニタに配線されている。そして**モニタは横倒し**
（ROT270）なので、プレイヤーが見る画は 240x384 の縦長。`render()` は既定で回転させる。
`render({ rotate: false })` で基板そのままの向きが得られ、MAME との比較はこちらを使う。

### アドレスデコーダ

Seta の基板はどれも「同じ3つのチップ＋デコーダの配線違い」なので、基板を
**「64KBページごとに何があるか」の256エントリの表**として持ち、read/write はそれで分岐する。
ページ内の細かいデコードは基板に依存しない。セタが毎回チップをページ内の同じオフセットに
置いたからで、スプライトYは常に `$x00000-$x005FF`、制御4バイトは常に `$x00600` にある
（`x` が何であっても）。基板を足すのは `SETA_BOARDS` に1行足すことであって、ファイルを書くことではない。

### バイトアクセスは合成せず自前で持つ

`m68000.js` は `read16`/`write16` から `read8`/`write8` を合成できるが、合成は
read-modify-write になる。そしてこのマップの半分は「読むだけで副作用があるレジスタ」で、
`$200000` は**読むと**割り込みがアックされる。そのページへのバイト書き込みが毎回それを撃つ。
だから4本とも自前で渡している。実機もそうしている（68000 には UDS/LDS のバイトストローブがある）。

### custom は8bit幅

X1-001 の制御レジスタとYテーブルは、68000基板でもチップ内部は8bit幅なので、
**ワード書き込みは下位バイトしか届かない**。上位バイトを親切に保存する実装は、ゲームが
16bit定数を書いた瞬間から実機とずれていく。`$E00000` のコードテーブルは本当に16bit
（CPU とチップが共有する外付けRAM）なので両方保持する。

## 4. ROM セット

家庭用のカートリッジは1ファイル。アーケードの ROM セットは**チップ1個につき1ファイル**で、
組み直すには配線を知っている必要がある。

**配線は2通りあって、間違えると起動しない。** 68000 は 8bit ROM 2個から並列に16bit取る。
片方が D15-D8（偶数アドレス）、もう片方が D7-D0。だからプログラムROM対は
**インターリーブ**（0番地は1個目、1番地は2個目、2番地は1個目…）。逆にすると、
最初に起きることがリセットベクタの読み出し失敗で、1命令も実行せずに死ぬ。
グラフィックROMはどちらの配線もあり得て、セタは両方使った。`thunderl` のスプライトROMは
インターリーブ対、`krzybowl` は普通の連結半分。ファイル自体からは区別できないので、
`setarom.js` の表に記録してある。

**照合はファイル名ではなく CRC32。** 同じ内容が `t17` だったり `25.a10` だったり
`un001008.7l` だったりする。セットは改名されるし、親子マージされるし、サブディレクトリに
展開される。MAME が公開している CRC で照合すればそれが全部どうでもよくなるし、
おまけに「これは別リビジョンだ」と言えるようになる（黙って絶対起動しない基板を組む代わりに）。
名前照合はフォールバックで、使うと警告が出る。

```js
import { loadSetaRomSet } from './setarom.js';
import { SetaMachine } from './machineseta.js';

const romset = await loadSetaRomSet(zipBytes, { name: 'thunderl.zip' });
const m = new SetaMachine({ romset });
for (let i = 0; i < 1200; i++) m.stepFrame();
const { width, height, rgb } = m.render();
```

`loadSetaRomSet` は MAME のセット zip のバイト列（`zip.js` で展開する）でも、展開済みの
ファイルの束でも受ける。どれにも一致しない zip は、雑音を映す基板に読み込む代わりに拒否する。

**ROM はこのリポジトリに一切コミットしていない。** 入手先とツールへの渡し方は 9 節。

## 5. X1-001 は「スプライトチップ」ではない

名前に騙されると1日溶ける。このチップは**同じ RAM から2種類**を描く:

* **自由スプライト512枚** — 任意座標の16x16タイル。奥から手前へ描くのでスプライト0が最前面。
* **浮動タイルマップ** — 2x16タイルの列を最大16本、列ごとにスクロール対を持つ。
  名前以外はタイルマップそのもので、**タイルマップチップの載っていない基板が
  プレイフィールドを出せる理由**がこれ。

スプライトだけ実装すると、サンダー＆ライトニングは走るしコインも入るし、
キャラが真っ平らな背景の上に浮く。その症状はパレットのバグに見える。

推測では絶対に当たらない規則が3つ:

1. **スプライトのY軸は上向き**で、256ラインの下端から測る:
   `y = height - ((spriteY + yoffset) & 0xff)`。タイルマップ側は違う。
   両方に同じ規約を使うと、プレイフィールドとその上のコマが別世界に行く。
2. **すべてラップする。** どのタイルも `x - 512` と `y - 256` にもう一度描く。
   省略できる最適化ではない。座標フィールドは9bitと8bitしかなく、
   「左端から入ってくるスプライト」はカウンタが回った状態として表現される。
3. **バンクビットは「ビット」ではなく「比較」。** `ctrl[1]` の bit5 と bit6 を
   互いに比較してコードテーブルのどちら半分が有効かを決める。そして**全部0だと
   後ろ半分が選ばれる**。オフセット0から埋めてレジスタを0のままにしたテストは何も描かない。

### タイルの形式

スプライトROMは16x16タイル・4プレーンで、プレーンは**リージョンの前半と後半に分かれている**。
前半がプレーン0と1、後半がプレーン2と3。半分の中では1タイル64バイトで、
16バイトの4象限（左上・右上・左下・右下）。象限の中では1行2バイトが2プレーンで、MSBが左端。

`decodeSpriteTiles()` は読み込み時に1回だけ全部を1画素1バイトに展開する
（`thunderl` の4096タイルで1MB）。ROM由来なので読み込みのたびに作り直し、
**スナップショットには絶対入らない**。`test-seta.mjs` は逆関数を持っていて往復を検査するので、
デコーダは「動かしてみた」ではなく「証明した」状態になっている。

### 色

スプライトもタイルマップタイルも4bit深度＋5bitのカラーコードなので、ペンは
`color * 16 + pixel` で 512本の `RRRRRGGGGGBBBBB` パレットを引く。各チャンネル5bitは
DAC と同じやり方で8bitに伸ばす（上位3bitを下位に繰り返すのでフルスケールが255になる）。
背景は**パレット496番**であって0番ではない。黒でクリアする実装は、実機に無い黒縁が出る。

タイルコードは14bitだがROMには16384タイルより多く入っているので、カラーワードの2bitが
16Kタイル単位のバンクを選ぶ。これが無いとゲームは後半のグラフィックに一切到達できない。

## 6. X1-010 — 16音、レジスタの意味が2通り

1音につきレジスタ8本。そして**1ビットで残り7本の意味が変わる**:

* **PCM**（bit1=0） — サンプルROM から 8bit符号付きをそのまま鳴らす。開始と終了は
  4KB単位で、終了フィールドは `0x100 - ブロック番号` として格納されている。
  つまり**長いサンプルほど小さい数**。ステップは 4.4 固定小数。
* **波形**（bit1=1） — チップ自身のRAMにある128バイトの波形を 6.10 固定小数のピッチで鳴らし、
  音量はやはりチップRAM内の128バイトのエンベロープからサンプル毎に取る。

分岐を間違えると雑音ではなく無音になる。波形用のレジスタ値を PCM 側で読むと、
終了判定が即座に成立するから。

**キーオンはエッジ。** bit0 の 0→1 で発音位置とエンベロープが巻き戻る。
同じ値をもう一度書いても再発音してはいけない。

**レート。** チップは clock/512 で走る（16MHz水晶なら 31250Hz）。ここではネイティブレートで
生成して、次のサンプルが来るまで前の値を保持する（整数の位相アキュムレータ）。
ゼロ次ホールドで、演算が整数のままなので**復元したスナップショットからビット単位で同じ音**が出る。
足されるエイリアスは 8bit ソースがもともと持っている量より上にある。
ポリフェーズのリサンプラの方が正しいが、入れていない。

**サウンドイネーブルはミキサを止めない。** コインロックアウトレジスタにそのビットがあり、
状態としては保持するが、ゲートには使っていない。MAME が「ゲートすると、そのビットを
一度も立てないゲームが無音になる」ことを見つけているので、実チップはもっと別のことを
しているらしい。同じ判断・同じ理由。

## 7. 割り込み

`SETA_BOARDS` に2方式:

* `vblank2`（thunderl, wits） — 垂直帰線の開始でレベル2を上げ、ゲームが `$200000` に
  触るまで**上げっぱなし**。**読み出しでもアックされる**（書き込みだけではない）。
  セタのゲームは結果を捨てる `MOVE` でアックすることが何本もあり、書き込み専用ハンドラだと
  レベルが下りずゲームはハンドラに入り続ける。
* `scanline12`（krzybowl） — 112ラインでレベル2、240ラインでレベル1。どちらも 68000 の
  割り込みアックサイクルで落ちる。`m68000.js` はそのサイクルで `bus.irqAck` を呼ぶので、
  そこで落としている。負値を返すとオートベクタのままになり、これらの基板の挙動と一致する。

割り込み**ライン**は CPU が覚えるものではなく機種が駆動するものなので、`restore()` は
再アサートする。復元直後の1命令が、復元前の1命令と同じピンを見るようにするため。

## 8. フレームと、画を取る瞬間

クロックは60で割り切れない（8MHz なら 1フレーム 133333⅓ サイクル）ので、余りは整数で持ち回る
（3フレームに1サイクル追加）。ここで float を使うと、同じ入力の2回の走行が数分で分岐する。
巻き戻しが最も許容できない性質。

**1ステップは垂直帰線の最初のラインから始まる。** 0ラインからではない。これは自明な位相では
なく、この機種で一番おもしろい判断。要求が2つあって逆方向に引っ張る:

* 画は**帰線の始まりで**取らなければならない。それがモニタが今スキャンし終えたものであり、
  ゲームの帰線ハンドラが次のフィールド用にスプライトRAMを書き換える前だから。
  それより後で取ると、プレイヤーが見られたはずのない書き込みが混ざる。
* 画は**スナップショットの関数**でなければならない（履歴の関数ではなく）。でないと
  `restore()` は復元先のフレームを再現できない。

普通の位相のまま帰線で描くと、1つ目は満たすが2つ目を落とす。スナップショットが持っている
スプライトRAM は**ハンドラが走った後**の状態で、そこから描き直すと違う画になる。
これは推測ではなく実測で、サンダー＆ライトニングの250スロットを巻き戻したら
**61スロットで違うフレームに着地した**。時間操作を実際に使ったときにしか出ない種類の欠陥で、
契約を紙の上では満たしている機種でも起こりうる。

帰線からステップを始めると両方満たせる。ステップの終わりで描く＝帰線の始まりで描く、
になるから。他は何も変わらない（割り込みは同じラインで出るし、サイクル配分も同じ）。

パレットも同じ瞬間にコピーする。ゲームは帰線中にパレットを書き換えてよく、
コピーが無いと、後で復元したスナップショットが古い画を新しい色で解決してしまう。

## 9. MAME を神託にする

MAME には `seta.cpp` ドライバがあるので、着手前から答え合わせの相手がいる。
PC-8801 の M88（`docs/m88-comparison.md`）と違い、**パッチも再ビルドも要らない**。
`-video none` ＋ Lua スクリプトで足りる。

### MAME を入れる

`apt install mame` で 0.242。root が無い場合でも、deb と依存を `dpkg-deb -x` で展開して
`LD_LIBRARY_PATH` を展開先の `usr/lib` に向ければ動く。0.242 で知っておくべきことが2つ:

* `emu.add_machine_frame_notifier` は**まだ無い**。フレームフックは `emu.register_frame_done(fn)`。
* 終了時に必ず segfault する（速度行を出し切った後）。**終了コードは成否判定に使えない**ので、
  出力ファイルが完結しているかを見ること。

### 状態を領域ごとに突き合わせる

```sh
SETAREF_OUT=/tmp/ref.txt SETAREF_FRAMES=10,60,300 \
  mame thunderl -rompath <dir> -video none -sound none -nothrottle \
    -skip_gameinfo -seconds_to_run 8 -autoboot_delay 0 \
    -autoboot_script setatools/mameref.lua

node setatools/mameref.mjs --zip <dir>/thunderl.zip --ref /tmp/ref.txt
```

`mameref.lua` はワークRAM・パレット・スプライト両テーブル・制御バイトを
**CPU 自身のアドレス空間経由で**読む。比較対象が「MAME の内部確保領域」ではなく
「CPU から見える姿」になるので、アドレスデコーダの間違いが隠れずに差分として出る。

**画ではなく領域を比べるのが肝。** 画が違う原因は十数通りあるが、領域が違う原因は1つ。
ワークRAMとスプライトRAMが一致していて画面だけ違えば、犯人は `x1001.js` に確定する。
実際そうなった。

`thunderl` の結果: **フレーム10・60・300 で、ワークRAM・パレット・スプライトY・
スプライト制御・スプライトコードの全バイトが一致。** フレーム900では20領域中19が完全一致で、
残る1つはワークRAM の `$FFFF9F`（スタック内）の5バイト。この残差は下に書く位相差から
来るもので、機械の解釈の違いではない。2つのダンプ点は8ラインずれていて、その間に
例外フレームが積まれる。

### 画素を突き合わせる

MAME の Lua `screen:pixels()` は可視領域を生の ARGB32 で返すので、PNG デコーダを一切
使わずに画素まで比べられる:

```lua
local scr = manager.machine.screens[":screen"]
emu.register_frame_done(function() ... io.open(path,"wb"):write(scr:pixels()) ... end)
```

`thunderl` の結果。フレーム1〜3600 から21点（起動、ROMチェックのタイル羅列、タイトル画面、
デモプレイ、ハイスコア表）:

```
frame     1 …  3600     どのフレームも 92160画素中 0画素の差
21/21 frames pixel-identical
```

ROM が手元にある残り2基板も各6フレーム:

```
umanclub   6/6 frames pixel-identical   (384x240、毎回 0/92160)
krzybowl   6/6 frames pixel-identical   (304x240、毎回 0/72960)
```

3基板、割り込み方式が3通り、スプライトROMの配線が2通り、うち1つはプロテクトPAL付き。
全部一致した。

正直に書いておく注意点が2つ。

**画については MAME のフレーム番号がこの機種より1つ先**（`register_frame_done` は
最初の完了フレームを1と数え、その画はこちらの `frame` から1引いたものに対応する）。
`--pix` はその整合を既定にしてある。`--offset 0` で素のカウンタ同士の比較も見られる。

**状態と画で整合するオフセットが違う**（`--ref` は0、`--pix` は-1）。MAME は状態を
ハードウェアフレームの末尾でダンプするのに対し、その画は8ライン前（帰線開始時）に
描かれているから。この機種は両方を同じ瞬間に取る（8節）ので、2つの整合のどちらかが
その8ラインを吸収することになる。スタック以外はどちらの整合でも一致する。

### 他では絶対に捕まらなかったバグ

MAME のスプライトオフセットは `set_fg_yoffsets(flip, noflip)` — **反転側が先**。
`(noflip, flip)` と読むと、画面全体が縦に2画素、スプライトが32画素ずれる。
つまり**「それらしい画がちょっとずれた場所に出る」**。テストでは捕まらない。
画素差分は1回で捕まえたうえ、「一定の縦シフト」という形で原因の性質まで示した。

## 10. スナップショット — 実測

`snapshot()` には可変状態しか入れない。プログラムROM・スプライトROM・展開済みタイル・
サンプルROM はそのまま参照で残る。

`thunderl` を1200フレーム走らせた後の実測。typed array はバイト長、それ以外は1値8バイトで
数える（`mdtools/screenshot.mjs` とホストの巻き戻し予算と同じ算術）:

| 部位 | thunderl | krzybowl | umanclub |
|---|---|---|---|
| X1-001 チップRAM | 16.8 KB | 16.8 KB | 16.8 KB |
| X1-010 チップRAM＋バス影 | 16.2 KB | 16.2 KB | 16.2 KB |
| ワークRAM | 16.0 KB | 64.0 KB | 64.0 KB |
| パレット（現在＋表示時） | 2.0 KB | 2.0 KB | 2.0 KB |
| 68000 | 0.2 KB | 0.2 KB | 0.2 KB |
| 不揮発設定 | — | 0.3 KB | — |
| パレットページに同居するスクラッチRAM | — | — | 16.0 KB |
| **合計** | **51.3 KB** | **99.5 KB** | **115.3 KB** |

比較: ファミコン 3KB、FDS 47KB、メガドライブ 142KB、X68000 1564KB。

**巻き戻しが一番よく効く機種**になった。ホストのリングは 192MB のバイト予算なので、
1枚 51KB なら上限いっぱいの1000枚が取れる。既定の6フレーム間隔だと
**100秒ぶんのプレイを遡れる**（X68000 は12秒）。

実測してから外したものが2つある。Wit's だけがデコードする 16KB のスクラッチRAM と、
Krazy Bowl だけが持つ 256バイトの不揮発設定は、**その基板にあるときだけ確保する**。
そうしないと `thunderl` のスナップショットの1/4が「thunderl 基板に載っていない領域」になる。

音源の 8KB の上位バイト影はチップの状態ではなくバスの副産物だが、それでも入れてある。
サウンドレジスタの上位バイトにデータを置くゲームがあれば、無しでは復元がずれる。
このリポジトリのスナップショットは「完全な状態か、さもなくば無」でありたい。

推測ではなく検証済み: `thunderl` を1500フレーム（コイン投入・スタート・スティック入力込み）
走らせて250枚のスロットを取り、後ろから1枚ずつ復元した。**250/250 が捕った通りのフレームに
着地**し、中間から同じ入力で再生すると同じ画に到達する。

## 11. 無いもの

**X1-012 が無い。** 後期基板に載っている独立したタイルマップチップで、
`msgundam` / `wrofaero` / `eightfrc` / `zingzip` / `blandia` / `gundhara` / `jjsquawk` と
`seta.cpp` の大半がこれを要る。加えて6bitタイルマップカラーモードと第2パレットバンクも要る。
ROM は手元にあるが1本も読み込ませていない。読ませると「正直な拒否」ではなく
「レイヤが1枚欠けた基板」ができるから。

**第2CPUが無い。** 一部の基板（`tndrcade` / `downtown` / `calibr50`、
サンダー＆ライトニングの bootleg）はサウンドやI/O用に Z80 や 65C02 を積んでいる。
`z80.js` も `m6502.js` もこのリポジトリにあるので新しいチップではなく配線の問題だが、配線していない。

**OKI6295 が無い**ので、X1-010 の代わりにそれを使う基板は対象外。

**トラックボールは常に0を返す。** Krazy Bowl は起動してタイトルを出すがボールは動かない。
uPD4701 のカウンタは状態としてはあり、駆動するものが無い。

**`wits` は未検証。** 基板記述とROM表は `seta.cpp` から書いたが、実物の ROM が無く走らせていない。

**ウルトラマン倶楽部のパレットページ同居RAMは取りすぎている。** 実際は
`$300400-$300FFF` の 3KB なのに 16KB のバッファを与えている（Wit's の
`$E04000-$E07FFF` と同じバッファを使い回しているため）。この基板の巻き戻し1枚につき
13KB の無駄で、他の基板には影響しない。

**音は未検証。** X1-010 は MAME の `x1_010.cpp` に対して書き、テストはレジスタの意味論と
決定論を見ているが、**MAME の音声出力と突き合わせても、実際に聴いてもいない**。
6節は「正しいと思っている」であって「測った」ではない。

**ブラウザは未検証。** この文書の内容はすべて headless 走行から来ている
（フレーム統計、MAME との画素差分、PNG に落として目視）。機種は `demo/machine.html` に
組み込んであり、ホストの capability probe も受け付けるが、
**ブラウザでは何ひとつ見ていない**。CRTシミュレーションも、音の経路も、ファイル選択UIも。

**カクテル（反転）モードは未検証。** 反転用オフセットは基板の表に入っていて経路も存在するが、
DIPスイッチを立てて走らせたゲームは無い。

## 12. 基板を足すには

1. MAME の `seta.cpp` でそのゲームを探す。`ROM_START`、`_map`、`machine_config` の3つ。
2. `setarom.js` の `SETA_SETS` に1行足す。チップ・CRC・各リージョンがインターリーブか
   （`step: 2`）連結か（`step: 1`）。
3. デコーダが違うなら `machineseta.js` の `SETA_BOARDS` に1行足す。ページ表、クロック、
   可視窓、回転、割り込み方式、スプライトオフセット
   （**`set_*_offsets(flip, noflip)` — 反転側が先**）。
4. `setatools/boot.mjs` で統計を見る。そのあと 9 節の MAME 突き合わせをやるまで何も信じない。

タイルマップ層のあるゲームなら、そこで止まること。まず `x1_012.cpp` を書く必要がある。
