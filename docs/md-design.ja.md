# メガドライブ / Genesis — 設計

PC-8001 / PC-8801 / ファミコン の隣に、**機種として**セガのメガドライブを足す。ファミコンのときと同じで、狙いは「エミュをもう一本作る」ことではない。`demo/machine.html` のホストは、機種固有のものが一切入っていない `snapshot()` / `restore()` 契約の上に、決定論・早送り・巻き戻し（ジョグシャトル）を既に実装している。**契約さえ満たせば時間操作機能はタダで付いてくる** — 実際そうなった。ホスト側の変更はファイル選択と機種ボタンの追加だけで、時間操作系は一行も触っていない。

68000 コア（`m68000.js`）は先に、意図的に機種非依存で書かれている。X68000 がそのまま共有できる。この文書はそれを一切変更しない。

## 1. 契約（suite-contract 準拠）

- pure・依存ゼロのJavaScript。DOMなし・**`Math.random` 禁止**。
- 決定論：同じカートリッジ＋同じ入力列＋同じステップ数 → **ビット単位で同一の状態**。巻き戻しは「スナップショットに戻して同じ入力を流し直す」方式なので、非決定性が混じると画が少し乱れるのではなく、**時間操作機能が全部壊れる**。
- 出力は plain data ＋ `schemaVersion`。
- 依存は一方向。`m68000.js` と `z80.js` はメガドライブを知らない。`mdvdp.js` に CPU は無い。`ym2612.js` と `sn76489.js` にバスは無い。ループを閉じる coordinator が `machinemd.js`。
- テストは `node --test`、headless、決定論テストを含む。

## 3. クロック

すべてが1本のマスタークロックから分周される。NTSC は 53.693175 MHz、PAL は 53.203424 MHz。

| 部品 | 分周 | NTSCでの周波数 |
|---|---|---|
| 68000 | mclk / 7 | 7.670453 MHz |
| Z80・PSG | mclk / 15 | 3.579545 MHz |
| YM2612 | mclk / 7、内部でさらに /144 | FMレート 53.267 kHz |

1ラインは画面モードによらず**ちょうど 3420 マスタークロック**。H40 は mclk/8 のドットクロックで320ドット、H32 は mclk/10 で256ドット、どちらも表示期間 2560 mclk ＋ ブランキング 860 mclk になる。NTSC は262ライン、PAL は313ラインなので、フレームレートは 59.9227 Hz と 49.7015 Hz。

YM2612 の1tick は 7 × 144 = **ちょうど 1008 マスタークロック**。だからスケジューラは整数だけで回り、どこにも誤差が溜まらない。

`stepFrame()` はラインを回す。各ラインで `vdp.beginLine()`（Hカウンタの再ロード、表示終了ラインでV割込）を呼び、2560 mclk ぶんCPUを走らせ、そのラインを描き、残り860 mclkを走らせる。その中では 1008 mclk のスライス単位で進め、68000 と Z80 に分配し、間で DMA エンジンと FM タイマを進める。

## 4. ラインをいつ描くか

**そのラインの水平ブランキングが始まった瞬間**。

メガドライブの面白い表現は全部フレーム途中のレジスタ書き込みでできている。ソニックの水面はH割込ハンドラでのCRAM書き換えだし、ステータスバーはウィンドウ面＋スクロール変更、多重スクロールは水平スクロールテーブルの1ライン1エントリ。フレームに1回レジスタを読むレンダラはそのどれも描けない。Hブランク開始時に描けば、そのラインのレジスタ状態は確定しているし、ライン N-1 のHブランク中に書いた値（H割込はまさにそのためにある）は**ライン N 向け**として正しく効く。

ラインは**その場で RGB に変換する**。パレットインデックスで溜めない。CRAM 自身がフレーム途中で変わるものの筆頭なので、色引きをフレーム末尾に遅らせると、このレンダラが存在する理由そのものを潰してしまう。DACのランプ（通常/シャドウ/ハイライト）は実測値の3本で、掛け算ではない。

優先順位はピクセルごとに1本の順序で解決する:

```
sprite(pri=1) > A(pri=1) > B(pri=1) > sprite(pri=0) > A(pri=0) > B(pri=0) > 背景色
```

ウィンドウは7枚目のレイヤではない。効いている場所ではスクロール面Aを**置き換える**（自前のスクロールは持たない）。

## 5. DMA は memcpy ではなくステートマシン

議論の余地がある唯一の設計判断なので、理由を書いておく。

VDP は画面モードが決めるレートでバススロットを盗む。ブランキング中はおよそ20マスタークロックに1ワード、表示中はレンダラがスロットを使っているのでその1/10程度。だから全画面のタイル転送は垂直帰線のほとんどを食うし、表示ONで始めた長いDMAは何ラインにもまたがる。

このタイミングは些細な話ではない。**ダイレクトカラーDMA** — 61色をはるかに超える色数を出すあの技 — は、CRAM への巨大なDMAをフレーム全体にわたって走らせ、ビームが走査する間に各ラインが別のパレットを見る、というものだ。トリガー時に一気に転送するエミュレータでは真っ黒になる。全部の色が1ライン目より前に届いてしまうから。実際この実装の初版がそうで、Nemesis の `Direct-Color-DMA.bin` は真っ黒だった。転送を「機械がマスタークロック単位で進めるステートマシン」に変え、その合間に画を描くようにしたら直った（37色・52.7%）。

したがって `_startDma()` は `vdp.dma` を組み立てるだけ、`runDma(mclk)` が経過したバススロットぶんだけ進め、`dmaHoldsBus` が「このスライスで68000を走らせてよいか」を機械に伝える。VRAMコピーは68000のバスを取らない（VDP内部で完結する）。68000→VDP転送とVRAMフィルは取る。

## 6. CPU 2個

機械を所有しているのは68000。Z80 は自分の 8KB RAM と FM音源・PSG を持ち、加えて 68000 のアドレス空間への 32KB の窓を持つ。窓の位置は `$6000` の**シフトレジスタ**が決める — 1bitずつ9回、LSBから。（バンク番号をバイトで書くドライバはデタラメな場所を見る。だからどのドライバもループになっている。）

68000 は `$A11100` で Z80 のバスを要求し、`$A11200` で Z80 をリセットに落とす。電源投入時は Z80 はリセット保持・バスは68000が所有。走り始めた Z80 は自分のRAMに残っていた何かを実行してしまうから。

68000 の**ワード**書き込みを Z80 空間に対して行うと、8bitバスに出るのは**上位バイトだけ**。ワード読み出しでは同じバイトが2回見える。ここを間違えるとサウンドドライバが1バイトおきに転送される。

2つのCPUは命令単位ではなく 1008 マスタークロックのスライスで交互に走る。Z80 の FM 書き込みは実機に対して 1/3 ライン程度の誤差に収まる — どの音楽ドライバの分解能よりずっと細かく、真のロックステップよりずっと安い。

## 7. 割込

VDP は 68000 に2つのレベルを出す。**6** が垂直割込（レジスタ1 bit5 で許可）、**4** が水平割込（レジスタ0 bit4）。Hカウンタはフレーム先頭でレジスタ10からロードされ、表示期間中カウントダウンし、ブランキング中はリロードされたまま保持される。レジスタ10が *n* なら、割込はライン *n* に来て、以後 *n*+1 ラインごと。

どちらも**レベルトリガ**。`vdp.irqLevel()` がピンの状態を答え、pending は `irqAck()` で落ちる（`m68000.js` がオートベクタを取るときに呼ぶ）。これが唯一正しい形で、assert時に落とすとマスク中の割込が消えるし、落とさないと永久に再入する。

垂直割込は Z80 にも 1ライン幅の INT パルスとして届く。割込禁止中のドライバは取りこぼすので、1回だけ撃つのではなくそのライン中は再試行する。

## 8. スナップショット — 実測

`snapshot()` には可変状態しか入れない。カートリッジ（512KB〜4MB）はそのまま参照で残り、VDP のフレームバッファは状態ではなく出力。

| 中身 | バイト |
|---|---|
| 68000 ワークRAM | 65,536 |
| VDP VRAM | 65,536 |
| Z80 RAM | 8,192 |
| CRAM＋VSRAM＋VDPレジスタ＋制御状態 | 約1,000 |
| YM2612（両バンクのレジスタ＋6×4オペレータの状態を1本の `Float64Array` に） | 約4,000 |
| 68000/Z80 レジスタ、PSG、コントローラ、スケジューラ | 約1,000 |
| **合計（実測）** | **141.9 KB** |
| …バックアップRAMに書き込みがあった場合 | **173.9 KB** |

（`node mdtools/screenshot.mjs <rom> --snapsize` で計測。typed array はバイト長で数える。`JSON.stringify` は測り方として誤り — `Uint8Array` はキー65,536個のオブジェクトになる。）

バックアップRAMは**何か書かれてから初めて**コピーする。32KBのセーブチップを宣言していて遊んでいる間まったく触らないカートリッジは山ほどあり、1枚あたり32KBのゼロは巻き戻しリングの1/5を無駄にする。`sramDirty` は単調（falseに戻らない）なので、コピーの無いスナップショットは「この時点でセーブチップはまだ空だった」を曖昧さなく意味する。

`demo/machine.html` のリングに対して何が買えるか:

| 巻き戻しバッファ設定 | 間隔 | 枚数 | メモリ |
|---|---|---|---|
| 45秒（既定） | 6フレーム | 450 | 62 MB |
| 2分 | 8フレーム | 900 | 125 MB |
| 10分（最大） | 36フレーム | 1000 | 139 MB |

ホストは枚数が1000を超えないよう間隔を自動で粗くするので、メガドライブは最大の10分でも約139MBに収まる。PC-8801（1枚約130KB）と同オーダー、ファミコンのNROM（約3KB）の40倍強。YM2612 のチャンネル/オペレータ状態を「6個のオブジェクトが4個のオブジェクトを持ち各15フィールド」ではなく1本の平坦な `Float64Array` に詰めたのは、前者だと履歴1秒あたり3万個の短命オブジェクトが生まれ、スクラブ中のカクつきとして出るから。

### 9.5 決定論

`test-md.mjs` は55件。効いているのは:

- 同じROMから作った2台を25フレーム進めると、スナップショットが**deep-equal**；
- `snapshot()` → 12フレーム → `restore()` → 12フレーム で同一状態に戻る；
- 20フレームぶんの垂直割込をまたいだリプレイで、フレームごとの割込回数が一致；
- `restore()` が CPU に割込**レベル**を再表明する（レベルは機械が駆動するものであってCPUが覚えているものではない）；
- スナップショットにカートリッジが入っておらず、同じカートリッジを持つ別の機械に restore すれば足りる。

## 10. 既知の穴

以下はすべて「分かっていて省いた」ものであって、未知ではない。

1. **VDP の書き込みFIFOが無い。** ステータスは常に空FIFOを報告し、満杯による68000のストールも起きない。`VDPFIFOTesting.bin` は動いて画も出るが、その**判定内容は未確認**。
2. **CRAM はラインに1回しかサンプルしない。** ライン途中のCRAM書き込みは次のラインから効く。上の `cram flicker.bin` 参照。
3. **インタレース無し。** レジスタ12のLSMビットは保持するだけで無視。
4. **3ボタンパッドのみ。** 6ボタンパッド・マルチタップ・光線銃は無い（HVカウンタのラッチは実装したが、トリガするものが無い）。
5. **カートリッジマッパー無し。** 4MBまでの素のROM＋`$A130F1` のセガ製バックアップRAM制御のみ。SSF・SSF2・各種の海賊版マッパーは無い。
6. **メガCD無し、32X無し。**
7. **Z80と68000は 1008 マスタークロック単位の交互実行**で、命令単位ではない。Z80が書いたフラグを1命令精度でビジーウェイトするゲームなら気付くはずだが、そういうものは知られていない。
8. **YM2612 の LFO は近似。** レートは資料どおり、深さも近いが、実チップのPM はF-numberの上位ビットで引く区分表であって比例した揺れではない。DACのラダー歪み（「メガドラの音」の一部）はモデル化していない。
9. **Hカウンタは機械のライン内位置から導出**していて、粒度は 1008 マスタークロック（約1/5ライン）。ブランキングの端を探すポーリングは動くが、特定のドットを要求するものは動かない。
10. **見た目は未検証。** 上のすべては headless 実行のフレームバッファ統計。ブラウザで**実際に正しく見えるか**は確認しておらず、それは headless テストに言えることの外にある。

## 11. ホスト統合

`demo/machine.html` に要ったのは、ファイル選択・機種ボタン・キーマップ・boot分岐だけ。それ以外は何も要らなかった — 早送り・巻き戻し・ジョグシャトルは無変更で動いた。契約が仕事をしたということ。

ついでに `instanceof` 相当の判定を2箇所、ファミコン担当と同じ流儀で一般化した:

- `renderAudioInto()` が `machine.opn`（PC-8801のフィールド）を見ていたのを、`typeof machine.renderAudio === 'function'` に。音を出せる機種なら何でも出せる。
- canvas クリックが autoplay 解除の前に `bootMode === 'n88'` を見ていたのも同じ capability probe に。

キーボード：方向キーが十字、`Z`/`X`/`C`（または `A`/`S`/`D`）が A/B/C、Enter か Space が START。ゲームパッドの8801ジョイスティックビットは2度マッピングせず**変換**しているので、既存のパッド設定パネルはそのまま効く。

## 12. X68000 担当への申し送り

68000 コアは快適で、変更は一切要らなかった。具体的には:

- **必須のバスメソッドが `read16`/`write16` だけなのは本当**だが、マップにレジスタが1つでもあるなら **`read8`/`write8` も渡したほうがよい**。合成されるバイトアクセサは対象ワードのread-modify-writeをするので、「読むと消える」ステータスレジスタがあると刺さる。（メガドライブのVDPステータスもコントローラのラッチも、どちらも刺さるところだった。）
- `irqAck(level)` がオートベクタで `-1` を返す形は、レベルトリガの割込源にとってちょうど良い。pending はそこで、そこだけで落とす。
- `new M68000(bus)` はコンストラクタでリセットするので、その時点でバスがベクタ0と1に答えられる必要がある。ROMを後からマップするなら `cpu.reset()` を呼び直す（`machinemd.js` は自分の `reset()` からそうしている）。
- `{ tasWriteBack: false }` はメガドライブ固有。X68000 は既定のままでよい。
- `cpu.step()` はクロック数を返すので、マスタークロックへの変換は掛け算1回。CPUサイクルではなくマスタークロックで予算を持ったことが、7:15の2つのCPUを1本の整数スケジュールに乗せられた理由。
- 唯一つまずいたのはコアの話ではなく、**時間予算でCPUを回す機械は、CPUがバスを失った瞬間に止まらなければならない**という点。`_run68k()` は `vdp.dmaHoldsBus` が立った瞬間に return する。そうしないと命令の途中で始まったDMAがそのスライスの残りの間まるごと無視される。
