# ファミコン / NES — 設計（第1段：カートリッジ＋CPU）

PC-8001 / PC-8801 の隣に、**機種として**ファミコン(NES)を足す。狙いは「エミュをもう一本作る」ことではない。`demo/machine.html` のホストは、機種固有のものが一切入っていない `snapshot()` / `restore()` 契約の上に、決定論・早送り・巻き戻し（ジョグシャトル）を既に実装している。つまり **契約さえ満たせば時間操作機能はタダで付いてくる**。

この文書は **第1段だけ** を扱う：カートリッジ形式（`ines.js`）と CPU（`m6502.js`）、そしてそのテスト。PPU・APU・マッパー・機種クラスは **次段**（[7. まだ無いもの](#7-まだ無いもの)）。

## 1. 契約（suite-contract 準拠）

- pure・依存ゼロのJavaScript。DOMなし・`three`なし・**`Math.random` 禁止**。
- 決定論：同じカートリッジ＋同じ入力列＋同じステップ数 → **ビット単位で同一の状態**。これは「あると良い」話ではない。巻き戻しは「スナップショットに戻して同じ入力を流し直す」方式なので、非決定性が混じると画が少し乱れるのではなく、**時間操作機能が全部壊れる**。
- 出力は plain data + `schemaVersion`。
- 依存は一方向。`m6502.js` は NES を知らない（バスを受け取って実行するだけ）、`ines.js` は CPU を知らない。ループを閉じるコーディネータが機種クラス（次段）。
- テストは `node --test`、headless、**決定論テストを含む**。

## 3. `ines.js` — カートリッジ

`.nes` はメモリイメージではなく **基板の記述**。本体側にはほとんど何も無い（ワークRAM 2KB、VRAM 2KB）。プログラムROMもキャラクタROMもネームテーブルの配線もバンク切替回路も、カートリッジが持ち込む。だからヘッダが答えているのは「これは何の基板か」で、その解析結果が次段のマッパーの入力になる。

この形式には20年分の粗悪なツールが埋めた地雷がある。無いことにせず、明示的に扱う：

- **汚いヘッダ（dirty header）**。90年代のリッパーがバイト12..15に自分のハンドルを書いた。そういうファイルでバイト7のマッパー上位ニブルを信じると「マッパー $40」のような出鱈目になる。末尾に印字可能ASCIIが入っているのが目印で、見つけたら上位ビットを捨てて警告に残す。
- **NES 2.0 の指数サイズ**。サイズニブルが `$F` のときは下位バイトが「2^E × (2·MM+1) バイト」に化ける。8bitフィールドに巨大な同人ROMを収める逃げ道。
- **途中で切れたファイル**。ダウンロード失敗でよくある。**宣言されたサイズ**を保ち（マッパーが配線するのはそのサイズ）、欠けた尻尾をゼロ埋めして警告する。黙って短いPRGを返すと、それはゴミコードとして実行される。

### エラー方針

`parseINes(bytes)` は `INesError` を投げる。**コード**（`too-short` / `bad-magic` / `no-prg` / `truncated-trainer`）と、人が読める文言を持つ。ただしファイル選択ダイアログにゴミが来るのは日常なので、**ホストが呼ぶ入口は `tryParseINes(bytes)`** ＝ 投げずに `{ ok: false, code, error }` を返す。生き延びられる損傷は決して投げず、`cart.warnings` に入れる（ホストが「なぜこのゲームが変なのか」を言えるように）。

`summarizeINes(cart)` は表示用の plain data（typed array を含まない）を返す。`boardName(mapper)` 付きで、未知のマッパーは推測せず `mapper 999` と正直に名乗る。

**解析済みカートリッジは不変（immutable）**。機種は参照で持ち、スナップショットには決してコピーしない（§5）。

## 4. `m6502.js` — CPU

`z80.js` の相棒。形は同じ（バスを注入、`step()` を呼ぶ、サイクル数が返る、レジスタをスナップショット）。違いは、NESでは **タイミングが意味を持つ** こと。映像チップがCPUクロックのちょうど3倍で走り、ゲームはスキャンラインの途中でスクロールレジスタを書き換える。だから1サイクルのズレは丸め誤差ではなく、目に見える乱れになる。

### サイクル表を持たない — サイクルはバスアクセスから落ちてくる

このコアには **命令ごとのサイクル表が無い**。実機と同じく **バスアクセス1回＝1サイクル**とし、内部サイクルは実機がそれを使う場所で使う：

- **インデックス付き読み出し**（`abs,X` / `abs,Y` / `(zp),Y`）は、インデックスがページを跨いだとき **まず間違ったアドレスを読み**、その後で正しいアドレスを読み直す。これが有名な「ページ跨ぎで +1」で、その空読みは実在の挙動だ：`abs,X` 経由で `$2007` を読むと PPU アドレスが2回進んでしまうのも、MMC3 のスキャンラインカウンタがプログラマの意図しない読み出しで刻まれてしまうのも、これが理由。
- **リードモディファイライト**は、新しい値の前に **古い値を書き戻す**。ゲームはこの二重書き込みを意図して使う（マッパーやAPUのレジスタに対する RMW は、2サイクルで2回叩く）。
- **インデックス付き書き込み**は、ページを跨ごうが跨ぐまいが常に空読みの1サイクルを払う。
- **分岐**は 2 / 3 / 4 サイクル（不成立 / 成立 / 成立かつページ跨ぎ）。

アクセスの並びさえ正しければ、サイクル数は自動的に正しくなる。これが nestest をサイクル単位で一致させている理由であり、次段で PPU を「レジスタアクセスの時点で追いつかせる」やり方が成立する理由でもある。

### 割込

- **NMI はエッジトリガ**。PPU は vblank 開始でラインを Low に引いて保持するので、レベルで見るとハンドラが `$2002` を読むまで毎命令 NMI が発火してしまう。ラインをモデル化するなら `setNmi(level)`、1発だけ撃つなら `nmi()`。
- **IRQ はレベルトリガ**で、複数のソース（APUフレームカウンタ、DMC、マッパー）がワイヤードOR。`setIrqSource(bit, level)` でソースを独立に持つので、片方が下ろしても他方の要求は消えない。
- **`SEI` / `CLI` / `PLP` が書いた I フラグは1命令遅れて効く**。割込ロジックがフラグ更新の1サイクル前にサンプルするため。`CLI; <1命令>; <IRQ>` は実際のゲームコードにある書き方。`RTI` だけは例外で、P を十分早く取り出すので即座に効く。
- **`B` フラグは実在のフリップフロップではない**。スタックに積まれるバイトの中にだけ存在し、ハンドラが `BRK` と IRQ を区別する手段になっている。`p` の中では常にクリア、push のときに OR する。
- 割込のポーリングは **命令境界**。命令の途中で起きる "interrupt hijacking" 系は未対応（§7）。

### 未定義命令

256パターン全部をデコードする（default に落ちるものは無い）。メーカーは速度のために未定義命令を使った（`LAX` は「LDA+LDX を1命令で」）ので、未定義を綺麗にトラップするコアは実カートで落ちる。

- **安定・正確**：`LAX` `SAX` `DCP` `ISC` `SLO` `RLA` `SRE` `RRA` `ANC` `ALR/ASR` `ARR` `SBX/AXS`、未定義 `SBC`（`$EB`）、複数バイト `NOP`（アセンブラがパディングとして吐いたので、正しいサイクル数を消費する必要がある）。
- **近似**：不安定な命令。`ANE/XAA`（`$8B`）と `LXA`（`$AB`）は、チップ個体・温度・直前にバスに乗っていた値で変わる「マジック定数」をANDする。多くのエミュが落ち着いている `$EE` を使う。`&(H+1)` 系ストア（`SHA`/`SHX`/`SHY`/`TAS`）は「値 AND （ベースアドレス上位バイト+1）」を書き、ページ跨ぎではアドレス上位バイト自体がその値に化ける。どちらも依存している市販ゲームは知られていない。
- **`JAM`/`KIL`** は RESET まで停止。例外ではなく `cpu.jammed = true` としてモデル化する（暴走したゲームは、デバッガで観察したい正当な状態だから）。

デシマルモードは実装しているが **既定でオフ**。2A03 は BCD 加算器がシリコンレベルで殺されている。`new M6502(bus, { decimal: true })` で素の NMOS 6502 になる（フラグは 65C02 ではなく NMOS 準拠）。

### バス

`z80.js` と同じく注入：`{ read(addr), write(addr, val) }`。`in`/`out` は無い（6502 に独立したI/O空間は無い）。1アクセス＝1サイクルなので、バス側には空読みも RMW の二重書き込みも見える。次段のマッパーと PPU が必要とするのは、まさにそれ。

## 5. スナップショット方針（＝巻き戻しの実体）

`demo/machine.html` はスナップショットを最大1000個リングバッファに持ち、約150MBに収まるよう間隔を自動調整する。**1個が大きいと巻き戻せる時間が短くなる**。だから：

- **不変データはスナップショットに入れない。** PRG-ROM / CHR-ROM は読み込み済みカートリッジから参照で持ち、復元も参照のまま。（`machine88.js` がマウント済みD88に対して取っているのと同じ方針で、隠さず明記するところまで同じ。）
- CPU の状態はレジスタだけ ── `a, x, y, s, p, pc, cycles` ＋割込ライン。数十バイト。
- `getState()` / `setState()` は厳密な逆操作。`snapshot()` / `restore()` は別名（機種クラスと同じ読み味にするため）。
- 全部 plain data（数値・真偽値・typed array）。クラス再構築をしないので `snap.js` の `snapObj` / `restoreObj` がそのまま効き、`restore()` は既存オブジェクトに書き込む。

次段がフレームごとに詰めるべきもの：ワークRAM 2KB、VRAM 2KB、OAM 256B、パレット32B、PPU/APU のレジスタと内部ラッチ、マッパー状態、CHR-RAM があればそれ ── 圧縮前でおよそ5KB。これが「1000フレーム分持てる」予算。

## 6. テスト

### 単体テスト

`node --test`。`test-6502.mjs` はフラグ・アドレッシングモード・**サイクル数**を個別に固定する（nestest が落ちたとき、落ちどころがあるように）。`test-ines.mjs` は損傷に集中する：汚いヘッダ、途中切れ、ゴミ入力。

### 決定論テスト（必須）

3つの性質をそれぞれ直接テストする：

1. 同じプログラムを2回流す → フィンガープリント（レジスタ＋RAMのハッシュ）が一致。
2. snapshot → 先へ進める → restore → 同じ手順を流し直す → 一致。
3. 同上で、**再生の途中で割込が入る**版 ── 巻き戻し中の「スナップショットの後から入力が来る」がまさにこれなので、これが最悪ケース。

テスト用プログラムは手で種を決めた小さなLCGで生成する。`Math.random` は使わない。

### nestest — 1命令単位の突き合わせ

これが受け入れテスト。nestest.nes は `$C000` から入ると PPU 無しで走り、公式命令も文書化された未定義命令も全部を叩く。そして実機で走らせたサイクル正確な参照ログが公開されている。`PC/A/X/Y/P/SP/CYC` を1行ずつ突き合わせれば、演算だけでなくタイミングまで詰められる。

これはこのリポジトリが M88 に対して既にやっている手法と同じ（`docs/m88-comparison.ja.md`）：参照実装と自分を同じプログラムで走らせてトレースを diff し、**ズレた瞬間の命令**として報告させる。

**ROMとログはリポジトリに入れない**（テストROMをコミットしない）。`nes-test-roms` コレクションから取る：

```sh
curl -L -o /tmp/nestest.nes https://raw.githubusercontent.com/christopherpow/nes-test-roms/master/other/nestest.nes
curl -L -o /tmp/nestest.log https://raw.githubusercontent.com/christopherpow/nes-test-roms/master/other/nestest.log
```

引数でも環境変数でも渡せる：

```sh
node nestools/nestest.mjs /tmp/nestest.nes /tmp/nestest.log
NESTEST_ROM=/tmp/nestest.nes NESTEST_LOG=/tmp/nestest.log node --test test-6502.mjs
```

環境変数が無ければ `node --test` は nestest のケースを skip するので、ROM 無しでもスイートは通る。

**現状の結果：8991行すべて一致（PC/A/X/Y/P/SP と CYC）、nestest 自身の判定バイト `$02`/`$03` は `00 00` ── 公式命令も未定義命令も全サブテスト合格。**

## 7. まだ無いもの

次段以降（issue の順序どおり）：

- `nesppu.js` — 背景・スプライト・スクロール・スプライト0ヒット。CPU 側の準備はできている：サイクル数が正確で、バスに全アクセスが見えるので、PPU はレジスタアクセスの粒度で追いつかせられる。
- `nesmapper.js` — 最低 NROM(0) / MMC1(1) / UxROM(2) / CNROM(3) / MMC3(4)。MMC3 のスキャンラインIRQ は PPU アドレスバスの挙動 **と** このコアが既に行っている空読みの両方に依存する。
- `nesapu.js` — 矩形×2・三角・ノイズ・DMC。DMC は CPU サイクルを盗むが、現状の `step()` はそれをモデル化していない。
- `machinenes.js` — `stepFrame()` / `frame` / `snapshot()` / `restore()` / `schemaVersion` を満たす機種クラス。
- `demo/machine.html` へのホスト統合。残っている機種決め打ちの一般化も含む。

第1段の中に残っている既知の穴（隠さず列挙する）：

- 割込のポーリングは命令境界であって命令の途中ではない。delayed-NMI や "interrupt hijacking"（`BRK` の処理中に NMI が来る）は再現しない。これを捕まえるテストは blargg の `cpu_interrupts_v2` で、PPU が載って走らせられるようになる次段の仕事。
- 不安定な未定義命令は近似（§4）。
- オープンバス読み出しはバスが返した値をそのまま返す。減衰するオープンバスのラッチはモデル化していない。これは CPU ではなく機種側のバスの仕事。
