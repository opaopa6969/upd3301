# ファミコン / NES — 設計

PC-8001 / PC-8801 の隣に、**機種として**ファミコン(NES)を足す。狙いは「エミュをもう一本作る」ことではない。`demo/machine.html` のホストは、機種固有のものが一切入っていない `snapshot()` / `restore()` 契約の上に、決定論・早送り・巻き戻し（ジョグシャトル）を既に実装している。つまり **契約さえ満たせば時間操作機能はタダで付いてくる**。

段階を分けて作っている。**第1段**はカートリッジ（`ines.js`）と CPU（`m6502.js`）。**第2段**は PPU（`nesppu.js`）・マッパー基板（`nesmapper.js`）・機種クラス（`machinenes.js`）・ホスト統合。**第3段**は APU（`nesapu.js`）、CPU の命令途中の割込挙動、そして20枚の追加基板。**第4段** — この文書の現状 — は**ファミコンディスクシステム**（`fds.js`）と、それが可能にした192本一斉スイープ：[§12](#12-fdsjs--ファミコンディスクシステム) 参照。まだ足りないものは [§11](#11-まだ無いもの) に列挙してある。

## 1. 契約（suite-contract 準拠）

- pure・依存ゼロのJavaScript。DOMなし・`three`なし・**`Math.random` 禁止**。
- 決定論：同じカートリッジ＋同じ入力列＋同じステップ数 → **ビット単位で同一の状態**。これは「あると良い」話ではない。巻き戻しは「スナップショットに戻して同じ入力を流し直す」方式なので、非決定性が混じると画が少し乱れるのではなく、**時間操作機能が全部壊れる**。
- 出力は plain data + `schemaVersion`。
- 依存は一方向。`m6502.js` は NES を知らない（バスを受け取って実行するだけ）、`nesppu.js` は CPU を知らない、`nesmapper.js` はどちらも知らない。ループを閉じるコーディネータが `machinenes.js`。
- テストは `node --test`、headless、**決定論テストを含む**。

## 3. `ines.js` — カートリッジ

`.nes` はメモリイメージではなく **基板の記述**。本体側にはほとんど何も無い（ワークRAM 2KB、VRAM 2KB）。プログラムROMもキャラクタROMもネームテーブルの配線もバンク切替回路も、カートリッジが持ち込む。だからヘッダが答えているのは「これは何の基板か」で、その解析結果がマッパーの入力になる。

この形式には20年分の粗悪なツールが埋めた地雷がある。無いことにせず、明示的に扱う：

- **汚いヘッダ。** 90年代のリッパーがバイト12..15に自分のハンドルを書いた。それを信じてバイト7のマッパー上位ニブルを読むと「マッパー $40」のような出鱈目になる。末尾に印字可能ASCIIが入っているのが目印で、見つけたら上位マッパービットを捨てて warning を残す。
- **NES 2.0 の指数サイズ。** サイズニブルが `$F` だと下位バイトの意味が「2^E × (2·MM+1) バイト」に切り替わる。8bitのフィールドに巨大な同人ROMを収めるための仕掛け。
- **途中で切れたファイル。** ダウンロード失敗でよくある。**宣言されたサイズ**を保ち（マッパーが配線するのはそちら）、足りない尾をゼロ埋めして warning を出す。黙って短いPRGを返すと、それはゴミコードとして実行される。

### エラー方針

`parseINes(bytes)` は **コード付き**の `INesError` を投げる（`too-short` / `bad-magic` / `no-prg` / `truncated-trainer`）。ただしファイル選択にゴミが来るのは日常なので、ホストが呼ぶ入口 `tryParseINes(bytes)` は投げずに `{ ok:false, code, error }` を返す。生き延びられる損傷は例外にせず `cart.warnings` に入るので、ホストは「なぜこのゲームが変なのか」を表示できる。

`nesmapper.js` も一段上で同じ規則に従う。未実装の基板には `tryCreateMapper(cart)` が `{ ok:false, code:'unsupported-mapper', mapper, error }` を返す。ROMライブラリは未実装基板だらけなので、投げるよりも基板名を言えるほうが良い。

**解析済みカートリッジは不変。** 機種は参照で持ち、スナップショットには決してコピーしない（§9）。

## 4. `m6502.js` — CPU

`z80.js` の相棒。形は同じ（バスを注入し、`step()` を呼び、サイクル数を受け取り、レジスタファイルをスナップショットする）。違いは、NESでは **タイミングが意味を持つ** こと。映像チップはCPUクロックのちょうど3倍で走り、ゲームはスキャンラインの途中でスクロールレジスタを書き換える。1サイクルの誤差は丸め誤差ではなく、見えるグリッチになる。

### サイクル表を持たない — サイクルはバスアクセスから出てくる

このコアには **命令ごとのサイクル表が無い**。実チップと同じく、バスアクセス1回＝1サイクルで、内部サイクルもチップが使う場所で使う：

- **インデックス付きリード**（`abs,X` / `abs,Y` / `(zp),Y`）は、インデックスがページを跨ぐとき**まず間違ったアドレスを読み**、次に正しいアドレスを読む。有名な「ページ跨ぎで+1」の正体で、この空読みは実機の挙動そのもの。`abs,X` 経由で `$2007` を読むと PPU アドレスが2回進むのも、MMC3 のスキャンラインカウンタがプログラマの意図しないリードでクロックされるのも、これが理由。
- **リード・モディファイ・ライト**命令は、新しい値の前に**古い値を書き戻す**。ゲームはこの二重書き込みを意図して使う（マッパーやAPUのレジスタに RMW を撃つと、2サイクルで2回叩ける）。
- **インデックス付きライト**はページ跨ぎの有無に関わらず常に空読みを払う。
- **分岐**は 2 / 3 / 4（不成立 / 成立 / ページ跨ぎ成立）。

アクセスパターンさえ合っていればサイクル数は自動的に合う。nestest がサイクル単位で一致するのはこれのおかげで、**第2段の CPU↔PPU 同期がコード1行で済むのもこれのおかげ**（§7）。

### 割込

- **NMI はエッジトリガ。** PPU は VBlank の頭で線を下げて保持するので、レベルで判定するとハンドラが `$2002` を読むまで毎命令 NMI が飛ぶ。線をモデル化する側は `setNmi(level)`、単発で撃ちたい側は `nmi()`。
- **IRQ はレベルトリガ**で、複数ソース（APUフレームカウンタ、DMC、マッパー）がワイヤードORされる。`setIrqSource(bit, level)` でソースを独立に持ち、片方の解除で他方の要求が消えないようにしている。
- **`SEI` / `CLI` / `PLP` が書く I フラグは1命令遅れて効く。** 割込ロジックがフラグ更新の1サイクル前にサンプルするため。`CLI; <1命令>; <IRQ>` は実際のゲームコードに出るパターン。`RTI` だけは例外で、P を早く引き上げるので即座に効く。
- `B` フラグは実在のフリップフロップではない。スタックに積まれるバイトの中にだけ存在し、ハンドラが `BRK` と IRQ を見分けるためのもの。`p` の中では常にクリアで、push するときに OR する。
- **割込を「取るかどうか」は命令境界で決めるが、線そのものは毎サイクル見ている。** 実チップは毎サイクル IRQ/NMI をサンプルしていて、その帰結のうち3つは直接測定できる。だからこのコアは、アドレッシングモード全部にポーリング点を通す代わりに、1サイクル分の履歴を持つ（バスアクセスのたびに呼ばれる `_endCycle()`）：

  - **ベクタの乗っ取り（hijacking）。** `BRK`・`IRQ`・`NMI` は**同じ**7サイクルのシーケンスを走る。違うのは末尾のベクタ読み2回だけで、チップはそれを読む直前までベクタを決めない。だから `BRK` や IRQ がすでに状態を積んでいる最中に NMI が来ると、スタックは `BRK` の形なのに飛び先は NMI ハンドラになる。判定はステータスの push の後 ＝ 5サイクルの窓で、1サイクルずらすと blargg の `2-nmi_and_brk` が乗っ取り回数を5回ではなく4回か6回と数える。
  - **ページを跨がない成立分岐は、最後のクロックの間の IRQ を無視する。** ポーリングは最後から2番目のサイクルなので、最終サイクルの中で立った IRQ は1命令まるごと後ろにずれる。ページ跨ぎは1サイクル増える＝もう一度ポーリングが入るので、この癖はページ内に収まる分岐に限られる（`5-branch_delays_irq`）。
  - **DMA による停止は割込ロジックから見えない。** DMAコントローラが RDY を下げている間 — OAM DMA の513サイクル、DMC のサンプル取得の4サイクル — CPU は実行もポーリングもしないので、その中で立った線は停止を終えた境界では見えない。機種は `cpu.stallForDma()` で停止を宣言する。これが無いとスプライトDMA中に上がった IRQ を1命令早く取ってしまう（`4-irq_and_dma`）。
  - **割込シーケンス自身は割込をポーリングしない**ので、次の割込が取られる前にハンドラの命令が必ず1つは走る。

  ここまで入れて blargg の `cpu_interrupts_v2` は 5/5。

### 未定義命令

256パターン全部をデコードする（default に落ちるものは無い）。パブリッシャは速度のために未定義命令を使った（`LAX` は「LDA+LDX を1命令で」）ので、未定義命令をトラップするコアは実カートリッジで落ちる。

- **安定・正確**：`LAX` `SAX` `DCP` `ISC` `SLO` `RLA` `SRE` `RRA` `ANC` `ALR/ASR` `ARR` `SBX/AXS`、未定義 `SBC`（`$EB`）、複数バイト `NOP`（アセンブラがパディングとして吐いたので、正しいサイクル数を消費しないと困る）。
- **近似**：不安定系。`ANE/XAA`（`$8B`）と `LXA`（`$AB`）は「マジック定数」を AND するが、その値はチップ個体・温度・直前にバスに載っていた値で変わる。多くのエミュが落ち着いた `$EE` を使う。`&(H+1)` 系ストア（`SHA`/`SHX`/`SHY`/`TAS`）は `値 & (ベースアドレス上位バイト + 1)` を書く。これらに依存する市販ゲームは知られていない。（blargg の `instr_test-v5` も同意見で、16本中15本が通り、唯一の失敗がまさに `$AB`。）
- **`JAM`/`KIL`** は RESET までチップを止める。例外ではなく `cpu.jammed = true` としてモデル化した（クラッシュしたゲームはデバッガで観察する価値のある状態だから）。jam 中も機種側が PPU を手で回すので、クラッシュしたROMがホストを `stepFrame()` の中でハングさせることはない。

デシマルモードは実装済みだが **既定オフ**。2A03 は BCD 加算器がシリコンレベルで殺されているため。`new M6502(bus, { decimal: true })` で素の NMOS 6502 になる。

## 5. `nesppu.js` — PPU

PPU は **フレームバッファではない**。341ドット × 262スキャンライン、CPUクロック1に対して3ドット、という固定のラスタを歩きながら、ビームのすぐ先のタイルを取ってくる機械だ。この機種で「テクニック」に見えるものは全部、ゲームが**ビームの位置**を利用しているだけ：画面分割のステータスバー、多重スクロール、フレーム途中のパレット変更。だからこのコアは**ドット単位で** tick し、機種側が CPU のバスアクセスの中から tick する（§7）。すると、レジスタ書き込みは追いつき処理なしで本物のドット位置に落ちる。

### スクロールは X と Y ではなく、2本のアドレスレジスタ

いちばん重要な設計判断であり、issue が名指しした部分。PPU に「スクロールX」「スクロールY」は無い。あるのは

- **`v`** — 15bit の現在VRAMアドレス（`$2007` が読み書きするアドレスでもある）
- **`t`** — 各ライン/フレームの頭で `v` に再ロードされる15bitの「一時」アドレス
- **`x`** — 水平方向の微調整3bit
- **`w`** — `$2005` と `$2006` が共有する書き込みトグル

`$2005` と `$2006` は**同じ `t`** の重なり合うビットフィールドに書く。この4本をモデル化すれば（loopy の名前をあえて使う。レジスタレベルの資料が全部この名前なので、コードと資料が同時に読める）、スクロールは正しく出る。バグに見えるものも全部込みで：画面を動かすフレーム途中の `$2006` 書き込み、全スクロールゲームが NMI ハンドラでやる `$2005`/`$2006` の並び、coarse-Y が 29 で折り返す仕様（ゲームが 30 を入れると属性テーブルがタイルとして描かれる）。代わりに「scrollX / scrollY」でモデル化すると、以後ずっとゲームごとの特殊処理を書き続けることになる。

`v` の更新はハードウェアと同じ3つの基本操作で行う：8ドットごとの coarse-X インクリメント（水平ネームテーブルビットへ桁上がり）、ドット256での fine/coarse-Y インクリメント、そして `t` からの水平コピー（ドット257）と垂直コピー（プリレンダ行のドット280-304）。

### 背景

標準のフェッチパイプライン：ネームテーブルバイト、属性バイト、パターン下位、パターン上位。各2ドットで、16bitシフトレジスタに供給し、fine-X がそこから1bitを選ぶ。属性は**タイル**あたり2bitだが8ピクセルに揃える必要があるので、`$00` か `$FF` として専用のシフトレジスタに塗り広げる。

### スプライト — 評価はサイクル精度のステートマシン

「このラインのスプライトを集める」式の素朴な実装は基本テストを通って面白いテストで落ちる。**スプライトオーバーフローはハードウェアのバグで、ゲームはそのバグに依存している**からだ。実チップはドット65-256にわたって小さなステートマシンでOAMを評価し、8個見つけた後も走査を続けるが、そのとき `n` と `m` を**両方**インクリメントする。つまり次のスプライトの間違ったバイトからY座標を読み始める。結果としてフラグは9個未満のラインで立ち、9個以上のラインで立たないことがある。`$2002` bit5 をラスタタイマとして使うゲームはこの挙動を前提に書かれているので、再現は衒学ではない。「修正した」実装はそれらを壊す。このコアはステートマシンを実装している：

- ドット1-64の偶数ドットで二次OAMをクリア（その間 `$2004` は `$FF` を返す）
- 評価開始は 0 ではなく **`OAMADDR`**（VBlank終わりに非ゼロを残したゲームはスプライトリストが回転する）
- ドット257-320の間 `OAMADDR` は0に固定される
- `n`/`m` 二重インクリメントのバグ
- オーバーフロー検出後の追加3リード

スプライトのフェッチはドット257-320、8ドット×8グループ。未使用スロットもタイル `$FF` をフェッチする — 誰にも見えないダミーだが、MMC3 はアドレスバスを見ている（§6）。

スプライト0ヒットは、不透明なスプライト0ピクセルと不透明な背景ピクセルが重なったときに立つ。左端クリップの2ビットと、x=255 では立たないというハードウェアの仕様も守る。

### VBlank・NMI・`$2002` の競合

VBlank フラグは (241, 1) で立ち、スプライト0ヒット／オーバーフローと一緒に (261, 1) でクリアされる。`nmiLine()` は NMI 線を**レベル**として返し（VBlankフラグ AND `$2000` bit7）、機種がそれを CPU 自身のエッジ検出器に流す。だから「フラグが既に立っている状態で NMI を有効化」が特別扱いなしで即発火する。

`$2002` の読み出しはフラグ**と** NMI 条件の両方をクリアする。フラグが立つちょうどそのドットに読み出しが当たると、そのフレームの NMI は起きない。1ドット手前だとフラグ自体が立たない。ゲームは `$2002` をタイトループでポーリングするので、これは隅っこの話ではない — 「ゲームが動く」と「数分ごとに固まる」の差だ。どちらも特殊処理ではなくモデルから自然に出てくる（早い読み出しには抑止フラグ、遅い読み出しには通常のクリア）。

奇数フレームの短いライン（レンダリング有効時、プリレンダ行のドット340をスキップ）の判定はドット**339**でラッチする。340ではない。プリレンダ行の途中で背景を有効にしたゲームは、既に決定済みの結果を受け取るからだ。

### 出力

`frameBuf` は `Uint8Array(256×240)` の NESパレットインデックス（0-63、グレースケールは適用済み）、`frameEmph` はそのピクセルを描いたときの強調ビット。DOM無し、RGBの判断も無い — `machine88.js` が 8801 のパレットインデックスをピクセルに変える構造とまったく同じ切り分け。`buildNesPaletteRgb()` が 64 × 8 × RGB のルックアップテーブルを作る。強調ビットは標準的な方法（あるビットを立てると**他の2チャンネル**が0.746倍に減衰する。だから3つ全部立てると画面全体が暗くなる。ゲームはまさにそれを使う）でモデル化した。

**VRC2/VRC4 は1つのチップに iNES 番号が4つ付いている。** コナミは基板リビジョンごとにレジスタ選択の下位2線を別々に配線したが、`.nes` フォーマットにはそれを書く場所が無い。だからレジスタ index は `A0`/`A1` から来たり、その2本が入れ替わっていたり、`A2`/`A3` だったり、`A6`/`A7` だったりする。ここでの解決は定石通り、候補の線の組を OR で合成する方式。ゲームは自分の基板が使う組しか駆動しないので、他は0として読め、実用上は一意になる。

**VRC の IRQ タイマは分数プリスケーラを持つ。** スキャンラインモードではカウンタは 341 PPU ドット＝113と2/3 CPUサイクルごとに1回刻まれ、実機は「毎サイクル341段カウンタから3を引く」でそれを実現している。この分数が肝で、スキャンラインあたり整数サイクルにすると1フレームかけて目に見えてズレる。コナミのラスタ分割はズレない。

**MMC2/MMC4 は CPU を一切介さずに CHR バンクを切り替える。** 4KB 窓それぞれに2本のバンクとラッチがあり、PPU がタイル番号 `$FD` / `$FE` を読むとラッチが反転する。パンチアウト!! は対戦相手の顔をそのタイルに置いているので、スプライトの上半分と下半分が別バンクから描かれる。MMC2 は厳密なアドレス（`$0FD8`）で、MMC4 は `$0FD8`-`$0FDF` の範囲でラッチする（1PPUサイクル遅れてラッチするため）。

実ゲームが起動するかどうかを決める2点：

**MMC1 は連続CPUサイクルの2回目の書き込みを無視する。** チップが落ち着くのに1サイクル要る。これは些事ではない：リード・モディファイ・ライト命令（`INC $8000`）は古い値と新しい値を背中合わせのサイクルで書き、ゲームは**1命令で1bit送るために意図的に**それをやる。両方の書き込みをエミュレートするとシフトレジスタが同期を失い、ゲームはゴミを起動する。だから機種は `cpuWrite` に CPU サイクル数を渡している。

**MMC3 の IRQ カウンタはタイマではなく、PPU のアドレス線 A12 を見ている。** 背景タイルが `$0000`、スプライトタイルが `$1000` にあると、A12 はスキャンラインの背景フェッチの間ずっと Low で、スプライトフェッチが始まるところで立ち上がる。CPUへの配線なしで、スキャンラインあたり1回の立ち上がりがタダで手に入る。難点は通常のフェッチでも A12 が揺れること。そこで基板はフィルタをかける — **先に A12 がしばらく（約3CPUサイクル ≒ 8-9ドット）Low だった立ち上がりだけを数える**。フィルタが無いとカウンタは数倍速く走り、ステータスバーが違う場所に出る。

ここから他のコードへの帰結が2つ。PPU は**すべての**フェッチをアドレスバス経由で出さなければならない — スプライト期のガベージ・ネームテーブルフェッチも、各ラインの末尾2回のダミーフェッチも含めて（それらこそ A12 を Low に保ってフィルタを武装させている）。そして基板が見るアドレスは**1ドット遅れ**で渡す — PPU はあるドットでアドレスを駆動し、基板は次のドットでそれが落ち着くのを見る。この遅れは測定できる：`mmc3_test` の `4-scanline_timing` は結果のIRQ位置を1PPUクロック単位で確認しており、遅れが無いと全スキャンラインIRQが1ドット早く出る。関係ない基板は `wantsPpuBus = false` を宣言して何も払わない（毎フレーム89,000回の呼び出しは、スキャンラインカウンタのためなら払う価値があるが、NROM のためには無い）。

## 7. `machinenes.js` — 機種と、2つのクロックの同期

`NesMachine` は `Pc8801Machine` と同じ契約を満たす：`stepFrame()` / `frame` / `snapshot()` / `restore()` / `schemaVersion`、加えて `update(dt, onFrame)` と `render()`。

### 同期はコード1行

m6502.js にはサイクル表が無い — **バスアクセス1回がちょうどCPU1サイクル**。だから CPU 自身のバスが*サイクルクロックそのもの*であり、同期の全部は「バスアクセスの頭でPPUを3ドット進めてから、アクセスを行う」で終わる。

```js
this.cpu = new M6502({
  read:  (a)    => { this._tick3(); return this._read(a); },
  write: (a, v) => { this._tick3(); this._write(a, v); },
});
```

これでレジスタ書き込みは本物のドット位置に落ち、6502 がやる空読み（ページ跨ぎ、RMW）も実機どおりに PPU を進める。追いつき処理も、「Nサイクル走ってからN×3ドット」式の近似も要らない。

### 割込線をどこでサンプルするか

CPU 1サイクルは3ドットだが、割込線はその両端ではなく**内側**でサンプルされる。m6502.js は命令境界でポーリングするので、サイクルNの間に渡したレベルがサイクルN後のポーリングで見えるレベルであり、そのレベルを何ドット目でサンプルしたかは直接測定できる：

- **NMI** は3ドットのうち**1ドット目**の後でサンプルする。blargg の `05-nmi_timing` は NMI がどの命令の後に落ちたかを、1行ごとに1PPUクロックずつ遅らせながら印字する。サイクル頭でサンプルすると1ドット遅く、サイクル末でサンプルすると2ドット早く、真ん中だけが通る。`06-suppression` `07-nmi_on_timing` `08-nmi_off_timing` も同じ位置で通る。
- **IRQ**（マッパー＋APUフレームカウンタを `setIrqSource` でワイヤードOR）は**2ドット目**の後。これを決めているのは `mmc3_test` の `4-scanline_timing`。

### OAM DMA

`$4014` は CPU を止めて256バイトを OAM にコピーする。513サイクル、奇数サイクルで始まると514。このサイクルは実在する — その間も PPU は描き続けるので、DMA を遅く始めたゲームはスプライトリストが裂ける — ので、機種が `cpu.cycles` に手で足し、各サイクルで PPU を回す。

### コントローラ

`$4016`/`$4017` はパラレルイン・シリアルアウトのシフトレジスタ。ストローブHighの間は連続リロード、Lowにしてから `$4016` を8回読んで8bit を取り出す。`machine.pads` はポートごとに1バイトのボタン状態（`BUTTON.A`=0 … `BUTTON.RIGHT`=7）。ホストが書き、機種がシフトする。

### DMC DMA

DMC は CPU バスに触る唯一の音源チャンネルで、サンプルの1バイトが欲しくなると**CPUを4サイクル止める**。このサイクルは共有ではなく**横取り**で、実行中の命令が自分のサイクルの合間で中断される。APU 自身はバイトを取りに行けない（バスは機種のもの）ので、`nesapu.js` は `dmc.needByte` を立てるだけで、`machinenes._dmcDma()` がサイクルを払って `dmc.fill()` を呼ぶ — OAM DMA が元々やっていたのと同じ形。どちらも `cpu.stallForDma()` で「自分は寝ていた」ことを CPU に伝える（§4）。

1フレームは固定のPPUドット数なので、DMA でフレームが**長くなる**わけではない。**フレームの中でCPUがこなせる仕事が減る**。ゲーム上の見え方はこう：命令数を数えて作ったラスタ分割が、サンプル再生中だけ揺れる。

## 7a. `nesapu.js` — 音

矩形×2・三角・ノイズ・DPCM と、それら全部を刻むフレームカウンタ。

**OPN のように pull するのではなく、CPU から刻む。** `ym2203.js` は `render()` がサンプルを要求したときに発振器を進める。FM チップは独立したクロックドメインだからだ。2A03 はそのチップではない — **CPU そのもの**で、同じダイ・同じクロック — そしてゲームが依存するもののうち3つは音のイベントではなく CPU サイクルのイベントだ：フレームカウンタの IRQ（汎用タイマとして使われる）、`$4015` の長さカウンタビット（音楽ドライバがポーリングする）、そして DMC の DMA。だから `tick()` は `_tick3()` から CPU 1サイクルにつき1回走り、音はその副産物として出てくる — 箱型フィルタが約37 CPU サイクルを1つの48kHzサンプルにまとめ、`render()` が吸い出すリングに積む。**音はシミュレーションの出力であって、シミュレーションを駆動するものではない** — これが巻き戻しを正確に保つ理由でもある。

フレームカウンタ（分周器リロード後の CPU サイクル数）：

| サイクル | 4ステップ | 5ステップ |
|---|---|---|
| 7457 | quarter | quarter |
| 14913 | quarter + half | quarter + half |
| 22371 | quarter | quarter |
| 29828 / 29829 / 29830 | **3サイクルすべてでIRQフラグをセット**、29829 で quarter+half、29830 で折り返し | 29829 で quarter |
| 37281 / 37282 | — | quarter + half、折り返し |

飾りではない3点：

- **IRQ フラグは3サイクル連続で立つ**（1サイクルではない）。`bit $4015` を背中合わせで撃つドライバはそのどれかで捕まえられる。1サイクルのモデルにすると blargg の `6-irq_flag_timing` と `5-branch_delays_irq` が2サイクルずれる。
- **`$4017` への書き込みは3〜4 CPU サイクル遅れて効く** — APU サイクル上に落ちたなら3、間なら4 — これによって、CPU がいつ書いたかに関わらず再スタートしたシーケンスが APU 自身のクロック格子に揃う。即座に適用すると以後のフレームIRQが全部ずれる。
- **分周器がリロードされるサイクルが新シーケンスのサイクル0。** ここを1ずらすと quarter/half とIRQが全部1サイクル早く出る。`apu_test` の `5-len_timing` と `6-irq_flag_timing` がどちらも「too soon」と言う。

**リセットは電源投入ではない。** RESET は `$4015` をクリアしてフレームカウンタを再起動するが、レジスタの値は残る — 特に **`$4017` に最後に書かれた値がもう一度書かれる**ので、5ステップモードを選んでいたドライバは5ステップのままになる。リセットを電源投入として扱うエミュレータは、音楽を間違ったモードで再開する（`apu_reset/4017_written`）。

**ミキシング**は文書化されている非線形DACカーブを2つのテーブルに焼いてある。チャンネルを線形に足すと和音が大きくなりすぎる — 微妙にではなく、聴いて分かるほど間違う。その後は本体のアナログ段を通す：ハイパス2極（90Hz・440Hz）とローパス14kHz。**チップではなく基板**をモデル化するのは、`machine88.js` が OPN の抵抗ミキサに対してやっているのと同じ選択。

**`renderAudio(out, n)`** は `machine88.renderAudio()` と同じシグネチャなので、ホストのオーディオポンプは相手がどの機種か気にしない。OPN と違うのは**吸い出すだけ**という点 — サンプルは CPU が走っている間に既に作られている。アンダーラン時は最後のサンプルを保持する：時間を進めずに音だけ追加で作らせることはできないので、代替はクリックノイズしかない。

## 8. ホスト統合（`demo/machine.html`）

ホストは機種を**クラスではなく能力**で選ぶようになった。以前は `machine instanceof Pc8801Machine` が十数箇所にあり、新しい機種を足すたびにホストに `instanceof` を1つずつ教える必要があった。一般化の中身：

- `hasOwnRender(m)` / `renderMachine(extra)` — 自前の `render()` を持つ機種にはオプションを渡す（意味の無いオプションは機種側が無視する）。PC-8001 はテキストシステム経由で描く。三項演算子3箇所が呼び出し1つになった。
- `crtcOf(m)` — CRTC があればそれ、無ければ `null`。ステータス行は例外を投げずに劣化する。
- フロッピープールは `typeof m.insertDisk === 'function'`、フレーム毎オーディオフックは `typeof m.renderAudio === 'function'`、CPU速度表示は `m.effectiveCpuPct !== undefined` で判定。

それ以外 — スナップショットのリングバッファ、巻き戻しボタン、ジョグシャトル、速度倍率 — は元から機種非依存で、**変更は一切不要だった**。issue が賭けたのはそこで、賭けは当たった。

ファミコン固有に増えたもの：`ファミコン` 起動モードボタン、`.nes` ファイル入力（壊れたヘッダや未実装基板を黙って失敗せず画面に出す）、**ディスクシステムのグループ**（`.fds` ＋ `disksys.rom` ＋ 面セレクタ。§12.7）、キーボード→パッドのマップ（カーソル、Z/X = B/A、Enter = START、Shift/Space = SELECT）。既存のゲームパッド設定のジョイスティックビットも変換するので、パッド設定パネルは両方の系統で効き続ける。

第4段が「足した」のではなく「直した」もの：**ファミコンのファイル選択は画面に出ていなかった。** これらは折り畳みメニューバーが隠す `row-sys1` にあり、📁ファイル メニューに項目が無かった — メニューバーが行を乗っ取ったときに 📼テープ が孤児になったのと同じ形。`fnes` と新設の `grp-fds` を項目に足した。

CRTパイプラインはドットあたりの GRB インデックス（0-7）と、任意で銃ごとの `drive` レベルを食う。ファミコンの `render({ indexed: true, analog: true })` は両方を出す：インデックスは64色パレットの粗い縮退で、`drive` が本物のRGBを運ぶ。だから蛍光体シミュは8原色ではなく本来のパレットを描く — `machine88.js` がアナログパレットに使っているのと同じ仕組み。

**未検証：** ブラウザでの実際の見え方。上記はすべて headless で検証している（フレームバッファ、snapshot/restore、`test-nes.mjs` で再現したトランスポートループ）。蛍光体/ブラウン管シミュを通って実際のキャンバスに届くピクセルは **visual未検証**。

## 9. スナップショット方針（巻き戻しの実体）

`demo/machine.html` はスナップショットを最大1000個リングバッファに持ち、約150MBに収まるよう間隔を自動調整する。**スナップショットが大きいと巻き戻せる時間が短くなる**ので：

- **不変データはスナップショットに入れない。** PRG-ROM / CHR-ROM は読み込み済みカートリッジから参照で持ち、参照で復元する（`machine88.js` がマウント済みD88に適用しているのと同じ規則を、隠さず明記している）。
- **フレームバッファは出力であって状態ではない。** 次のフレームが再生成するもののために1枚120KB払うと、巻き戻し可能時間が桁で縮む。
- **一度も書かれていないワークRAMはコピーしない。** iNES 1.0 は基板の実態に関わらずほぼ全カートリッジに8KBのPRG-RAMを宣言する。マッパーが「書かれたか」を追跡し、書かれていなければ `null` を格納する（復元時はゼロ埋め ＝ 「一度も書かれていない」の意味そのもの）。
- すべて plain data：数値・真偽値・型付き配列。クラス再構築は無いので `restore()` は**既存の**オブジェクトに書き込み、ビューやエイリアスが生き続ける。

- **APU のサンプルリングも出力なので、スナップショットに入れない。** チップの**状態**（分周器・シーケンサ・エンベロープ・DMCのシフトレジスタ）は入れる。リサンプラの位相とフィルタのメモリも入れる — これが「復元後に**出てくるサンプル列**が元の走行と完全に一致する」理由。失われるのはまだ吸い出されていなかった数十サンプルだけ ＝ 巻き戻した瞬間の1バッファ分で、その後には響かない。

- **書けるメディアは差分で運ぶ。コピーでは運ばない。** ディスクシステムはここで唯一メディアが書ける機種。スナップショットはセーブが変えたバイトだけを運ぶ（§12.4）。

実際に運ばれるもの：ワークRAM 2KB、CIRAM 2KB（4画面基板なら4KB）、OAM 256B、二次OAM 32B、パレット 32B、PPUのレジスタ/ラッチ/パイプライン状態、CPUレジスタファイル、マッパーレジスタ、基板にあればCHR-RAM、コントローラとAPUの状態。**素のNROMゲームで約3KB、CHR-RAM＋書き込み済みワークRAMを持つ基板で約11KB、ディスクシステムのゲームで46KB**（32KBのアダプタRAMが常に生きているため） — PC-8801 のスナップショット（RAM＋GVRAM3面＋サブCPU）より一桁小さいので、リングは枚数で律速され、メモリでは律速されない。

APU をまるごと足して増えたのは**約90個の数値、JSONで800バイト未満**。ワークRAM 2KB に対して測定上ほぼ無で、テストがそれを維持していることを検証している。

## 12. `fds.js` — ファミコンディスクシステム

第4段。これがこのエミュレータを「ゲームが1本も無いもの」から「ライブラリがあるもの」に変える部分で、理由は算数だ：このマシンには **`.nes` が0本**、**`.fds` が192本**ある。

### 12.1 ディスクシステムとは何か

カートリッジではない。カートリッジスロットに刺さる **RAMアダプタ** — `$6000`-`$DFFF` の 32KB プログラムRAM、8KB キャラクタRAM、`$E000` の 8KB BIOS、CPU に割込をかける汎用ダウンカウンタ、そして波形音源 — と、三菱 **クイックディスク**を読むドライブ。iNES がこれを「マッパー20」と呼ぶのはファイルフォーマットに他に置き場所が無いからで、そんな基板は存在しない。番号が指しているのは**アダプタ**だ。

ここから3つの帰結が以下すべてに効いてくる：

- **ゲームを起動するプログラムはディスクではなく BIOS にある。** だから `.fds` だけでは走らない。`disksys.rom` を別に用意する必要がある（§12.7）。
- **`$E000`-`$FFFF` が ROM で `$6000`-`$DFFF` が RAM** — カートリッジと逆なので、`FdsAdapter` は基底 `Mapper` の CPU バスを丸ごと上書きする。
- **メディアが書ける。** このリポジトリの他のどの機種にも無い性質で、スナップショットがこれまで無視できていた唯一のものだ（§12.4）。

### 12.2 イメージ形式と、そこから欠けている層

クイックディスクのトラックはセクタの無い1本の長い螺旋。そこに載っているのは**ブロック**の連なり：

```
[ リードインギャップ ][1][ ブロック1: ディスクヘッダ 56B ][CRC][ ギャップ ][1][ ブロック2: ファイル数 2B ][CRC]
[ ギャップ ][1][ ブロック3: ファイルヘッダ 16B ][CRC][ ギャップ ][1][ ブロック4: ファイルデータ 1+N B ][CRC] ...
```

`.fds` 形式が保持しているのは**ブロックのバイトだけ** — 1面あたり65500バイト、先頭に16バイトヘッダが付くこともある。ギャップもスタートビットもCRCも消えている。だから欠けた層をどうするかを決める必要があり、ここで第3段の見立ては**半分だけ当たっていた**：

- **ギャップは戻さなくていい。** このドライブはギャップの中を走らない（§12.3）。
- **CRC バイトは戻す必要がある。** FDS BIOS は CRC をデータと全く同じように `$4031` から読む：ディスクヘッダの56バイトの後、さらに2回転送する。これを省くと2ブロック目以降が全部2バイト手前から始まり、BIOS は `$02` を期待している場所で `$09` を読み、ロードが2ブロック目で失敗する。**これが第4段で最初に踏んだ本物のバグで、その症状 — 自分のディスクヘッダだけは完璧に読んで、そこで諦める — は覚えておく価値がある。**

というわけで `parseFds()` はブロックチェーンを歩き（ブロック2のファイル数は信用しない。実際のイメージではかなりの割合で実態と食い違う）、面ごとに2本目の配列＝**物理ストリーム**を作る：各ブロックの後ろにゼロ2バイト。`exportFds()` はその厳密な逆で、ゲームが書き込んだディスクを普通の `.fds` として書き戻せる。CRC の**値**は一切検査しない — `$4030` bit4 のエラーは決して立たない。`.fds` イメージには間違いようのある CRC が無いからだ。

### 12.3 ドライブ：ヘッドはプログラムが動かしたときに動く

素直なモデルは自走ヘッドだ：149 CPUサイクルごとに1バイト（ドライブは約96.4kbit/s）、誰が聞いていようがいまいが延々と。実機はそうしている。ここではそれが**動かない**。理由は消されたギャップだ：2つのブロックの間で、自走ヘッドには*待つ場所が無い*。BIOS が1ブロック目を消化している間にヘッドは次のブロックを食い進み、ディスクが同期を失う。

ここで採った答えは FCEUX が20年間出荷してきたもの：**バイトクロックは本物、ヘッドは自走しない。** 転送フラグ（`$4030` bit1、`$4025` bit7 が要求していればその IRQ も）は前のバイトから149サイクル後に来て、実機同様に BIOS の転送ループをペーシングする。だがヘッドが1歩進むのは CPU が実際にバイトを通したときだけ：読み込みモードでの `$4031` 読み、書き込みモードでの `$4024` 書き。こうするとブロック境界を見失うことが原理的に起きない。

コストははっきり書いておく：`$4030` を見る代わりにサイクルを数えてドライブのタイミングを取るプログラムからは、「自分を待ってくれるドライブ」に見える。そんなタイトルは知られていない — ドライブは BIOS のものだ。

間違えやすく、実際ここでも最初に両方間違えた2点：

- **`$4031` はラッチ。** バイトが来ていないときに読むと直前のバイトを返し、ヘッドは**動かしてはいけない**。BIOS は vblank 待ちの NMI ハンドラ（`$E1E6`）から、*ゲームが画面を待つ全フレームで* `$4031` を読む。だから読むたびにヘッドを進めるドライブは、プログラムの知らないところで毎フレーム1バイトずつディスクを先送りする — 症状が出るのは数万バイト先、ブロックが違う場所から始まったときだ。
- **`$4025` bit6 が転送のゲート、bit1 が巻き戻し。** bit6 を落とすとヘッドはブロックとブロックの間で止まる（BIOS はこれでブロック単位に読む）。bit1 を立てるとヘッドは面の先頭に戻る — クイックディスクのヘッドは物理的に戻るのであって、ディスクが一周してくるのではない。

このアダプタの2つの IRQ 源は1本の線を共有するが、**確認応答は別々**：`$4030` の読みがタイマを、バイトを1つ動かすことがドライブをクリアする。

### 12.4 書き込みと、巻き戻しがそれを生き延びる方法

ゲームはディスクにセーブする。つまりメディアは機種状態の一部であり、バイトを戻さない巻き戻しは「セーブより手前に巻き戻してセーブだけ残す」ことを許してしまう。

§9 のルールはそのまま生きている — **不変データは絶対に運ばない** — のでスナップショットはディスクもそのコピーも運ばない。運ぶのは**差分**：`(面, 位置)` → 書かれたバイト の `Map`。`restore()` はスナップショットに無い書き込みを取り消し（元のバイトは、汚れないまま保持されている解析済みイメージから読み戻す）、有るものを適用する。コストはディスクのサイズではなく書き込み数に比例するので、巻き戻しリングが1面65500バイトを毎フレーム memcpy することはない。

実測、`とびだせ大作戦` を1500フレーム走らせた時点：**1スナップショット47,220バイト** — 32KB アダプタRAM ＋ 8KB CHR-RAM ＋ 約6KB の PPU/CPU/APU/マッパー状態、そしてディスクは**0バイト**。素の NROM カートリッジ3KBの15倍だが、それでもホストのリングを縛るのは150MBの予算ではなく1000枚という枚数の上限のまま（1000 × 46KB = 46MB）。

**書き込み経路の位置合わせは実BIOSを実測して決めた。このファイルで一番ややこしいのがここ。** 書き込まれるブロックはストリーム上の長さと一致しない：

- BIOS が `$4024` に流す最初のバイトは `$80` — ブロックの**スタートマーク**で、物理ディスク上では1ビット、`.fds` には対応するバイトが無い。飲み込むが、**ヘッドを動かしてはいけない**。
- 反対の端では、BIOS は CRC の*1バイト目*を普通のデータと同じように流してから `$4025` bit4 を立て、**2バイト目はドライブが自分で出す**。つまり `$4024` の書き込みが対応しないスロットを1つ跨ぐ必要がある。

どちらかを間違えても書き込み自体は成功しているように見える（バイトはどこかに行く）が、全部が1バイトずれ、BIOS が検証のために読み戻して比較に失敗し、無限に書き直す。**光神話パルテナの鏡は起動時にこれをやる**。だからここは推測ではなく実測になった：ヘッドがずれた状態では走行時間いっぱいリトライループに座り、2つの規則を入れるとタイトル画面まで到達する。FCEUX はここで2バイト飲み込む。このドライブでそれをやると書き直したブロックが全部ずれる。

### 12.5 音源

追加の1声。しかもこの本体で一番変な声だ：1ステップ6ビットの64ステップ波形テーブルを、*2枚目の*テーブルが再生中に上下に曲げる周波数で鳴らす。ディスクシステム特有のうねりはここから来る — ゼルダのタイトル、メトロイドの洞窟、パルテナ。

変調器は LFO ではない。32エントリの5方向ステップ表（+1, +2, +4, リセット, −4, −2, −1）が符号付き7ビットカウンタを駆動し、そのカウンタが整数アルゴリズムでピッチオフセットになる。そこには意図的な非対称が2つある：丸めステップが上方向には +2、下方向には −1 を足すこと、そして折り返し点が ±128 ではなく 192 と −64 であること。両方そのまま再現している。どちらかを「素直な」対称版に置き換えるとビブラートが上ずる。

音が出るまでの経路は `nesapu.js` の新しいフック **`apu.expansion`** — `output` ゲッターを持つオブジェクトで、`mix()` で足される。拡張音源は 2A03 の一部ではなく、本体の音声ピンで合成されるものなので、チップの持ち主が刻み、APU は読むだけ。`FdsAdapter` がチャンネルを所有して自分の `cpuCycle()` から刻む。`nesapu.js` はディスクが何かを知らないままでいる。VRC6・VRC7・Sunsoft 5B・Namco 163 も同じフックに刺せる。

**誰も聴いていない。** アルゴリズムは数値として検証してある（`test-fds.mjs` が波形ポインタの進み方、halt の挙動、非対称な曲げ、スナップショットを跨いでサンプル列がビット一致することを縛っている）し、ミキシング係数は耳を使わない見積もりだ。

### 12.6 192本一斉スイープ

`nestools/sweep.mjs`。`docs/m88-comparison.ja.md` が PC-8801 の353枚に、`mdtools/sweep.mjs` がメガドライブの66本に対してやったのと同じ手：全部走らせて機械的に分類し、落ちたものだけを開ける。

**神託が無い。** PC-8801 のスイープは M88 と差分が取れた。これは何とも差分が取れない — 参照エミュレータが入っていないし、これらのディスクの正解スクリーンショットもここには無い。

純粋なピクセル推測から救ってくれるのは、独立した2つ目の観測対象だ：**CPU がどこにいるか。** FDS BIOS が vblank 待ちを所有しているので、動いているゲームも死んだゲームもフレーム間は `$E1C5` に居る — が、動いているゲームはそこを抜けてアダプタRAM上の自分のコードを実行し、死んだゲームは決して抜けない。だから走行後に20万命令ぶん進めて、`$E000` 未満に落ちた数を数える。「絵が凍っている **かつ** ゲームのコードが走っていない」は、イメージについての意見ではなく機種についての事実だ。

ただしこのプローブは「十分長く走らせる」ことの代わりにはならない：**まだロード中**のタイトルも自分のコードを1つも実行していないので、死んだものと見分けがつかない。磁界少年メット・マグ は2400フレームでは stuck と読め、3600フレームでは遊べている。

```sh
FDS_BIOS=/path/disksys.rom node nestools/sweep.mjs <dir> --frames 3600 --jobs 12
```

| バケツ | 意味 |
|---|---|
| `reject` | `.fds` が解析できない、または機種が組み立てられない |
| `noload` | ヘッドが最初のブロック群から先に進まなかった — BIOS がゲームをディスクから読めていない |
| `stuck` | `$E000` 未満のコードが1つも走らなかった — 機種が諦めている。BIOS のエラーバイト `$90` を添えて出す。 |
| `black` / `flat` | ロードはできたが1色か2色しか描いていない |
| `static` | 一度出た絵がそれ以降変わらない |
| `ok` | 複数色があり、動き続けている |

**スイープ側**が学ぶ必要のあった3点。どれもエミュレータ側の修正より数字を動かした：

1. **最後のフレームではなく一番良いフレームで判定する。** ディスクのゲームは最初の1分の多くを黒画面で過ごす — BIOS のロード、パブリッシャのロゴ、2回目のロード。最終フレームを見るのは「20秒後に何が映っていたか」を答えているだけで、聞きたい問いではない。走行中の最大色数を取るようにしたら、エミュレータを1行も変えずに `flat` 22本＋`black` 4本が `ok` に移った。
2. **十分な秒数を与える。** ドライブは本当に149サイクルで1バイトしか動かないので、ロードは1986年と同じだけ時間がかかる。1200フレーム（20秒）ではドラキュラIIはまだロード中で、2400フレームで冒頭のテキストを出す。磁界少年メット・マグ は3600フレーム要る。
3. **ディスクを裏返す。** 2面のゲームはぴたりと止まって要求してくる。スイープはヘッドが遊んでいて**かつ**絵が凍っている状態が4秒続いたら面を入れ替える。両方の条件が要る — 遊ばれているゲームは何分もドライブに触らないので、その下でディスクを抜いたら測っている対象を壊すことになる。

**192本全部・各3600フレーム（1分）の結果：**

| 判定 | 本数 |
|---|---|
| `ok` — ロードして動作 | **189** |
| `stuck` | **3** |
| `reject` / `noload` / `black` / `flat` / `static` | 0 |

**192本中189本（98.4%）がディスクから読み込まれて動く。** 解析に失敗するイメージも、未実装の基板も、CPUのJAMも、ロードできないディスクも1本も無い。落ちている3本はすべて同じ形 — **ロードは最後まで通り、そのあとで止まる**。

止まる3本：

| ディスク | 何が起きているか |
|---|---|
| `きね子 - Kinetic Connection - The Monitor Puzzle` | A面の全ブロックを正しく読む（ブロック表と突き合わせて確認：12,482→12,497 ファイルヘッダ、12,500→12,502 データ、12,505→12,520 ファイルヘッダ、12,523→45,419 データ、すべてバイト単位で一致）。そのあと自前のドライバが `$4025=$2F` を書いて諦める。最後は BIOS の vblank 待ちに座り、短いメッセージを表示したまま、20万命令中 BIOS 外は483。 |
| `きね子 … Vol. II` | 同じゲームの同じ場所。 |
| `カリーンの剣` | 同じ形：ロードし、画面を描き、そのあと自分のコードを実行しない（882 / 20万）。 |

**3本とも、原因はディスク層ではない。** ブロック境界は全部 `parseFds()` のブロック表と一致し、CRC フェーズのずれも無く、ディスク終端にも達しておらず、書き込みも無い。残るのは「他の189本が入らない状態で、このドライブが実機と違う応答を返している」こと。一番怪しいのは**ブロック途中の一時停止**（ブロックの途中で `$4025` bit6 を落として立て直す動作。このドライブはそこから厳密に再開するが、実機のヘッドは回り続ける。§12.3）。

### 12.7 BIOS の入手（リポジトリには入っていないし、今後も入らない）

`disksys.rom` は8192バイトで著作物。これを作ったマシンでは BIOS アーカイブの中にあり、第3段がここで踏み抜いたので罠を書いておく：**ディスクイメージの隣にある `disksys.dat` は BIOS ではない。** データベースだ（先頭が `NEU ;1;0;1;2;…`）。本物は：

```
(EMU)BIOS(…,FDS,…).zip → BIOS/FamicomDiskSystem.zip → disksys.rom
```

使う前に確認すること：**8192バイト、MD5 `ca30b50f880eb660a320674ed365ef7a`**。このリポジトリの `zip.js` は二重の zip をどちらも開けるので、ブラウザ側は外部ツール無しで済む。

そのうえで：

```sh
export FDS_BIOS=/path/to/disksys.rom
node nestools/fdsrun.mjs game.fds --frames 3600 --art     # 1本、サムネイル付き
node nestools/sweep.mjs /path/to/disks --frames 3600 --jobs 12
```

`demo/machine.html` では BIOS は `💽 ディスクシステム` グループで一度だけ選び、IndexedDB に `fdsbios` ロールで保持する。ディスクは保持しない（ディスクはユーザーが差し替えるものだから）。2面のディスクを読むと面のセレクタが出て、切り替えると排出→挿入する — 黙って中身を差し替えたら、BIOS からは何も起きていないように見える。
