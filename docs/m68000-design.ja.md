# 設計 — m68000（Motorola MC68000 / 68EC000）

`m68000.js` はこの collection の 16/32bit CPU コア。**1本だけ書いて共有する**：
メガドライブも X68000 も 68000 を積んでいるので、チップは機種非依存で書き、
バスは各機種が注入する。コアは VDP のレジスタもスプライトコントローラも
FDC も知らない。

## 契約（suite-contract 準拠）

- pure・依存ゼロの JavaScript。DOM なし・`Math.random` なし・sibling import なし。
  ES modules。
- 決定論：同じプログラム＋同じバス → 毎回ビット単位で同一の状態。
- `step()` は命令をちょうど1つ実行する（あるいは保留中の例外・割込を1つ受け付ける）
  だけで、消費したクロック数を返す。
- `snapshot()` は `schemaVersion` 付きの plain data を返し、`restore()` はその
  厳密な逆関数。
- コアは「どう使われるか」を決めない。フレームループも、タイミングの主導権も、
  画面という概念も持たない。

## API

```js
import { M68000, BusError, VEC } from 'upd3301/m68000';

const cpu = new M68000(bus, { tasWriteBack: true });
```

### バス

68000 のデータバスは UDS/LDS のバイトストローブ付き 16bit、アドレスバスは 24bit。
注入するオブジェクトはそれを写している：

| メンバ | 必須 | 意味 |
|---|---|---|
| `read16(addr)` | ○ | ワードサイクル1回（両ストローブ） |
| `write16(addr, val)` | ○ | ワードサイクル1回 |
| `read8(addr)` | — | バイトサイクル1回（偶数=UDS・奇数=LDS） |
| `write8(addr, val)` | — | バイトサイクル1回 |
| `read32(addr)` / `write32(addr, val)` | — | ただのRAM向けショートカット |
| `irqAck(level)` | — | 割込アクノリッジ。ベクタ番号を返す。負値/未定義ならオートベクタ |
| `resetLine()` | — | `RESET` 命令から呼ばれる |

必須なのは 16bit の2本だけ。ピンがそうだから。バイトアクセサが無ければ、
含んでいるワードの read-modify-write で合成する。32bit アクセサが無ければ
上位ワード先行の2ワードサイクルに分解する。**つまり副作用のあるレジスタを持つ
ハードは、実シリコンと同じ回数のトランザクションを見る**。
**渡したオブジェクトは絶対に書き換えない**：解決済みのコールバックは CPU 側に
持つので、クラスで書いたバスも自分の `this` を保てる。

バスに渡すアドレスは 24bit にマスクされる。レジスタは 32bit を保つ。

バスのコールバックは `throw new BusError(addr, isWrite)` で `/BERR` を主張できる。
コアはそれを group 0 のスタックフレーム付きバスエラー例外に変換する。

```js
const mem = new Uint8Array(0x100000);
const bus = {
  read16: (a) => (mem[a] << 8) | mem[a + 1],
  write16: (a, v) => { mem[a] = v >> 8; mem[a + 1] = v & 0xff; },
};
const cpu = new M68000(bus);   // reset がアドレス0からSSP・4からPCを読む
```

`new M68000(bus)` はハードウェアリセットを行うので、コンストラクタの時点で
バスが応答できる必要がある。ROM を後からマップする機種は、マップ後に
`cpu.reset()` をもう一度呼べばよい。

### レジスタ

`cpu.d` / `cpu.a` は `Uint32Array(8)`。`a[7]` は常に**現在アクティブな**スタック
ポインタで、`cpu.usp` / `cpu.ssp` はどちらのモードにいても論理的な値を返す
（書き込みも正しく振り分ける）。ステータスレジスタはフィールド（`sr_t`・`sr_s`・
`sr_ipm`・`fx`・`fn`・`fz`・`fv`・`fc`）としても
`getSR()`/`setSR()`/`getCCR()`/`setCCR()` としても見える。`setSR()` 経由で S ビットが
変われば、スタックポインタも入れ替わる。

### 割込

```js
cpu.setIRQ(4);       // IPL2..0 = 4 を主張
cpu.setIRQ(0);       // 解除
```

レベル1〜6はレベルセンシティブ：SR のマスクを超えていれば次の命令境界で受け付ける。
レベル7は NMI でエッジトリガなので、ラインを上げっぱなしにするデバイスがあっても
無限ループしない。受け付ける際、`bus.irqAck(level)` があれば呼ぶ。ベクタ番号を
返せばそれを使い、何も返さない（または負値）なら「デバイスが VPA を主張した」と
みなして `24 + level` にオートベクタする。マスクは実チップ同様その割込のレベルまで
引き上げられる。

### 例外

68000 の例外は全部入っている：リセット、バスエラー、アドレスエラー、不正命令、
line-A/line-F エミュレータトラップ、ゼロ除算、CHK、TRAPV、privilege violation、
TRAP #0..15、トレース、そして7段のオートベクタ割込。ベクタ番号は `VEC` が export
している。

group 1/2 の例外は6バイトフレーム（SP に SR、SP+2 に PC）を積む。group 0
（バスエラー・アドレスエラー）は14バイトフレーム（special status word、
アクセスアドレス、命令レジスタ、SR、PC）を積む。**そのフレームを書いている最中に**
再びフォルトすると double bus fault で `cpu.halted` が立つ——実チップと同じ。

トレース例外は**次の** `step()` の先頭で、保留中の割込より先に受け付ける。
トレース対象の命令はまず最後まで走り、命令の中で T を書き換えても、
それが遡ってトレースを取り消したり発生させたりはしない。

### 68010 以降

68010 以降にしか無い命令——`RTD`・`MOVEC`・`MOVES`・`BKPT`・`MOVE from CCR`・
`EXTB.L`・68020 の long 乗除算・ビットフィールド——は不正命令ベクタに落ちる。
実 68000 がそうするからである。`MOVE from SR` はここでは**特権命令ではない**。
68000 では特権ではないから（特権にしたのは 68010）。

## スナップショット

```js
const s = cpu.snapshot();   // plain data、JSON で約350バイト
cpu.restore(s);
```

`snapshot()`/`restore()` は厳密な逆関数のペアで、これがホストの決定論的な巻き戻しを
成立させている：スナップショットを取り、先へ進め、戻し、同じ入力を流し直すと
同じ場所に着く。`getState()`/`setState()` は別名。`z80.js` に向けて書かれた
機種コードがそのまま読めるようにしてある。

**スナップショットには ROM もメモリも意図的に入れていない。** `demo/machine.html` は
1フレーム1枚のリングバッファを持つので、ここに入れた不変バイトはそのまま
「巻き戻せる秒数」を削る。RAM は機種側が自分でスナップショットする。

## サイクル計上

`step()` は M68000 User's Manual の Appendix E のタイミング表に従ってクロック数を
返す：命令ごとの基本時間＋実効アドレス計算時間、MOVE だけは転送元/転送先を分けた
別表。命令の**内部**はサイクルステップしない——1回の `step()` が1命令まるごと。
データ依存の命令はきちんとモデル化してある：

- `MULU` は 38 ＋ ソースワードの立っているビット1つにつき2。
- `MULS` は 38 ＋ `src << 1` の 0→1 / 1→0 遷移1つにつき2（マイクロコードが
  Booth エンコードするため）。
- `DIVU` / `DIVS` はマイクロコードの復元法除算ループを回して実際の仕事量を数える。

## 検証

ここが本番。このリポジトリが PC-8801 を M88 とバイト単位で一致させたときの手法
（`docs/m88-comparison.ja.md`、`m88ref/`）をそのまま使う：参照実装を用意し、
状態を1命令ずつ突き合わせ、「ゲームが固まる」から推測するのではなく
**最初に食い違った1件**を追う。

ここでの神託は **[SingleStepTests/m68000](https://github.com/SingleStepTests/m68000)**
——MAME のマイクロコード実装 68000 から生成された、1命令分の状態遷移 317,500 件
（命令形式127種 × 各2,500件）。1件は「初期レジスタ/メモリ状態 → 1命令実行 →
期待される最終状態」＋サイクル数付きのバストランザクションログ。

### 再現手順

```sh
m68ktools/fetch-tests.sh                       # 約138MB を ./m68k-tests に取得
node m68ktools/run-sst.mjs --dir ./m68k-tests
```

テストデータは**コミットしていない**（サイズが大きく、上流で再生成されるため）。
主なフラグ：

| フラグ | 効果 |
|---|---|
| `--only <regex>` | 命令ファイル名で絞り込む |
| `--limit <n>` | 各ファイル先頭n件だけ |
| `--cycles` | クロック数も比較する |
| `--no-aerr` | アドレスエラーで中断した命令のケースを除外する |
| `--strict-aerr` | group 0 フレームの「予測不能」なPCフィールドも一致を要求する |
| `--verbose` | 失敗ケースとサイクル差分のヒストグラムを表示 |
| `--json` | 機械可読サマリ |

上流の `.json.bin` コンテナのデコーダは `m68ktools/sst.mjs` にあるので、Python は不要。

### 結果

| 走行 | 結果 |
|---|---|
| 状態のみ・アドレスエラーのケースを除外（`--no-aerr`） | **261,894 / 261,894 — 100 %** |
| 状態のみ・全件 | 314,174 / 317,500 — 98.95 % |
| 状態＋サイクル・アドレスエラーのケースを除外 | 259,031 / 261,894 — 98.91 % |

### 既知の穴（隠さずに書く）

**1. group 0 スタックフレームの PC フィールド（3,326件・約1%）。**
アドレスエラーで命令が中断したとき 68000 が積む PC は、User's Manual 自身が
「予測不能（命令の先頭から2〜6バイト先、プリフェッチがどこまで進んだかによる）」と
書いているもの。参照実装と完全一致させるには参照実装のプリフェッチ・マイクロコードを
再現するしかない。ここでは典型例を積んでいる（read フォルトならオペコードの1ワード先、
write なら2ワード先、分岐のプリフェッチが落ちた場合は分岐先そのもの）。
テストランナーはこれを隠さず `aerr-frame-PC` として別カウントする。
`--strict-aerr` を付ければ落ちる。フレームのそれ以外——special status word
（オペコード由来の上位ビットを含む）・フォルトアドレス・ファンクションコード・
命令レジスタ・SR・ハンドラの PC・スタックポインタ——は厳密に比較して一致している。

**2. アドレスエラー後のマイクロ順序（残りの1%）。**
既に失敗した命令の例外フレームからしか見えない細部がいくつかある：long オペランドの
どちらの半分に先に触ったか、アドレスレジスタの書き戻しがコミット済みだったか、
参照実装が命令レジスタにどのワードをプリフェッチ済みだったか。
文書化されている規則（`-(An)` 経由の long は下位ワード先行、byte/word のポインタ更新は
フォルトしてもコミットされたままだが long はされない、read-modify-write の宛先は
ポインタを先にコミットし上位ワード先行）はモデル化してあり大半は一致するが、
全マイクロコード経路までは合わせていない。**68000 は group 0 フレームからそもそも
復帰できない**ので、実ソフトからこれが観測されることはない。

**3. サイクル数（フォルトしない261,894件のうち2,863件・1.1%）。**

| 命令 | 状況 |
|---|---|
| `TAS`（メモリ） | 2,108件。マニュアル通り 14+ea を採用、参照実装は 10+ea。上流の README 自身が「TAS の特殊な5サイクル read-modify-write タイミングを正しく扱えていない」と明記しているので、ここはマニュアルを採る。 |
| `DIVS` | 353件、2または4のずれ。除算タイミングモデルの符号補正項が正の除数で厳密でない。`DIVU` は完全一致。 |
| `CHK`（トラップ時） | 402件。こちらは 38+ea、参照実装は「Dn &lt; 0」ケースの約半分で 40。区別する条件を特定できなかった。 |

これ以外——残り124命令ファイル全部——はサイクル単位で一致している。

**4. `TRAPV` と `TAS` 全般。** 上流はこの2つを「未検証」としている。
こちらの `TRAPV` は2,500件全部通る。`TAS` は状態は通り、上記の通りタイミングだけが違う。

## 決定論

`test-m68000.mjs` は同じプログラムを2回走らせて状態とメモリがビット単位で一致する
ことを確認し、途中でスナップショットを取り、先へ進め、戻し、流し直して結果が
収束することを確認する。さらにスナップショットが JSON を往復できること・
`schemaVersion` を持つこと・typed array を含まないこと・512バイト未満に収まることも
アサートしている。

## レイヤ

```
m68000.js        pure な CPU — バスだけを知り、それ以外を知らない
   ↑
機種ポート        メガドライブ / X68000：アドレスマップを組み、step() を回し、
                 setIRQ() を上げ、自分の RAM は自分の snapshot で持つ
```

依存の矢印は常に一方向。コアは何も import しない。
