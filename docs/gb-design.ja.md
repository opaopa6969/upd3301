# ゲームボーイ / ゲームボーイカラー — 設計

PC-8001・PC-8801・ファミコンの隣に、ゲームボーイとゲームボーイカラーを*機種*として足す。ファミコン（[docs/nes-design.ja.md](./nes-design.ja.md)）と同じで、狙いは「エミュレータをもう一本」ではない。`demo/machine.html` のホストは、機種依存を一切含まない `snapshot()` / `restore()` 契約の上に、決定論的な早送り・巻き戻し・ジョグシャトルを既に実装している。**契約を満たせば時間操作はタダで付いてくる。**

この機種が他と決定的に違うのはハードウェアではない。**検証コーパスが再配布できる**ことだ。PC-8801 は誰も配れない BIOS を要求するので、CI ではテストが skip され、「検証済み」は「作者の手元で一度やった」を意味していた。ゲームボーイの 256 バイトのブートROMはロゴをスクロールして自分を外すだけ——カートリッジだけで完結する——そして、この機種のテストROM文化は MIT ライセンスのスイートを産んだ。だから `gbroms/` に mooneye 103本と dmg-acid2 を置いてある（gzip 済みで 1.2MB）。**CI はクリーンな checkout でそれを本当に実行する。** これが issue #42 のゴールで、数字は §10 にある。

## 1. 契約（suite-contract）

- 純JS・依存ゼロ。DOM も `three` も無し、**`Math.random` 禁止**。ノイズチャンネルの乱数は LFSR＝ハードウェアであり、スナップショットに入る。
- 決定論: 同じカートリッジ＋同じ入力列＋同じステップ数 → **ビット一致の状態**。巻き戻しはスナップショットを復元して入力を再生することで動くので、非決定性は絵を劣化させるのではなく、時間操作機能を一度に全部壊す。
- 出力は plain data ＋ `schemaVersion`。
- 依存は一方向。`sm83.js` はゲームボーイを知らない（バスを受け取って実行するだけ）。`gbppu.js` は CPU を知らない。`gbmbc.js` はどちらも知らない。`machinegb.js` が輪を閉じる coordinator。
- テストは `node --test`、headless、決定論テストを含む。**ROM の無い clone でも通る**: 同梱コーパスはコミットしてあり、同梱していない唯一のスイート（blargg — §10）は skip する。

## 3. `gbmbc.js` — カートリッジ

`.gb` はメモリイメージではなく*ボード*。本体には 8KB のワークRAMと 8KB のVRAMがあるだけで、ストレージは無い。プログラム・セーブRAM・バンク切替、そして一部の系統では時計まで、全部カートリッジ側にある。だから `$0147` がボード名で、registry がそれをオブジェクトにする——`nesmapper.js` が iNES のマッパー番号にやっているのと同じ。未実装のボードは例外ではなく普通の答え（`tryCreateMbc()` → `{ ok: false }`）。どんな ROM ライブラリにも誰も実装していないボードは入っている。

実装済み: **MBC5**（2本の素直なレジスタに9ビットのバンク、穴なし。カラーのライブラリの大半）、**MBC3**（+RTC）、**MBC1**（ややこしいやつ）、**MBC2**（チップ内蔵の512ニブルRAM）、**HuC1**（MBC1互換）、**なし**。未実装: MBC6・MBC7・MMM01・HuC3・ポケットカメラ・TAMA5。

名前を付けておく判断が2つ。

**MBC1 のモードフラグと穴。** `$4000` の2ビットレジスタは、モード0では上位ROMバンクビット、モード1では RAM バンクになる。しかもモード1では `$0000-$3FFF` 窓にも効く——1MBのカートリッジが後半に手を届かせるのはこれ。さらに `$4000` でバンク `$00` を選ぶと `$01` が読め、上位ビットが絡むと `$20`・`$40`・`$60` も同じ。大きい MBC1 カートリッジは4バンクが到達不能で、ゲームはそれ前提で作られている。注意すべきは、**上位ビットは ROM がその配線を持つ大きさのときしか意味を持たない**こと: 512KB のカートリッジではバンク `$25` は `$05` を選ぶ。これはバグではなく「線が無い」という事実。（これを忘れたテストが、この branch が引き継いだ5件の失敗の1件目 — §12。）

**RTC は `Date.now()` を呼ばない。** MBC3 の時計は、ゲームボーイのエミュレータがホスト時計を読みたくなる唯一の場所で、読んだ瞬間にこのリポジトリ全体が立っている性質が壊れる。だから*エミュレート時間*のサイクルで進み、他のレジスタと同じようにスナップショットに入り、時間を巻き戻すとカートリッジの時計も一緒に巻き戻る。実際の日付を入れたい人は `setRtcFromDate()` で一度だけ設定する——環境からにじみ込むのではなく、明示的な入力として。

## 4. `sm83.js` — CPU、そして `z80.js` から派生させなかった理由

**issue #42 が理由の明記を求めた設計判断なので、全部書く。** SM83 は普通「Z80 から色々抜いたもの」と説明され、レジスタ名も一致し、`z80.js` はすぐそこにある。それでも却下した。理由は2つ。

**構造。** `z80.js` は*命令アトミック*で、`step()` は1命令をバスに対して丸ごと実行し、表から T ステート数を返す。PC-8801 では正しい形（命令の途中を観測する者がいない）。ここでは間違った形になる。ゲームボーイのテストスイートは、**アクセスが命令の何 M サイクル目に起きるか**を測るからだ。mooneye の `push_timing`・`call_timing`・`oam_dma_timing`・`timer/` 群は全部、1命令の2つのバスサイクルの*あいだ*に PPU やタイマの状態を変えて、その結果を読む。だから `sm83.js` は `m6502.js` と同じ書き方をしている（nes-design §4）: **サイクル表が無い**。バスアクセス1回がちょうど1 Mサイクルで、内部遅延は明示的な `_idle()`。そして machine のクロックは *CPU のバスの内側から*進む:

```js
this.cpu = new SM83({
  read:  (a)    => { this._tickM(); return this._read(a); },
  write: (a, v) => { this._tickM(); this._write(a, v); },
  tick:  ()     => this._tickM(),
  ...
});
```

サイクル数はこれで勝手に正しくなり、もっと有用なことに、**PPU・タイマ・DMA が実機と同じ順序でアクセスを見る**。`$FF46` への書き込みは本物の M サイクルで OAM DMA を始め、`$FF41` の読み出しはそのドットで PPU が見せている STAT を見る。catch-up ロジックはどこにも要らない。

**巻き添えの範囲。** `z80.js` は PC-8801 の CPU で、このリポジトリの出発点そのもの。`test-z80.mjs` がその回帰網だ。共通基底クラスにすると、ゲームボーイのタイミング修正が毎回その網の1編集手前に来る。しかも得られるものは見た目より小さい: 裏レジスタ無し、IX/IY 無し、ED/DD/FD プレフィクス無し、IN/OUT 無し、フラグは6本ではなく4本（S も P/V も無く、F の下位ニブルは**物理的に存在しない**——`POP AF` で `$FFFF` を入れると `$F0` が読める）、DAA が違う、16bit ADD のフラグが違う、存在しない命令が11個、Z80 に無かった命令が12個。実際に共有できるのは ALU の十数行だけ。

**結論: 独立コア、`m6502.js` と同じ形。** 569行。代償は CPU をもう1本保守すること、見返りは `blargg/cpu_instrs` と `blargg/instr_timing` が両方通ること（§10）と、`z80.js` に一切触らずに済んだこと。

名前を付けるべき挙動が3つ。どれもテスト1件に対応する。

- **EI ラッチ。** 微妙なのは持続時間ではなく*どこで解決されるか*: 次の命令の割込チェックの後、その命令の実行の前。だから `EI` の次の命令は必ず走り、`EI; DI` は何も通さず、`EI` を18回並べても割込は2つ目の後で入る（mooneye `ei_sequence` は push された戻り番地をバイト単位で固定する）。
- **HALT バグ。** IME=0 で割込が既に立っているときの `HALT` は停止せず、代わりに次のバイトが2回実行される（PC が1回インクリメントされ損なう）。
- **`ie_push`。** 割込ベクタは **PC の上位バイトを push した後に**決まる。`SP = $0000` だとその push は `$FFFF`＝IE レジスタそのものに落ち、ベクタは今書いた値から決まる——結果、行き先を失って `$0000` に着地しうる。

配線されていない11個のオペコードは、例外を投げるのでも NOP でもなく **CPU をロックする**（`jammed` フラグ）。そこに到達した ROM は脱線した ROM で、ホストはそれを知りたい。

## 5. `gbppu.js` — 絵

**モードタイミングはドット精度、描画はライン単位。** これは別々の主張で、分けたのは意図的。

実機はピクセルFIFOで走査線を組み立てる: タイルマップを歩く fetcher が2本のシフトレジスタを養い、オブジェクトを差し込むあいだ止まる。FIFO をエミュレートすると最後の数%（ライン途中のレジスタ書き込み、mealybug 系テスト）が取れるが、コアはずっと大きく遅くなる。dmg-acid2 の README 自身が「ライン単位のレンダラで十分」と言っており、*絵*が正しいかを決めるのはそのテストだ。だからオブジェクトは mode 2 → mode 3 の境界でラッチし、ラインは mode 3 → mode 0 の境界で一気に塗る。

一方*クロック*はドットで走る。1ライン456ドット、154ライン、そしてモード境界は動く: 背景がタイル境界からずれていると mode 3 は伸び（`+ SCX & 7`）、ウィンドウが開くとまた伸び（`+6`）、ライン上のオブジェクトごとにまた伸びる。ゲームはこの境界をラスタ時計として使い、mooneye の `ppu/` 群はドット単位で測るので、ピクセルは近似でもここは真面目にやってある。

**STAT レジスタはモードより 1 M サイクル遅れる。** この1点が、そうしないと互いに矛盾する mooneye の3件を同時に成立させる: `hblank_ly_scx_timing` は「mode 0 は本当にドット252で始まる」と言い、`intr_2_0_timing` は「mode 2 の割込はドット0」と言い、`intr_2_mode0_timing` は「でも STAT を*読む*と mode 0 はドット256まで見えない」と言う。3番目を境界の移動で満たそうとすると1・2番目のどちらかが壊れる。境界が正しく、レジスタが遅い。VRAM/OAM のロックも遅れたモードに従う（`intr_2_oam_ok_timing` が `intr_2_mode0_timing` と同じ答えを出すから）。

**STAT 割込は「4つのソース」ではなく「1本のORの立ち上がり」。** 実機は4条件を1本の線にORし、その線の立ち上がりでだけ割込が出る。結果は直感に反していて、しかも観測できる: HBlank と OAM を**両方**有効にすると、片方だけのときから素直に想像する数より**少ない**割込しか出ない。あるラインの HBlank が次のラインの OAM スロットに切れ目なく繋がり、線が落ちる隙間が無いからだ。コールドスタートから1フレーム測ると: HBlank だけ 143、OAM だけ 145、**両方で 144**——288 ではない。これが mooneye の `stat_irq_blocking` で、`test-gb.mjs` は3つの数字すべてを assert する。

間違えやすくて各1件のテストになっているものがあと2つ。**ライン153** は LY が4ドットだけ153を返し、残りは0を返す（ゲームは LYC=0 でフレーム最上部の割込を取る）。**LY=LYC ビットは読み出し時計算ではなくラッチ**なので、LCD を切ると凍り、切っているあいだに LYC を変えても何も起きない。

出力は `Uint16Array`: DMG では階調インデックス 0-3、カラーでは 15bit BGR555。DMG の4階調を `$FF/$AA/$55/$00` と書くのは、dmg-acid2 の README がその値を要求しているからで、これが比較を許容誤差なしのバイト一致にできる理由。

## 6. `gbapu.js` — 音

4チャンネルは4つの発振器ではなく、1本の 512Hz ハートビートを共有する4つの*カウンタ*。しかもそのハートビートはタイマと同じ DIV レジスタから来ている。だから `$FF04` を書いて DIV をリセットすると**音楽の位相が変わる**。よってフレームシーケンサは自前の分周器を持たず、**machine が DIV ビットの立ち下がりで叩く**（内部カウンタのビット12、倍速ではビット13。どちらでも 512Hz）。「DIV のビット4」を内部カウンタに対して額面通り取るとシーケンサが256倍速く回り、音としては特に何も起きないまま、長さカウンタ系のテストが全部静かに落ちる。

チャンネルタイマは T サイクルで厳密。ミキサは厳密ではない: 実機のチャンネルごとの DAC は抵抗ラダーで、左右の音量調整を持つアナログミキサに入り、チャンネルを音の途中で切ったときに「チャージ」が聞こえるハイパスが付いている。**ハイパスはモデル化してある**（プツッと言うか言わないかの差）。残りは線形。

サンプルのリングは**出力**でスナップショットに入らない。ただしリサンプラの位相とハイパスのメモリは入る。これが、復元後のサンプル列が波形の続きになり、ticking しない理由。

## 7. `machinegb.js` — 機種

coordinator は、どのチップにも属さないものを持つ: タイマ、ジョイパッド、シリアル、OAM DMA、そしてカラーの2つの HDMA エンジン。

**タイマは独立した分周器ではなく、分周器の1ビット。** TAC のクロック選択は DIV の裏にある16bitカウンタの「どのビットか」を指し、TIMA はそのビットの**立ち下がり**を数える。こうモデル化することが `timer/` 群を丸ごと通す鍵になる: `$FF04` を書くとカウンタがリセットされ、その瞬間に選択ビットが1だったら、そのリセットが**本物の立ち下がり**で TIMA が増える。オーバーフロー後の4サイクルのリロード窓もモデル化してある——そのあいだ TIMA は0を返し、TIMA への書き込みはリロードごと取り消し、TMA への書き込みが新しい値になり、リロードサイクルそのものでの書き込みは無視される。

**OAM DMA が奪うのはメモリマップではなくバス1本。** 本体にはバスが2本ある: 外部（カートリッジ・ワークRAM・そのエコー）と映像（VRAM）。DMA は転送元が乗っている方＋OAM を奪い、もう一方は放っておく。`$FF00` 未満を全部塞ぐ——よくある近道——と、mooneye のタイミングテストは `$FF`（= `RST 38`）を実行してハングする。彼らは `$8000` からの DMA 中に `$FDFE` のエコーRAM から `JP nn` を実行するように、わざと組んであるからだ。

**ブートROMは無く、それがこの機種をここに入れた理由そのもの。** 256バイトはロゴをスクロールし、ヘッダを検査し、自分をマップから外すだけ。`$0100` 以降はそれを必要としない。だから machine はブートROMが残したはずのレジスタで `$0100` から始まる（`sm83.js` の `reset()` と `_bootIo()`）。DIV カウンタも含む——これは恣意的に見えて違う: ブートROMのサイクル数は決まっているので、カートリッジが制御を得た瞬間の分周器の値は既知で、mooneye の `boot_div` はそれを読む。実物のブートROMを渡すこともでき（`{ bootRom }`）、`$FF50` が実機どおりにアンマップする。

`stepFrame()` はラスタが vblank の先頭に達するまで走る。その時点で絵は完成しており、ゲームの vblank ハンドラは*次の* `stepFrame()` の頭で走るので、ここで撮ったスナップショットは「完成した絵」と「これから知らされるプログラム」を持つ——ファミコンと同じ境界。**リセット後の最初の `stepFrame()` だけ短い**（17,556 ではなく 16,418 Mサイクル）。machine が LY=0 から始まるので最初のフレームだけ154ラインではなく144ラインになるため。以降は毎回まるまる1周で、60フレームの合計は 60×17,556 に対して命令1個ぶん以内に収まる。

## 8. ホスト統合（`demo/machine.html`）

`ファミコン` の隣に `ゲームボーイ` の起動モード、`.gb`/`.gbc` のファイルピッカー、そして **GB / GBC のセレクタ**（`auto` はカートリッジの CGB フラグを信じる。逆に強制できるのは意味がある——カラー対応 ROM は DMG でも動くので、それを見られるのは価値がある）。BIOS のピッカーは無い。選ぶものが無いから。

残りは全部すでにあった。ホストが「これは何クラスか」ではなく「この機種は何ができるか」を訊く作りだからだ。`render({ indexed: true, analog: true })` が共有のフォスファーパイプラインを養い（インデックスは粗いGRB縮約、`drive` が本当の色を運ぶ。カラーの32768色ではこれが効く）、`renderAudio()` がオーディオポンプを養い、`stepFrame()`/`snapshot()`/`restore()` が早送り・巻き戻し・ジョグシャトルをそのまま与える。入力はファミコンのキーレイアウトにゲームボーイのビット番号を当てたもの——同じ8個の操作系なので、プレイヤーが2つ目のキーボードを覚える必要は無い——ただし machine は*読まれる*のではなく*告げられる*（`setPad()`）。線が下がるとジョイパッド割込が要求され、`STOP` した CPU が起きるから。

デモでは DMG の画面を**緑**で出す（階調をあの豆スープ色のLCDに写す）。一方 `toRgb()` は dmg-acid2 が比較する中立グレーのまま。デモは実物に似せ、テストは数字を比べる。

**未検証:** ブラウザでの実際の表示と、実際の音。上に書いたことは全部 headless で検証してある（フレームバッファ、snapshot/restore、`test-gb.mjs` で再現したホストの搬送ループ）が、フォスファー/ブラウン管シミュレーションを通って実キャンバスに届くピクセルと、実スピーカーに届くサンプルは**視覚的・聴覚的に未検証**。

## 9. スナップショット方針 — なぜここでは絵が*状態*なのか

`demo/machine.html` はスナップショットを最大1000枚リングに持ち、150MB 付近に収まるよう間隔を自動調整する。つまり**スナップショットが大きい＝巻き戻せる時間が短い**。いつもの規則はそのまま: 不変データ（カートリッジROM）は参照で持ち、絶対にコピーしない。一度も書かれていないセーブRAMは丸ごと省く（`null`。復元時はゼロ埋め＝「一度も書かれていない」の意味そのもの）。全部 plain data なので `restore()` は既存オブジェクトに書き込む。

**ただしフレームバッファはスナップショットに入れてある。他のどの機種でも入れていないのに。** ここがこの設計が `machinenes.js` から外れる唯一の場所なので、1段落を割く。

Seta の機種は自分のファイルの契約テストを全部通したうえで、ホストが巻き戻したときに 250回中61回、違うフレームに着地した。絵が状態ではなく履歴の関数だったからだ。同じ罠が形を変えてここにもある。完成したゲームボーイのフレームは、ラスタが横切った瞬間のレジスタで塗られた144本のラインを持つ。これは*さっき起きたフレームの記録*であり、どれだけレジスタ状態があっても再計算できない。ホストはスナップショットを復元してから描く——ジョグシャトルを握っているあいだ、毎アニメーションフレームで文字どおりこれが起きる——ので、絵の無いスナップショットは「エミュレータが最後に走らせたフレーム」を画面に出すことになる。

これは机上の話ではなかった。それを捕まえるテスト（`dmg-acid2 also exercises the rewind ring on a real ROM`）は**落ちた状態で**引き継がれた。120フレームのリングのスロット0と7が、フレーム120の絵を持って帰ってきていた。他のどのテストも気づかなかったのは、もう一方の巻き戻しテストが「タイルデータを一切アップロードしない＝一様な画面を描く ROM」を回していて、比較が毎回「同じ真っ白同士」だったから。両方直した: 絵は旅をするようになり、そのテストは画面が実際に動く ROM を回すようになった（§12）。

DMG の1ピクセルは2ビットなので、絵は4ピクセル/バイトに詰めて **5,760バイト**。カラーの1ピクセルは本物の15bit色で、後からパレット引きでは再構成できない（ゲームが後のラインでパレットを書き換えているかもしれない）ので、そちらは生のまま 46,080バイト。

`snapSize()`（型付き配列はバイト数、数値は8、オブジェクトは少額）で、フレーム境界で撮ったスナップショット:

### 決定論とホストの搬送系

ここの全機種で見る4つの性質に、Seta の失敗が足した2つ:

1. 同じカートリッジを2回走らせる → スナップショットも**絵も**一致。
2. snapshot → 先に進める → restore → 再生 → スナップショットも絵も一致。
3. 同じことを、**再生の途中に入力が来る**状態で（スナップショットの後に押されたジョイパッド割込）。
4. ×4 早送りが ×1 の到達点にちょうど着く。
5. **ホストの巻き戻しリングの再生。** 画面が*動く* ROM を600フレーム回した100スロットを、逆順（シャトルが実際に動く向き）に復元し、フレーム番号と全ピクセルを比較。0/100 不一致。
6. **同じことを実ROMで。** dmg-acid2 の120スロット全部を逆順に復元し、さらに復元したスロットから1フレーム進めて次のスロットの絵になることも確認（ホストの「プレビュー地点から再開」がこれ）。

## 11. まだ無いもの

プレイヤーが先に気づく順に。

- **ピクセルFIFO。** 描画がライン単位なので、SCX・LCDC・パレットへの*ライン途中の*書き込みは、次のピクセルではなく次のラインから効く。`ppu/intr_2_mode0_timing_sprites`（オブジェクトごとの mode 3 の伸びは、無い FIFO の近似）と mealybug 系全部の代償。ライン途中の書き込みで効果を出すゲーム（水面の揺らぎなど）は正しく出ない。
- **LCD オンのタイミング。** フレーム途中で LCD を入れる挙動は粗い: 最初のフレームを捨て、最初のラインで mode 2 の場所を mode 0 が走る——方向は合っているが、ドット精度ではない。`ppu/lcdon_timing-GS`・`ppu/lcdon_write_timing-GS` の代償。
- **`ppu/stat_lyc_onoff`。** LY=LYC ビットが LCD の off/on をまたいでラッチされる部分は合っているが、比較が再開する正確なドットが残っている。
- **OAM DMA の起動。** `oam_dma_start` と `oam_dma/reg_read` は DMA の最初の M サイクルと、DMA 中に `$FF46` が何を返すかを測る。遅延は平坦な1 Mサイクルとしてモデル化している。
- **OAM 破壊バグ。** DMG で mode 2 中に OAM を指す16bitレジスタを増減させると OAM の1行が壊れる。まったくモデル化していない（blargg `oam_bug` 2/8）。ゲームが避けるハードウェアの欠陥なので依存しているものは無いが、テストは正直に落ちる。
- **波形チャンネルのアクセス窓。** チャンネル3が鳴っているあいだ波形RAMはそれのもので、CPU はフェッチ直後の2サイクル窓を除いて `$FF` を見る。窓自体はモデル化してあるが、開く正確なサイクルは合っていない（blargg `dmg_sound` 09/10/12、`cgb_sound` 08/09/11/12）。可聴なものは何も依存していない。
- **APU 電源断の差。** ここでは APU を落としても長さカウンタは消えない（DMG の挙動）。カラーは消す。
- **MBC1 マルチカート。** 普通の 8Mb MBC1 カートリッジとは ROM 内容のヒューリスティックで区別するが、未実装（`mbc1/multicart_rom_8Mb`）。
- **ボード。** MBC6・MBC7（加速度センサ）・MMM01・HuC3・ポケットカメラ・TAMA5。どれもクラッシュせず、名前付きで `{ ok: false }` を返す。
- **シリアル。** 何も繋がっていない: 送ったバイトはどこにも行かず、`$FF` が返り、割込は時刻どおりに出る。blargg のスイート（これで結果を印字する）とポーリングするゲームにはこれで足りる。通信ケーブルはエミュレートしていない。`serial/boot_sclk_align-dmgABCmgb` はシリアルクロックの位相をブートROMの終了に対して測るので、実物のブートROMが要る。
- **スーパーゲームボーイ。** 枠・パレットコマンド・SNES側、どれも無い。SGB対応カートリッジはただの DMG カートリッジとして動く（実機のゲームボーイに挿したときと同じ）。
- **実ゲーム。** dmg-acid2 と mooneye 103本はライブラリではない。**マトリクスが通ることは、市販タイトルが動く証拠にならない。** ファミコン側は issue #40 でこれを2度踏んだ。ここでは市販カートリッジを1本も走らせていない。コミットできるものが無く、手元にも無かったから。

## 12. この branch が引き継いだ5件の失敗

第1段はエージェントが走行中に落ちて終わり、3,730行が「51件中46件 pass」でコミットされていた。「テストの方が間違っていた」は証拠が要る主張なので、記録しておく。

| 落ちていたもの | 原因 | 直し方 |
|---|---|---|
| `gbmbc: MBC1 has the bank-0 hole and the mode flag` | **テスト。** 512KB のカートリッジを作ってバンク `$25` が存在すると期待していた。32バンクの ROM では上位バンクビットに駆動する配線が無いので `$25` は `$05` を選ぶ——ボードはそのとおりに動いていた。 | テストを 1MB（64バンク）に変更。モードフラグが観測できる最小サイズ。mooneye の `mbc1/` 群は元から全部通っていた。 |
| `gbppu: the STAT interrupt is the rising edge of an OR` | **テスト。** HBlank と OAM を両方有効にした1ラインで割込2回を期待していた——それはこのファイルが否定するために存在する「4ソース」の答え。1本の線なら1回。 | 1フレームを、各ソース単独と両方で数える形に書き直した: 143・145・**144**。厳密に強くなり、タイトルが主張していることを実際に示すようになった。 |
| `machinegb: a frame is the right number of cycles` | **テスト。** *最初の* `stepFrame()` を測っていた。machine が LY=0 から始まるので、それは154ラインではなく144ライン。 | 1フレーム空回ししてから、各フレームが 17,556 の命令1個ぶん以内であること、60フレームの合計が 60×17,556 であることを assert。 |
| `gbapu: state round-trips and the samples continue` | **テスト。** 「走行全体の最初の64サンプル」と「スナップショット以降の最初の64サンプル」を比べていた。`setState()` は未回収のリングを意図的に捨てる（復元が放棄した未来のものだから）ので、居残った方も同じ地点まで排出しないと合わない。 | 比較前に排出する。 |
| `dmg-acid2 also exercises the rewind ring on a real ROM` | **エミュレータ。** フレームバッファがスナップショットに入っていなかったので、`restore()` + `render()` は「エミュレータが最後に走らせたフレーム」を返していた。スロット0と7がフレーム120として返ってきていた。 | 絵を状態にした（§9）。もう一方の巻き戻しテストも一様な画面の ROM を回していて捕まえようが無かったので、スクロールする ROM に差し替えた。 |
