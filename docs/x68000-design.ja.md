# X68000

シャープ X68000 をこのリポジトリの「機種」として実装したもの。10MHz の 68000、
ソフトウェアがドット単位でプログラムする CRTC、1つの 512KB を4通りの見え方で共有する
グラフィック4面、実体は4枚のビットプレーンであるテキスト面、128枚のスプライト、
8ch の FM 音源と ADPCM、そしてボード上の全割り込みを握る MFP。

`machine88.js` / `machinenes.js` / `machinemd.js` と**同じ契約**
（`stepFrame()` / `frame` / `snapshot()` / `restore()` / `schemaVersion`）を満たすので、
`demo/machine.html` は X68000 のことを何も知らないまま早送り・巻き戻し・
ジョグシャトルを提供する。

## 1. 何があるか

| ファイル | 中身 |
|---|---|

| `x68crtc.js` | CRTC。R00-R23、そこから導かれる画面サイズ、ラスタコピー、高速クリア |
| `x68video.js` | 4通りのグラフィックVRAM、テキスト面、パレット、ビデオコントローラ、スプライト、BG2面、優先順位の解決 |
| `mc68901.js` | MFP。16本の割り込み源、4本のタイマ、GPIP、キーボードのシリアル受信 |
| `hd63450.js` | DMAコントローラ。4チャンネル、チェイン転送、8bit/16bitデバイス |
| `x68fdd.js` | `.XDF`/`.IMG`・`.DIM`・`.D88` の読み込みと、FDCのドライブ側 |
| `ym2151.js` | OPM。8ch×4オペレータ、LFO、ノイズ、ステレオ、タイマ2本 |
| `msm6258.js` | OKI の ADPCM |
| `test-x68.mjs` | `node --test` 46件。**ROM不要** — すべて自前のIPLを組み立てて走る |

## 2. メモリマップ

```
$000000-$BFFFFF  RAM。搭載量を超えるアクセスはバスエラー
$C00000-$DFFFFF  グラフィックVRAM。見え方は CRTC R20 の上位バイトが決める
$E00000-$E7FFFF  テキストVRAM。1024x1024 のビットプレーン4枚、各128KB
$E80000-$E81FFF  CRTC
$E82000-$E823FF  パレット。グラフィック256本＋テキスト/スプライト256本
$E82400/500/600  ビデオコントローラの3レジスタ
$E84000-$E85FFF  DMAC
$E86000-$E87FFF  エリアセット（受けて捨てる）
$E88000-$E89FFF  MFP
$E8A000-$E8BFFF  RTC
$E8C000-$E8DFFF  プリンタ（受けて捨てる）
$E8E000-$E8FFFF  システムポート
$E90000-$E91FFF  YM2151
$E92000-$E93FFF  MSM6258
$E94000-$E95FFF  FDCとドライブ制御
$E96000-$E97FFF  SASI（0を返す）
$E98000-$E99FFF  SCC（$FFを返す）
$E9A000-$E9BFFF  8255。ジョイスティック2ポートとADPCMのクロック選択
$E9C000-$E9DFFF  I/O割り込みコントローラ
$EB0000-$EBFFFF  スプライトレジスタ、BG制御、PCG、BGテキスト2面
$ED0000-$EDFFFF  SRAM 16KB（ミラー）
$F00000-$FBFFFF  CGROM
$FC0000-$FFFFFF  IPL ROM（下半分はミラー。SASI機と同じ）
```

**I/O ブロックへのワードアクセスは、上位バイト→下位バイトの2回のバイトアクセス**にする。
ここには本当に16bit幅のもの（CRTCの全レジスタ、パレット、DMACのカウンタ）と、
バスの奇数側にぶら下がった8bit部品（MFP、FDC。偶数バイトは無視する）が同居している。
バイトに分解すれば両方が正しく動く。ブロック全体を「奇数バイトだけ答える8bit」として
扱うと**CRTCレジスタの上位バイトが全部消える**。症状は「起動して走るのに画面設定を一度も
しない機械」で、これを見つけるのに時間を使った。

## 3. リセット — 3命令のあいだだけROMが0番地にいる

68000 はリセット時に $000000 からSSP、$000004 からPCを読む。X68000 はそこがRAMで
ROM は $FE0000 にあるので、アドレスデコーダが**ROMの最後の64KBをマップの底に被せる**。
それを外すのが IPL の3命令目：

```
FF0010  MOVE  #$2700,SR
FF0014  LEA   $2000.L,A7
FF0016  RESET            <- ここでオーバレイが消える
```

`m68000.js` の `resetLine()` が `bootOverlay` を落とす。そこまで低位メモリには
一切触れていないし、あとから Human68k が出す `RESET` は既に消えているものを消すだけ。
`test-x68.mjs` が両方を検証している。

## 4. RAM量と、スナップショットの大きさ

この機種で一番効く設計判断なので、議論ではなく実測を置く。

Human68k 3.1 が起動しきったあとのスナップショット（KB）：

| 搭載RAM | スナップショット | RAM | 映像 | SRAM | OPM | その他 |
|---|---|---|---|---|---|---|
| **1MB（既定）** | **1564** | 1024 | 514 | 16 | 8 | 2 |
| 2MB | 2588 | 2048 | 514 | 16 | 8 | 2 |
| 12MB | 12828 | 12288 | 514 | 16 | 8 | 2 |

比較のために：ファミコンは約3KB、メガドライブは142KB。X68000 がファミコンの100倍を
超えるのは、**メインメモリと映像メモリという、どうやっても小さくならないものが2つある**から。

そこから3つ決めた。

**既定は1MB。** ACE/EXPERT の標準構成であり、世に出回っている `sram.dat` が宣言している
値でもあり、次のサイズに対してスナップショットが半分になる。多く要る人は `ram:` を渡す。

**映像メモリは「何か書かれてから初めて」コピーする。** グラフィックVRAMは512KB、
スプライト/PCG領域は32KBで、Human68k のプロンプトで止まっている機械はどちらにも
1バイトも書いていない。ダーティフラグは単調（falseに戻らない）なので、コピーの無い
スナップショットは「ここではまだ全部ゼロだった」を曖昧さなく意味し、復元時はゼロで埋める。
これで1枚あたり544KB浮き、2108KB だったものが1564KB になった。
`machinemd.js` がカートリッジのバックアップRAMでやっているのと同じ手。

**ホストの巻き戻しリングを「枚数」ではなく「バイト数」で切るようにした。** 従来は
「どの機種も状態はだいたい同じ大きさ」という前提で1000枚を上限にしていた。X68000 の
1000枚は1.5GBになる。`demo/machine.html` の `sizeRewindFor()` がセッション最初の
スナップショットを実測し、192MB の予算から枚数を出す：ファミコンとメガドライブは
約1000枚、X68000 は約125枚。既定の取得間隔だとこの機種の巻き戻しは約12秒（他機種は約100秒）。
短いが正直で、しかも**全機種で同じコード**が走る。

**あえてやっていないこと**：メインRAMのダーティページ追跡。効くのは確かだが（大半のフレームは
1MBのごく一部しか触らない）、`restore()` が「最後のフルスナップショットまでの鎖」に
依存することになり、ホストのリングは古いものを勝手に捨てる。このリポジトリの
スナップショットは**完全な状態か、さもなくば無**である。

## 5. 映像

### 4通りに見えるグラフィックメモリ

512KB のグラフィックRAMは常に「512x512 の16bitワード」。CRTC R20 の上位バイトが
「1ドットが何ビットか」を決め、それが $C00000 へのアドレスの意味を決める：

| R20上位 | 形 | アドレス演算 |
|---|---|---|
| 0 | 16色 512x512 が4面 | 奇数バイトのみ。ワード=`y*512+x`、ニブル=`page*4` |
| 0 かつ bit2 | 16色 1024x1024 が1面 | ワード=`(y&511)*512+(x&511)`、ニブル=`8*(y>>9)+4*(x>>9)` |
| 1 or 2 | 256色 512x512 が2面 | 奇数バイトのみ。ワード=`y*512+x`、バイト=`page*8` |
| 3、または bit3 | 65536色 512x512 が1面 | **ワードがそのまま色** |

16色/256色モードでは**ワードの偶数バイトは存在しない**。`MOVE.W` の上位バイトは
どこにも繋がっていないバス線に出て消え、下位バイトのニブルだけが書かれる。
両方受け付けるモデルは全ドットを2回書くので、画が横半分に潰れる。

256色モードにはもう一つ罠がある：**1バイトの上下ニブルが別々にスクロールする**
（下位は R12/R13、上位は R14/R15）。実体は「バイトを共有する4bitプレーン2枚」で、
静止画の下でカラーランプを流すのに使われる。

### テキスト面

1024x1024 のビットプレーン4枚（各128KB）で、1ドット4bitの色番号を組み立てる。
R21 の2ビットがこれを速くする：「同時アクセス」は1回のバイト書き込みを R21 が選んだ
全プレーンに配り、R23 の**マスク**はバイトのどのビットが生き残るかを言う
（マスクビット1＝古い方を残す）。両方使うと `MOVE` 一発で4色の文字が置ける。

CRTC のラスタコピーは512バイト＝4ラスタを、プレーンごとにハードウェアで移す。
**発火するのは R22 の下位（転送先）を書いたとき**で、モードビットを立てたときではない。
プログラムはモードビットを立てっぱなしにしてアドレスだけ書き換えていくため。

### 色

パレット1本は `GGGGGRRRRRBBBBBI`。各色5bitと、3色で共有する最下位1bit。つまり1色6bitで、
「純粋な赤」でも他の2色が黒から1段ずれる。初見でバグに見えるので `test-x68.mjs` が
明示的にそれを検証している。

### 優先順位

グラフィック・テキスト・スプライト/BG の3層が、ビデオコントローラのレジスタ1上位バイトに
各2bitの優先順位を持つ。0が手前。同値なら **GRP < SPRITE < TEXT**（テキストが手前）で、
実際に同値のまま出しているゲームが複数ある。グラフィック層の内部では4面が同レジスタの
下位バイトに2bitずつ持ち、「優先順位スロット k に置かれているページ番号」として読む。

スプライトとBG2面は下から順に：優先度1のスプライト → BG1 → 優先度2のスプライト →
BG0 → 優先度3のスプライト。その中では**番号の小さいスプライトが勝つ**。しかも勝者は
3つの帯をまたいで記憶されるので、優先度1の若い番号が優先度3の大きい番号に勝つ。

## 6. フロッピー

`upd765.js` は無改造で使う。周りに用意しなければならなかったものが3つあり、
どれも実機の IPL ROM 相手のデバッグ1回分の値段がついた。

1. **データ要求は割り込みではない。** `upd765.js` は非DMAモードのチップを模していて、
   INT ピンが1バイトごとに上がって次を要求する。X68000 はそのピンを DMAC の DREQ に
   繋ぎ、コマンド完了割り込みは I/O コントローラ経由の IRQ1 で取る。同じピン、別のフェーズ。
   実行フェーズをCPUに流すと割り込みの嵐になる。
2. **割り込みを出さないコマンドがある。** SPECIFY / SENSE DEVICE STATUS /
   SENSE INTERRUPT STATUS は INT を上げずに終わる。`upd765.js` は全コマンドで上げる
   （PC-8801 のサブCPUはポーリングだから）。区別しないと、**ブートROM自身の割り込み
   ハンドラがポーリング側と競争して結果バイトを先に読んでしまい**、ポーリング側は
   もう起きてしまった結果フェーズを永遠に待つ。この機種で一番難しかったバグ。
3. **保留なしの SENSE INTERRUPT STATUS の結果は2バイトではなく1バイト。**
   ST0=$80 で終わる。`upd765.js` は現在シリンダのバイトを無条件に積むので、
   余った1バイトのせいで結果フェーズが CB を立てたまま残り、ROM の
   「コントローラがidleになるまで待つ」ループが返ってこない。

3つとも `upd765.js` の外（`x68fdd.js`）で処理しているので、PC-8801 の挙動は無傷。

### イメージ形式

| 拡張子 | 中身 |
|---|---|
| `.XDF` `.IMG` `.2HD` | 生ダンプ。1,261,568バイト＝77シリンダ×2ヘッド×8セクタ×1024 |
| `.DIM` | メディア種別1バイト＋トラック存在フラグ170個＋`DIFC HEADER`＋コメント、そのあと**フラグの立ったトラックだけ**を詰めたもの |
| `.D88` | 既にセクタ単位。`d88.js` が読む |

3つとも `d88.js` が作るのと同じ構造に変換する。`upd765.js` の `findSector()` が
読むのがそれだから。DIM のメディアバイトが幾何を全部決める：0=2HD(8×1024)、
1と3=2HS(9×1024)、2=2HC(15×512)、9=2HQ(18×512)。

DIM は存在するトラックしか持たないので、**トラック t のファイル位置は
「t より前にある存在トラックの数」**であって t ではない。ここを間違えると最初の
歯抜け以降が全部ずれ、ディスクはゴミとして読まれる。

## 7. タイミング

すべて 10MHz の 68000 クロックから分周される：

- 1フレーム＝水平15.98kHz なら 162,707 クロック（61.46Hz）、31.5kHz なら 180,310（55.46Hz）。
  CRTC R20 の bit4 が選ぶ
- 1ラスタ＝それを R04（垂直トータル）で割ったもの
- MFP は 4MHz。比が 5/2 で整数にならないので、タイマは**68000の半クロック**で数える。
  1 MFPクロック＝5半クロック、プリスケーラ200＝1000。浮動小数は一切出ない
- OPM のタイマはマイクロ秒。CPUクロック10個で1µs
- FDD は **244 CPUクロックに1バイト**。2HD の1トラック8KBが1回転200msだから。
  DMAC を全速で回すと、ドライバが転送の設定を終える前にセクタが届いてしまう

1ラスタは2分割して走らせる。MFP の HSYNC ピンにプログラムがポーリングできる幅を
持たせるため：ラインの `R01/R00` ぶんは low、残りは high。

## 8. 音

`ym2151.js` は OPM の実装。log/linear の対、64レートのエンベロープ表、
キーコード＋フラクションによる音程、DT1、DT2、8つのアルゴリズム（フィードバック経路は
1サンプル遅れ）、LFO4波形、8ch目最終オペレータのノイズ、ステレオ。
`ym2203.js` とは**形は似ているが中身は違う** — OPN には DT2 も LFO波形選択も無く、
音程は F-number であってキーコードではない。

この機種では2つがチップの外に配線されている。OPM の割り込みは **MFP の GPIP3**
（同期信号と同じただのピンのエッジ）。そしてレジスタ $1B の書き込みは別のチップに
繋がった2本の出力ピンを動かす：**CT1 は FDC を強制レディに、CT2 は ADPCM の水晶を半分に**する。
X68000 で ADPCM のサンプリングレートを変えるとは、ジョイスティックポートとFM音源に
書き込むことである。

`msm6258.js` は OKI のコーデックそのもの：`step(n) = floor(16 * 1.1^n)`、
3bitの大きさ、`-1/-1/-1/-1/+2/+4/+6/+8` のステップ移動、±2048でのクリップ、
そして**1バイトは下位ニブルが先**。

## 9. 検証

### 起動する

Human68k 3.1 がコマンドプロンプトまで起動する。再現手順：

```sh
node x68tools/boot.mjs --ipl IPLROM.DAT --cgrom CGROM.DAT \
                       --fd0 HUMAN310.DIM --frames 1200 --thumb
```

`768x512 nonzero=393216 (100.0%) colours=2` と、起動メッセージ＋プロンプトの
ASCIIサムネイルが出る。1200フレームは実時間で約20秒ぶん、実行は約8秒。

**ROM はこのリポジトリには入っていないし、これからも入らない。** `IPLROM.DAT` は128KB、
`CGROM.DAT` は768KB。`demo/machine.html` では**名前ではなくサイズ**で判別している。
世の中のファイル名が何種類もあるため。

### 一斉スイープ

`x68tools/sweep.mjs` はディレクトリ内のイメージを走らせ、フレームバッファだけで分類する：
`ok`（内容があり2色以上）、`flat`（1色ちょうど。正しいことも多い）、`black`（何も無い）、
`halted`（ダブルバスフォルト）、`reject`（読めなかった）。

```sh
node x68tools/sweep.mjs --ipl IPLROM.DAT --cgrom CGROM.DAT \
                        --dir <ディスクのディレクトリ> --frames 900 --json out.json
```

`docs/m88-comparison.ja.md` で PC-8801 に対してやった手法そのまま — 全部走らせて、
おかしかったものだけ追う。

### 決定論

`test-x68.mjs` は、同じIPLから2台を20フレーム走らせてCPU状態とテキスト面をバイト単位で
比較し、さらに「スナップショット→6フレーム→復元→6フレーム」でPCが一致することを見る。

## 10. 既知の穴

- **SRAM に 1MB より多いメモリを宣言すると、IPL が画面設定をしなくなる。**
  `$ED0008` が1MBなら Human68k は 768x512 のプロンプトまで起動する。2MB以上だと、
  機械は起動して走る（PCは Human68k の中を歩き、ディスクは読まれ、テキスト面は埋まる）
  のに **CRTC の R00-R09 が一度も書かれず画面は黒のまま**。バスエラーではなく
  （その範囲で1件も出ていない）、クリアループが長引いているのでもなく（6000フレームでも変わらない）、
  RAM そのものでもない（2MB搭載・1MB宣言は動く）。**未解決**。既定の1MBはこれを避けている。
- **半透明・ハーフトーン・特殊プライオリティが無い。** ビデオコントローラのレジスタ2には
  合成の第二層（グラフィック2面の平均、グラフィックとテキストの平均、全部の上に乗る
  「特殊プライオリティ」面）が上位バイトの5ビットで選べる形で載っている。ここには無く、
  ビットは保存されるが無視される。使っているのは十数本程度。
- **透明の判定がパレット番号0であって「色が黒に解決されること」ではない。** 実機は
  解決後の色を比べる。0番に黒以外を入れているプログラムは、実機では不透明、ここでは透明になる。
- **テキスト面が1024ドットでクリップせず巻き戻る。** 横スクロールを右に振った広い画面でしか見えない。
- **SASI/SCSI が無い**ので、ハードディスクイメージからは起動しない。`$E96000` は0を返し、
  ROM が `$EA0000` を叩いたときは期待どおりバスエラーになる。
- **マウスとシリアルが無い。** SCC は $FF を返す。
- **ジョイスティックのボタンは2つまで。** 6ボタンパッドの残り半分は無い。
- **MFP の Timer A イベントカウントは表示期間しか数えない。** 他のピンからは駆動できない。
- **ADPCM の出力はホストレートでのサンプル&ホールド**。再構成フィルタ無し、モノラル。
- **ディスクへの書き込みはスナップショットに入らない。** 巻き戻してもフロッピーへの
  書き込みは戻らない（`machine88.js` と同じ）。気になるなら読み取り専用でマウントすること。
- **実画面は未検証。** この文書の判断はすべてフレームバッファの統計とASCIIサムネイルから来ている。
  **ブラウザでこの機種を見た人間はまだいない。**
