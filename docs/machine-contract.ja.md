# 機種契約

このリポジトリの全機種 — PC-8001 / PC-8801 / ファミコン / PC エンジン / メガドライブ / X68000 / セタのアーケード基板 / PC-9801 / ゲームボーイ — は、ひとつの小さなインタフェースを満たしている。`demo/machine.html` のホストは、**そのインタフェースだけ**の上に早送り・巻き戻し・ジョグシャトル・ICE の分岐 undo ツリーを実装している。**契約さえ満たせば時間操作はタダで付いてくる。** 逆に契約を壊すと、時間操作は静かに壊れる — 誰も2日間気づかない壊れ方で。

`test-contract.mjs` はその契約を実行可能な検査にしたもの。**ROM は一切要らない**。見つけた機種モジュールを全部回し、機種を足して登録し忘れたら落ちる。

この文書は「10機種目を足す人」のためのもの。[§1](#1-インタフェース) がインタフェース、[§2](#2-検査) が何を検査していてどの事故から来たか、[§3](#3-新機種をスイートに乗せる) が新機種の乗せ方、[§4](#4-いま壊れているとわかっているもの) がいま落ちているものとその理由。

## 1. インタフェース

```js
class YourMachine {
  constructor(opts)               // 起動できないなら throw（ROM 無し、壊れたイメージ）
  schemaVersion                   // === モジュールが export する SCHEMA_VERSION
  frame                           // 電源投入からのフレーム数
  stepFrame()                     // ちょうど1映像フレーム走らせる；this を返す
  update(dt, onFrame)             // 実時間を溜めて、フレーム単位で吐く
  snapshot()                      // → plain data。可変なものは全部、不変なものは何も
  restore(s)                      // s を「生きているオブジェクト」に書き戻す
  render(opts)                    // → { width, height, rgb | pixels, schemaVersion }
  renderAudio(out, n)             // モノラル Float32Array を埋める；書いたサンプル数を返す
}
export const SCHEMA_VERSION = 1;
export function createYourMachine(opts) { return new YourMachine(opts); }
```

重いのは3つの性質だけ。

**決定論。** 同じ構築・同じ入力・同じ回数の `stepFrame()` → バイト単位で同一の機械。`Math.random` 禁止、`Date.now` 禁止、未初期化メモリ禁止、挿入順に依存する反復順も禁止。

**`snapshot()` は完全、`restore()` は全域。** 完全＝未来に影響する物は全部入っている（クロック・債務・ラッチ・位相カウンタ。いつも壊れるのはここ）。全域＝`restore()` はそれら全部を、**そのフレームを一度も見たことのないオブジェクト**に書き戻す。

**絵はスナップショットの一部。** [§2.6](#26-restoring-a-snapshot-brings-its-picture-back) 参照。これが「間違って見えるが正しい」やつ。

## 2. 検査

`test-contract.mjs` は各機種に10件を回す。どれも具体的な事故が理由で存在している。

### 2.0 `the screen actually moves`（画面がほんとうに動く）

契約の検査ではなく、**テストの検査**。以下の絵の検査はどれも2枚の絵を比べるが、真っ白と真っ白は等しい。だから各機種の合成プログラムは毎フレーム画面を描き替えねばならず、この検査がそれを先に証明する。

`test-gb.mjs` の言い方が一番いい：*「絵が動く ROM。counterRom() のはそうではない：タイルデータを一つも上げていないと全フレームの全画素が色0で、それに対する巻き戻しテストは落ちようがない」*。

これは両方向に効く。PC-8001 のプログラムは DMA の終端カウントを間違えていて**フレーム1で画面が凍り**、それでも他の検査は全部通っていた。PC-9801 のプログラムはフリーランのカウンタを使って20フレームで9枚しか違う絵を出さなかった — いまはテキスト GDC の VSYNC ビットを待つ。

### 2.1 `the same program run twice lands in the same place`（同じ入力を2回）

新品の機械2台、同じプログラム、N フレーム、比較。時計・`Math.random`・未初期化バッファを、スナップショットの話に入る前に捕まえる。

### 2.2 `restoring a snapshot replays the identical timeline`（巻き戻し契約）

前進→撮る→前進→戻す→前進、で同じ状態に着地する。巻き戻しリング・ジョグシャトル・ICE の undo ツリーが全部この性質の上に建っている。

### 2.3 `a snapshot restores onto a different machine instance`（別インスタンスへの restore）

**`restore()` から丸ごと抜け落ちたフィールドを捕まえるのはこの検査だけ。** その場 restore は、書き戻していないフィールドがあっても**生オブジェクトが正しい値を持ったまま**なので偶然通る。そのフレームに行ったことのない機械には、その安全網が無い。

由来：2026-08-10、PC-8801 のサブ CPU クロック（`_subMark` / `_subDebt`）が `snapshot()` から漏れていて、restore 後の機械は2つの CPU を違う相対位相で走らせていた。1〜2フレームは見えず、その後発散する。`main` に2日間乗っていた。

### 2.4 `the snapshot carries no ROM`（ROM が入っていない）

ROM は不変で、機械はもう持っている。毎スナップショットに複製を入れると、情報ゼロのまま巻き戻しリングのメモリが ROM サイズ倍になる。

判定は**サイズではなく中身**。スイートは各 ROM イメージの未使用部を marker バイトで埋め、「全部その marker の配列」と「イメージとバイト単位で一致する配列」を探す。サイズ閾値は緩すぎて何も捕まえないか、正当な理由で落ちるかのどちらかになる — PC-8801 のスナップショットは RAM 64K ＋ GVRAM 48K ＋サブ基板で、大きいのが正しい。

### 2.5 `the snapshot is plain data`（plain data であること）

スナップショットの木に入ってよいのは数値・文字列・真偽値・`null`・plain object・plain array・typed array だけ。`Map`・`Set`・クラスインスタンス・関数・`undefined` — それ以外は**ホストがコピーできない状態**であり、しかも戻り道で文句を言わず、ただ空になって返ってくる。

そのうえでスナップショットを複製し（`structuredClone`。ホストのリングが実質やっていること）、新品の機械に restore して、**1フレームも進めずに即座に**比較する。数フレーム走らせてから比べるのが、この種のバグの隠れ場所：走っているプログラムは1〜2フレームで自分の作業 RAM を上書きするので、**RAM を丸ごと失ったスナップショットでも正しい答えに収束してしまう**。

これは仮定の話ではない。`test-determinism.mjs` には「plain data に強制する」ために `JSON.parse(JSON.stringify(...))` を通し、そのあと15フレーム走らせてから比べるケースがあった。**両方の半分が間違っていて、互いに打ち消し合っていた** — [§4.1](#41-スナップショットは生の-json-を通らない) 参照。

### 2.6 `restoring a snapshot brings its picture back`（絵が戻ってくる）

**フレームバッファはスナップショットの一部である。**

ここの機種のうち3つは、ほぼ同じ言葉で逆のことを書いていた：*フレームバッファは出力であって状態ではない、次のフレームで再生成される、スナップショットはフレーム境界で撮る*。どの節も真で、結論だけが偽。理由は**誰も絵を出す前にフレームを進めないから**。`demo/machine.html` の `restoreIdx()` は restore するだけでステップせず、メインループはそのあと `render()` が返したものを描く。だから絵の入っていないスナップショットは「ユーザーがスクラブし始めたときに画面にあったフレーム」を返し、120枚リングの全スロットがフレーム120を映す。

2026-08-10 にゲームボーイで、偶然見つかった。`test-gb.mjs` の言い方：

> セタの機械はこのファイルの契約テストを全部通っていて、それでもホストが巻き戻すと250回中61回**違うフレームに着地**していた。絵が状態の関数ではなく履歴の関数だったからだ。

サイズの反論には、**省略ではなく詰めること**で答える。絵は入れ物のバッファより1画素あたりのビット数がずっと少なく、`snap.js` に道具がある：

| 機種 | スナップショットに入れる絵 | コスト |
|---|---|---|
| ゲームボーイ（DMG） | 2 bit/画素に詰める | 5,760 B |
| ゲームボーイ（CGB） | 生の `Uint16Array` | 46,080 B |
| ファミコン | 6bit パレット番号を詰める＋エンファシス面を RLE | 46,084 B |
| PC エンジン | `frameWidth x frameHeight` の窓を 9 bit/画素で詰める | 256x224 で 64,512 B |
| PC-8001 / PC-8801 / PC-9801 | **何も入れない** — `render()` がスナップショットに既にある状態から絵を作り直す | 0 B |
| セタ | **何も入れない** — `restore()` が `video.drawFrame()` を呼んで作り直す | 0 B |

最後の2行が要点：`render()` が「スナップショット済みの状態の純関数」である機種は、絵をスナップショットに入れる必要がない。**契約は観測可能な出力に対してかかっていて、フィールドに対してではない。**

検査は2つあり、**2つ目のほうが重い**：別インスタンスへの復元。これはリセット後のリングの挙動そのもので、宛先はそのフレームを一度も描いていないから、偶然通る余地が無い。X68000 は2つ目**だけ**落ちる — 独立した第2の原因がある（[§4.4](#44-x68000--原因は2つ)）。

### 2.7 `schemaVersion is on the machine and on the snapshot`

モジュールが `SCHEMA_VERSION` を export し、インスタンスが `schemaVersion` を持ち、`snapshot()` と `render()` の両方が刻印する。推測するしかないホストは、レイアウトが動いた最初の一回で推測を外す。

### 2.8 `every machine module in the tree is in the registry`

`machine*.js` を `readdirSync` してレジストリと突き合わせる。**登録されていない機種は、誰も検査していない機種。** スイートがリポジトリと一緒に育つ（静かに置いていかれない）のはこの検査のおかげ。

## 3. 新機種をスイートに乗せる

`test-contract.mjs` の `REGISTRY` に1エントリ足すだけ：

```js
{
  id: 'yourmachine',
  title: 'Your Machine',
  module: './machineyours.js',
  export: 'YourMachine',
  branch: 'your-branch',        // マージ済みなら省く。それまではこの理由で skip する
  build(M) {
    const { rom, images } = yourRom();
    return { m: new M({ rom }), images };   // `images` = ROM イメージ全部（§2.4 用）
  },
  step: (m) => m.stepFrame(),
  picture: (m) => m.render(),
  state: (m) => ({ /* 「生きている機械」から読む。snapshot() からは絶対に読まない */ }),
}
```

外してはいけない3点。

**`state()` は生の機械から読む。`snapshot()` からは読まない。** 指紋を `snapshot()` から作ると、`snapshot()` が忘れたフィールドは比較からも消え、**テストがバグに同意する**。CPU 状態・フレームカウンタ・そして**テストプログラムが実際に書いているメモリ**の一部を入れること。メガドライブのエントリがカウンタをワーク RAM にも書いているのは、指紋に中身のあるものを入れるためだけ。

**`images` はコンストラクタに渡した ROM イメージ全部。** §2.4 が未使用部を marker で埋め、スナップショットの中を探す。

**プログラムは画面を動かさねばならない。** ROM は無いので合成する。Z80 系には `z80asm.js` がある。それ以外はハンドアセンブルしたバイト列で、各行の意味をコメントに書く。一番安上がりな「動く絵」はたいてい**背景色**：レジスタ1本の書き込みで全画素を塗り替えられて、タイルデータもネームテーブルも vblank ハンドシェイクも要らない。

| アーキ | 合成プログラムが画面を動かす方法 |
|---|---|
| Z80（PC-8801） | グラフィック面 ON、`C000` に GVRAM 窓、動くパターンを書き殴る |
| Z80（PC-8001） | μPD8257 ＋ μPD3301 を N-BASIC と同じ手順で設定し、VRTC の立ち上がりごとに最上行を書き替える |
| 6502（ファミコン） | 描画 **OFF** — 2C02 は表示中の全ドットをパレット0番で塗る — で `$3F00` をループで書き替える |
| HuC6280（PC エンジン） | VDC `CR = 0`（バーストモード）で VCE パレット0番を書き替える |
| 68000（メガドライブ） | VRAM 全ゼロ → 全画素が背景色。CRAM 0番を書き替える |
| 68000（X68000） | グラフィックページ ON、GVRAM 全ゼロ。グラフィックパレット0番を書き替える |
| 68000（セタ） | 基板の背景ペン `$1F0` を書き替える |
| 8086（PC-9801） | テキスト1セルを、**GDC の VSYNC 立ち上がりで**書き替える |
| SM83（ゲームボーイ） | 縞タイル1枚と市松マップを上げてから、`LY` を見て毎フレーム1画素スクロール |

そしてゲームボーイがこのスイートに教えたこと：**「N フレーム後に絵が違う」を固定回数で assert してはいけない。** `RUN` が16で、GB のスクロールプログラムの周期がちょうど16フレーム。フレーム40はフレーム24とバイト単位で同一で、**完全に正常に動いている機械でガードが鳴った**。いまは「絵が確かに変わるまで」進める。

**今日通せない検査は理由つきの `todo` にする** — `entry.todos` に検査 id ごとのキーを置く。`test-fdc-spec.mjs` が先例：**満たしていない目標は、消すより書き残すほうが価値がある**。機種を通すために検査を消してはいけない。

## 4. いま壊れているとわかっているもの

### 4.1 スナップショットは生の JSON を通らない

全機種で `todo`。スナップショットは typed array でできていて、`JSON.parse(JSON.stringify(a))` は `Uint8Array` を `{"0":…,"1":…}` にする — そこから `TypedArray.set()` がコピーする要素数は**ゼロ**、しかも**throw しない**。つまり生の JSON 往復はスナップショットの全バッファを、完全な沈黙のうちに空にする。

いまリポジトリでこれをやっている所は無い（リングと ICE はメモリに持ち、`analysisdb.js` は独自形式）。潜在的な穴であって現行のバグではない。塞ぐには全バッファに `Array.from()`（リングの中で1バイトあたり約8バイト。リングはまさにそこを予算にしている）か、両側が合意したタグ付きエンコーダのどちらか。どちらも機種側の変更ではないので、糊塗せず記録してある。**強制される契約は [§2.5](#25-the-snapshot-is-plain-data)** のほう。

### 4.2 PC-8801

`todo` 2件。どちらも1行修正で、どちらも `machine88.js` の中 — このスイートを足した変更では編集禁止だった：

- `_snapFdc()` が `drive._idx` を複製するが、`upd765.js` はこれを最初のセクタ読みで初めて作るので、触っていないドライブは `_idx: undefined` をスナップショットに入れる。
- モジュールは `SCHEMA_VERSION` を export しているが、インスタンスもスナップショットも `schemaVersion` を持っていない。

### 4.3 メガドライブ

`mdvdp.js` が絵を `getState()` から外していて、`machinemd.js` はゲームがセーブ RAM を書くまで `sramDirty: undefined` をスナップショットに入れる。どちらも `origin/megadrive` で実測確認済み。`getState()`/`setState()` に `frameRgb` を足すと絵の2件は通る。ただし 320x240x3 = 230,400 B は横着な形：`renderLine()` は画素ごとに CRAM を RGB に解決しているので、並行する8bit面（6bit の CRAM 番号＋シャドウ/ハイライト2bit）なら 76,800 B で済み、`snap.js` の `packPixels` がもう用意してある。

### 4.4 X68000 — 原因は2つ

絵がスナップショットに無い、**かつ**、復元時に映像の画面サイズが作り直されない。CRTC のサイズを `width`/`height` に写しているのは `x68video.beginFrame()` で、それを呼ぶのは `stepFrame()` だけ — だから「restore したがまだステップしていない新品の機械」は **1x1** の絵を返す。後者は1行（`machinex68.restore()` の末尾に `this.video.beginFrame()`）で直る。両方 `origin/x68000` で確認済み。

これは**別インスタンスへの restore でしか見えない**ケースで、[§2.3](#23-a-snapshot-restores-onto-a-different-machine-instance) と2つ目の絵の検査が存在する理由そのもの。

### 4.5 PC-9801 は内部バッファを返す

失敗ではなく罠。`pc98video.render()` は `out` を渡さないと**内部バッファ**を返すので、連続する2回の結果は同じメモリを指す（他の全機種は毎回確保する）。このスイートは絵を即座にキーへ潰すので安全だが、`render().rgb` を保持するリングテストは、スナップショットとは何の関係もない理由で全スロットが同一になる。
