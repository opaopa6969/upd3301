# 5日間の自律走行から学んだこと

2026-08-08〜13、M88 を基準に PC-8801 の再現度を上げる走行を行った。同時に機種を
1 から 9 に増やし、ICE をヘッドレス化し、解析基盤を作った。

**この文書は成果の一覧ではない。同じ失敗を繰り返さないための記録。**

数字だけ先に書いておく。完全一致 304→328/353、追従 335→333/353、テスト 63→1030件。
**追従が2本減っていることに注意。** 落ちた本は1本ずつ追って、**全部 M88 が固まっている側**だと
確認した上で採用している（例: M88 は Silpheed で f500〜f3000 まで1ビットも動かない）。
だが**この走行で最も時間を使ったのは、道具と自分の測定を疑うこと**だった。

---

## 1. 測定器が何を測っているか確かめずに、出た数字を信じた

**7回踏んだ。** 全部同じ形をしている。

| 何をしたか | 何が起きたか |
|---|---|
| `grep "^T "` が 0 行 → 「M88 はその番地に到達しない」 | **そういう出力形式が存在しなかった。** どの番地でも 0 になる |
| ROM を逆アセンブルして分岐を読んだ | 実行時その番地は **RAM** で、中身が違った |
| 2つのスイープの数字を比較して「6本悪化」 | 間に**判定規則を変える commit** が入っていた。物差しが違った |
| `reach` が「f0 に到達」と報告 → その番地を調べた | 領域内の**共有番地**を拾っていた。実際の最古は f336 |
| 排他リストの筆頭を「最古の分岐」として追った | **M88 のトレースが EI 直後の命令を記録しない**だけだった（実測 22/22 で欠落） |
| 353本スイープが1行も動かない → 「この変更は無影響」（#22 の VE） | **指紋がメモリしか見ていなかった。** `ram[0xE6CD]` と tvram/gvram の非ゼロ数では、CRTC が DMA でフェッチするかは原理的に測れない。画面セルで測ったら1本のテキスト面が死んでいた |
| 「EOT はこの基板では到達不能」と結論した（#40 の EOC） | **316本・3,934回 到達していた。** M88 も EOC を返していて、しかも `refdrv` は結果フェーズを最初から全部 printf していた —— 見に行かなかっただけ |

**共通する誤り**: 検出器が鳴らないことを「異常が無い」と読んだ。
**grep が 0 を返したとき、その grep が何かを返し得るかを確かめていない。**

最後の2例は特に安い教訓だった。どちらも**到達回数を数える20行のプローブ**で決着した
（`SET INTERRUPT MASK` の unmask は353本で4本だけ・そのすべてで発火、EOT 到達は
316本で3,934回）。**「変更が効かなかった」と「変更箇所を通っていない」を先に切り分ける。**

### 対策として入れたもの

- `tools/verdict.js` — 判定ルールを pure 関数にしてテストで固定
- `tools/reach.mjs` + `reachdiff.js` — 到達集合の比較。**その道具自身のバグを2つ潰した**
- `test-determinism.mjs` — **ROM 不要**の契約テスト

## 2. 「テストがある」と「テストが走る」は別

決定論契約が main で破れ、**2日間気付かれなかった**。

**検出器は存在し、実際に鳴っていた。** ただ一度も走っていなかった:

```js
if (!rom) return t.skip('no ROM (bring your own)')   // 全ケースがこれで始まる
```

このリポジトリは ROM を同梱しない。**誰もいない部屋で鳴っていた。**

対策として `z80asm.js` で数命令を合成し、ROM もディスクも要らない契約テストを書いた
（`test-determinism.mjs`、`test-contract.mjs`）。

> **契約テストは skip できてはいけない。skip できるものは skip される。**

同じ型が別の場所でも出た。ブラウザ検証の担当が最初に書いたスモークテストは、
ROM を読ませていなかったので `if (!machine) return` に阻まれ、
**9機種ぶん「keys OK」を出しながら何も検査していなかった。**

## 3. テストが「安心する嘘」を返すことがある

- `self-regress.mjs` は `machine88.js` だけ差し替えていたので、`upd765.js` の変更に
  **「変化なし」と報告した**。木ごと比較に直した
- `test-determinism.mjs`（自分で書いたもの）に**空虚なケース**があった。
  「plain data を強制する」つもりの `JSON.parse(JSON.stringify(...))` は、
  **`TypedArray.set()` が要素を1個もコピーせず例外も投げない**ので中身を空にする。
  しかも15フレーム進めてから比較していたため**空でも収束して通っていた**。
  2つの誤りが打ち消し合っていた
- 契約スイート自身も、ガードのフレーム数16がゲームボーイのスクロールROMの周期16と
  一致して**健全な機械で誤発火**していた

## 4. 一致率で判断するのをやめた（が、根拠だけでも足りない）

**M88 は完全な金の基準ではない。** 実証済み:

- ~~**4本（Hydlide3 / Stercru / starclsr / PRO_FAN）は M88 側がディスクを起動できていない。**~~
  **これは誤りだった（2026-08-13 訂正）。** 起動できなかったのは M88 ではなく
  **こちらのハーネス**。`m88ref/refdrv.cpp` は `Mount(0, diskPath, true, 0, false)` で
  **ドライブ0にイメージ0しか挿していなかった**のに、Node 側は `parseD88All` の
  2枚目をドライブ1に挿していた。353本のうち **202本が複数イメージ**なので、
  過半数で**両者が別の機械を走らせていた**。Hydlide3 の USER ディスク、PRO_FAN の
  Gibs ディスクを要求するタイトルは、M88 側で空のドライブ1を見て N88-BASIC の
  プロンプトに落ちていた。1行足したら4本とも起動し、うち2本は**うちと完全一致**した
  （スイープ全体で 328→332 一致・333→341 追従・乖離 18→11）。
  **「M88 が gold でない証拠」の筆頭が、5日間ずっとハーネスの穴だった。**
- **M88 は実物のサブROMを走らせていない。** モーター待ちの空ループを NOP で潰している
  （`m88ref .../pc88/subsys.cpp`）
- M88 のトレースは EI 直後の命令を記録しない

だから判断基準を「M88 との一致率」から「一次資料の根拠」に切り替えた。
VSYNC 位相の修正では**完全一致が1本下がったが採用した**。

**だが根拠だけでも足りない。** シーク遅延は M88 のソースから式も単位も確定させたのに、
353本で**8本悪化・5本が起動不能**になった。

> **「根拠が正しい」と「実装が正しい」は別。**
> 採用したのは**根拠と実測の改善が揃ったとき**だけにすべきだった。

## 5. 下の層が正しくないと上の層は直せない

FDC のシーク遅延を3回実装して3回とも戻した。原因は毎回**別**で、**毎回1つ下の層**にあった。

| 試行 | 直接の失敗 | 本当の原因 |
|---|---|---|
| 1 | 効果ゼロ | 単位が10倍違った（`1 tick = 10µs`) |
| 2 | 5本が起動不能 | **CPU の時間配分が 1.39倍ずれていた**（ブースト） |
| 3 | 同じセクタを読み直す | `0300` 系ドライバは **EXM しか見ない**ので待たない |
| 4 | 永久ループ | **MSR が「導出」で、M88 は「状態変数」** |

最後に分かった構造差:

```c
// M88: status は明示的な変数。RQM が低ければアクセスを黙って無視する
void FDC::SetData(uint, uint d) {
    if ((status & (S_RQM | S_DIO)) == S_RQM) { data = d; status &= ~S_RQM; ... }
}
```

うちは MSR を `phase` から導出しているので、「RQM が低い間は無視」が表現できない。
**タイマーが成立しないのはこの1点。**

同じ依存が上流にもあった。**フレーム周期が 60Hz（誤り）だった頃に入れた
「×15 ブースト」が、周期を 55.71Hz に直した後も残っていた** ── そして
そのブーストの正体は**ハードウェアではなく M88 のROMパッチの模倣**だった。

## 6. 「M88 が何をするか」は読んだが「どう見せるか」を推測で埋めた

最後の3連続の失敗はこれに尽きる。式（`250 << n`）も単位も正確に取ったのに、
**ドライバが実際に触る部分（MSR とデータレジスタの振る舞い）を読まなかった。**

4度目に `FDC::Status()` と `FDC::SetData()` を読んで、10分で答えが出た。

> **相手の実装を参照するなら、「何を計算するか」ではなく
> 「外から何が見えるか」を読む。** 相互作用するのは後者。

## 7. 機種横断の影響は、機種を増やしてから効いてくる

- `upd765.js` は PC-8801 と **X68000 が共有**する。シーク遅延を入れたら
  X68000 の基板は時計を進めないので**シークが永久に完了しなくなった**。
  **検証していない機種の挙動は変えない**方針で opt-in にした
- フレームバッファがスナップショットに入っていない問題は、
  ゲームボーイで見つかったが**9機種中4機種で実在**した。
  「NES/MD/Seta は影響なし」ではなかった
- **統合を先延ばしにすると、統合視点でしか見えない穴が溜まる。**
  9機種を main に集約したとき、**4機種でメニューバーの ROM ピッカー項目が抜けていて
  UI からファイルを選べなかった**のと、**PCエンジンが `package.json` の exports に
  丸ごと無かった**のが同時に見つかった

## 8. 正直な報告が実際に効いた

11体のエージェントを走らせ、全員に「**通らなかったものを隠さない**」と指示した。
実際に効いた例:

- ゲームボーイ担当が「**落ちていた5件のうち4件はテストが間違っていた**」と切り分け、
  1件だけが本物のバグ（フレームバッファ漏れ）だと報告した。
  そのバグが**他3機種にも波及**した
- ブラウザ検証担当が「**最初の版は虚空にキーを叩いていて何も検査していなかった**」と
  自己申告した
- ICE 担当が codex を使えなかったので**自分で敵対的レビューをして3件見つけた**。
  うち2件は「今は無害だが将来必ず刺さる」型

**「動きました」より「実際に何が起きたか」の方が価値がある。**
9機種のうち3機種しか動かなくても、**それが分かること**が今より良い状態。

**M88 の時間モデルは、走行の最後の2日で全層が決着した:**

| 層 | 状態 |
|---|---|
| フレーム周期 71,680サイクル（24kHz/55.71Hz） | **入った** |

3層が載らなかった理由は1つだった: `upd765.js` の MSR が導出で、「RQM が低い間は
アクセスを無視」が表現できなかった。**MSR を状態変数に作り替えたら3層が同時に載った**
（#55）。M88 の `FDC::Status()` は文字どおり `return seekstate | status;` で、
状態変数以外ではありえない形をしていた。

4層目の「×15 ブースト」は**入れるのではなく消すのが正解だった**。フレーム周期が
60Hz（誤り）だった頃の穴埋めで、正体は**ハードウェアではなく M88 のROMパッチの模倣**。
しかも #55 が FDC を「commandフェーズ・RQM低」で待たせるようになって発火条件が揃い、
削除直前には **4〜12.7倍**に育っていた（二重適用）。消して完全一致は 326→328 に上がった。
**時間モデルの係数は1つも残っていない。**
