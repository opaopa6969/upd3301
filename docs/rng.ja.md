# 乱数推定器 — ゲームの乱数を同定して、いじる

*Issue [#38](https://github.com/opaopa6969/upd3301/issues/38)。ヘッドレス ICE
（[#37](https://github.com/opaopa6969/upd3301/issues/37)、[ice-design](./ice-design.ja.md)）の上に載り、
共有の解析フォーマット（[#39](https://github.com/opaopa6969/upd3301/issues/39)、
[analysis-format](./analysis-format.ja.md)）に書き出す。*

8bit 機のゲームの多くは、乱数生成器を持っていない。持っているのは**乱数テーブル**
——RAM 上のポインタで歩かれる連続したバイト列——か、4命令の LCG か、
`SRL A` / `JR NC` / `XOR n` で組んだ LFSR である。プレイヤーがやる「乱数調整」は、
その構造を外側から、フレームを数えて突く行為だ。

決定論エミュレータの上では、その構造は**見える**。CPU が行う読み出しは全部バスに出て、
しかもどのバンクが選ばれていたかが解決済みの状態で出てくる。走行全体をバイト単位で
再生できる。だからこの道具は統計から生成器を推測しない。**観測し**、モデルを立て、
そして**その状態を書き換えて再生し、当たりか外れかを証明する**。2回目の走行が
分岐しなければ、その推定は外れている。そう言う。

| ファイル | 中身 |
|---|---|
| `rngfind.js` | 推定器。pure・**import ゼロ**・決定論・機種非依存 |
| `tools/rng.mjs` | ヘッドレス CLI: `scan` / `verify` / `callers` / `predict` / `adjust` / `search` |
| `test-rngfind.mjs` | 22件、**ROM 不要**。`z80asm.js` で組んだ生成器＝答えが分かっている |

## 手順（乱数調整の実務）

```sh
# 1. 候補を探す
node tools/rng.mjs scan --disk game.d88 --settle 900 --frames 400

# 2. 1本証明する。ここが本体。
node tools/rng.mjs verify --disk game.d88 --addr E123 --value 99 --probe E123

# 3. 誰が引いているか、何が出たか
node tools/rng.mjs callers --disk game.d88 --addr E123 --notes game-rng.json

# 4. 欲しい出目を出すには今なにを書けばよいか
node tools/rng.mjs adjust --model lcg:5,1 --want 07 --in 3

# 5. 目的の状態に届く入力列を総当たりで探す
node tools/rng.mjs search --disk game.d88 --goal E123=07 --at 1500 --tries 120
```

## 同定できるもの

| 型 | 見つけ方 | 得られるもの |
|---|---|---|
| **テーブル** | 1つの PC が一定ストライドで多数の番地を読み、折り返す | 範囲・ストライド・長さ・**CPU が実際に見たバイト列**・それを指す RAM の番地 |
| **LCG** `x' = ax+c mod 2^n` | 少数の番地が、ごく少数の PC から読まれ*かつ*書かれる | `a` と `c`。総当たりで求め、全サンプルで検証 |
| **LFSR** | LCG と同じ形 | タップマスクとシフト形（Galois / Fibonacci × 左 / 右） |
| **カウンタ** | 状態の差分が一定 | 増分。フレームカウンタはこの形で、**プレイヤーが実際に動かせる種**はたいていこれ |
| **それ以外** | — | `unclassified`。サンプル数と理由つき |

`unclassified` は一級の結果である。このリポジトリの流儀は「誰にも検証できないモデルは、
空白と認めるより悪い」（[ice-design](./ice-design.ja.md)、`analysisdb.js`）。
全部に名前が付くスキャンは、どこかで嘘をついている。

## 同定できないもの

隠さずに書く。穴を隠す道具は、いちばん信用してはいけない場所で信用される。

- **バスに出ない状態。** 種を `HL` に置いたまま回す生成器や、Z80 の `R` レジスタを
  使う生成器は、メモリ監視からは見えない。`R` は実在する 8bit の常套手段で、ICE は
  実物どおり持っている——が `LD A,R` はメモリ読み出しではないので、ここからは見えない。
- **非線形な生成器。** xorshift、加算＋ローテート、「16×16 の積の上位バイト」——
  どれもカウンタ／LCG／LFSR に当てはまらない。近いものを選ばず `unclassified` を返す。
- **まだ到達していない番地。** `verify` はプログラムがまだ触っていないバイトを確認できない。
  `--at 300` で REFUTED でも `--at 1500` なら CONFIRMED、はふつうに起きる。
- **そもそも引いていないタイトル。** キー入力待ちのタイトル画面は乱数を引かない。
  `--keys`（後述）を使うか、さもないと待ちループを測ることになる。
- **見ていないバンク。** 読み出しログはバンク解決済みなので「CPU が何を見たか」は
  一意だが、切り離されている間にバンク内で起きたことは見えない。
  PC-8801 の C000-FFFF は主記憶／GVRAM／ALU が切り替わるので、**番地だけでは
  記憶素子を特定できない**。同じ番地の候補が別のバンクの読みを混ぜていると、
  値の列は意味を失い、結果は `unclassified` になる（これは正直な失敗の側である）。

## 仕組み

### 2パス構成（1パス目は安くなければならない）

**パス1（国勢調査）** は窓の全期間にわたって全メモリアクセスをタップし、カウンタだけを
持つ：番地ごとの読み書き回数、読み出し地点（PC）ごとの番地範囲・ストライドの振る舞い・
**呼び出し元の集合**。400万アクセスの走行で 0.5 秒、数 MB。

**パス2（採取）** は機械を**リセットから再走行**させ、screening を通った少数の候補に
ついてだけ `(frame, pc, addr, value, caller)` の順序つき列を残す。巻き戻さずに
再走行してよい理由はただ一つ、同入力→同走行だから。だから `open()` は毎回
*新品の*機械を返さなければならない。

### 自明でないフィルタが3つ

どれも、最初は間違えた。

1. **命令フェッチとデータ読みが同じバスに乗る。** Z80 ではオペコードの1バイトも
   `LD A,(HL)` も同じ `bus.read` を通るので、素の読み出しログは 97% が
   「プログラムが自分自身を読んだ」であり、あらゆるルーチンがテーブルを歩いて見える。
   効くのは統計ではなく厳密な判定で、**フェッチの瞬間はコアがまだ PC をそのバイトの
   先へ進めていない**ので、**`addr === pc` ならフェッチ**。実ディスクではこれで
   389万アクセス中 378万が落ちる。

2. **データ読みと一緒に記録される PC は、オペランドの*後ろ*を指す。** `8000h` の
   `LD A,(1234h)` は `pc=8003h` を記録する（オペランド2バイトを先にフェッチしたから）。
   命令ごとに一意なキーではあるので集約には使えるが、「8003h の命令」と印字したら
   それは嘘になる。`resolveSite()` が逆アセンブラで巻き戻し、その番地で終わる解釈が
   複数あるときは `ambiguous` と言う（`8002h` は1バイトの `LD (DE),A` と読め、
   これも `8003h` で終わる）。

3. **スタックは乱数の状態と見分けがつかない。** よく読まれよく書かれる RAM のバイトで、
   隣に同じようなのがもう1つある——それは 16bit の種であり、同時に機械の全スタック
   スロットでもある。さらに悪いことに、2箇所の呼び出し元を往復する戻り番地は
   **LCG に当てはまる**：`x' = 255x + (x₀+x₁) mod 256` はちょうど2周期の写像で、
   ソルバはこれを平然と名指しする。防御を3つ入れた：SP から数バイト以内のアクセスを
   落とす、書き込み元 PC が多い番地を落とす、**値の種類がほとんど無い列を拒否する**
   ——「循環している」は「生成している」ではない。

4. **待ちループのポーリングが、状態を更新するルーチンを埋める。** Ys II は
   `25D5h` を1命令から**19,782回**読む（待っている。値はずっと `07h`）一方、
   それを減らす命令からは 102 回しか読まない。混ぜると、その番地の読み出し列は
   「ノイズ入りの定数」になり何にも当てはまらない。読み出し地点で分けると、
   更新側はきれいな mod 15 のカウントダウンである。だから列は
   `(方向, PC)` ごとにも集める。長くてきれいに当てはまったものが勝つ。

### 順位付け：まず呼び出し元の多様性

いちばん効いた信号は、ストライドでも量でもなかった。

> **結果が11箇所から消費されるルーチンは乱数生成器である。呼び出し元が1つのルーチンは、
> どれだけテーブル的な読み方をしていても memcpy である。**

なので候補は、まず **呼び出し地点**（ICE のシャドウコールスタック上の戻り番地）の
種類数で、次に量で並ぶ。これは呼び出し元マップが欲しい情報そのものなので、
1回集めて2回使う。

### `--frames` より `--settle` が効く

実タイトルの最初の数百フレームはディスクローダで、ローダは1つの PC から一定ストライドで
1000バイト連続に読む——**乱数テーブルの signature そのもの**である。`--settle` を
入れるまで、実ディスクのスキャンは毎回 FDC 転送ループを1位に出していた。既定は 600。
ゲームが実際に動き始めるまで上げる。

### `--keys`：タイトル画面を抜ける

タイトル画面は乱数を引かない。`--keys space,enter,z --every 60 --hold 6` はそれらを
順に押す。押し方は**フレーム番号の純関数**でなければならない——rngfind は採取のために
リセットから再走行し、検証のためにもう一度走るので、走行ごとに入力が違えば
「再生」が別の実験に化けたまま、見た目は同じになる。

マトリクスは `demo/machine.html` で確定した PC-8801 の配列（row 9 は
`SPACE ESC TAB ↓ BS INS CR ←`。PC-8001 の row 9 とは**違う**）。

## 検証 — 推定を主張に変える唯一の手順

```
node tools/rng.mjs verify --disk game.d88 --addr E123 --value 99 --probe E123
```

リセットから2回走らせ、走行 B では `--at` のフレームで1バイトだけ書き換える。
そのあと両方を `--frames` だけ進め、2つのダイジェストを比べる。

- **重複除去した PC トレース** — プログラムは違う分岐を通ったか？　機種非依存で、
  メモリ比較よりずっと強い。
- **プローブ** — 読み出し列をハッシュする番地または範囲。**範囲**プローブは
  `(番地, 値)` の対をハッシュする。テーブルの*中身*は変わらないので、値だけを
  ハッシュすると、ポインタを動かして全く違うエントリを引くようになっていても
  「何も起きなかった」と報告してしまう。合成テストで実際に踏んだ偽陰性である。

判定は3つ。

- **CONFIRMED** — 実行した命令列が変わった。因果がある。
- **PARTIAL** — 値の列は変わったが制御フローは変わらない。**そのバイトはデータの
  上流であって、判断の上流ではない**（この窓では）。実タイトルで最初に踏んだのが
  これで、1942 の毎フレームカウンタを書き換えたら値は確実に変わったのに
  515,261 命令がバイト単位で一致した。乱数調整に一日費やす前に知りたい情報である。
- **REFUTED** — 何も変わらない。スキャンが外れている。**これは道具が働いている
  証拠であって、失敗ではない。** 次の候補へ行け、という意味。

正直な注意：値で**分岐しない**消費者しか持たない生成器は、PC トレースを変えない。
直線コードは違う数から同じトレースを出す。プローブはそのためにある。

## 呼び出し元マップ — 人間が書く部分

同じテーブルでも `8C10h` から引けばエンカウント判定、`8C44h` から引けばクリティカル
判定である。それを自動で見分けられる道具はない。できるのは、**分けて・数えて・
あなたが書いた注釈を保持すること**だ。

```sh
node tools/rng.mjs callers --disk game.d88 --addr E123 \
     --notes game-rng.json --note 8C10=エンカウント判定 --export game-rng-doc.json
```

- 呼び出し地点は ICE のシャドウコールスタックの戻り番地から取る。つまりキーは
  「どの命令が読んだか」ではなく「**誰が数を要求したか**」；
- 注釈のとなりに実測の値分布が残る。`analysisdb.js` は書かれた `expected`（"1/16"）が
  実測と食い違うと**警告**する。別の ROM リビジョンでは正しかった注釈を捕まえられる；
- `--notes` は JSON ファイルと往復するので、注釈はセッションをまたいで生き、
  diff としてレビューできる；
- `--export` は[解析ドキュメント](./analysis-format.ja.md)を書く。注釈済みの
  呼び出し元はラベルになり、**未注釈のものは数値を持ったまま `unclassified` になる**。
  数えたことと理解したことは別だからだ。

## 予測と調整

```sh
node tools/rng.mjs predict --model lcg:5,1 --state 07 --n 16
node tools/rng.mjs adjust  --model lcg:5,1 --want 07 --in 3
```

`adjust` が調整側の本体で、状態空間（256 か 65536 通り）を総当たりして
「`--in` 回引いたら `--want` が出る」状態を**全部**印字する。ゲームによっては
自分の種を検査するので、もっともらしいものを選べるようにするためだ。乗数が偶数の
LCG では写像が全射でないので「そんな状態は無い」が正しい答えになることもある。

そのあと、機械の上で `verify` すること。信じるのはその後で。

## 入力探索（`search`）

```sh
node tools/rng.mjs search --disk game.d88 --goal E123=07 --at 1500 --frames 30 --tries 120 --press space
```

`--at` でスナップショットを取り、「W フレーム待つ」×「キーを押す」を総当たりし、
外れたら `restore` して次へ行く。**総当たりが正しく効くのがこの土台の強み**で、
実機やサイクル不正確なエミュでは再現しない。当たった計画はフレーム数で印字されるので、
そのまま再生できる。

`snapshot()`/`restore()` を持たない機械では、その旨を返して何もしない
（毎回リセットから走り直しても正しいが、一日かかる）。

## この手法自体の限界

- 見ているのは*プログラム*がやっていることで、*ハードウェア*がやっていることではない。
  未実装のデバイスを種にしている生成器は、正しく同定されて間違った予測をする。
- 自己書き換え・復号される乱数コードは静的には割れない。読み出しログはアクセスを
  見ているので候補としては出るが、`resolveSite` は*いま*その番地にあるものを
  逆アセンブルする。
- `distinct` 集合は読み出し地点ごとに上限（既定 512）がある。溢れた walker は
  黙って小さく報告されるのではなく `distinctCapped` が立つ。
- 68000 / 6502 のアーキ記述子にはまだ逆アセンブラが無い（[ice-design](./ice-design.ja.md)）
  ので、それらの機械では読み出し地点が素の番地で出る。それ以外は全部動く——
  推定器は仕事のために命令をデコードしない。

## テスト

`test-rngfind.mjs` は ROM も DOM も要らない。`z80asm.js` で 4種類の生成器を組む
——LCG（`x' = 5x+1`）、RAM のインデックスで歩く 256 バイトのテーブル、
タップ `B4h` の Galois LFSR、そしてテーブルから自然に出てくるインデックスカウンタ——
そして**ソースに書いてある定数**を推定器が言い当てることを assert する。
うち2件は「当たること」ではなく「**間違わないこと**」のテストである：
スタックが生成器として報告されてはならない、xorshift は名前を付けられずに
`unclassified` で返らなければならない。
